# Комплексный аудит проекта Global Info / Digital Profile

Дата: 2026-07-18.
Объём проанализированного кода: ~123 000 строк TS/TSX в `src/modules/digital-profile`, ~16 000 строк Python в `renderer/`, 260 скриптов, 42 модели Prisma.

Документ структурирован так: сначала карта того, как реально работает канонический пайплайн, затем — **разбор главной проблемы (полупустые слайды)** как цепочки «воронок», через которые теряются данные, затем — оценка «генерации частями», и в конце — остальные архитектурные, инженерные и продуктовые проблемы с приоритизированными рекомендациями.

---

## 1. Как на самом деле устроен канонический пайплайн

Единственный «живой» путь генерации отчёта — unified collection job (single CTA):

```
POST /api/digital-profile/cases/[id]/unified-collection
  └─ unified-orion-collection-orchestrator.ts (стейт-машина, файловый job store)
      1. BASE_COLLECTION      → runFullAudit (Yandex/Google/Wikipedia/поверхности) → дельта-манифест ID-шников
      2. ARSENKIN_ENRICHMENT  → 5 агентов Arsenkin (check-top, suggest, paa, ai-serp, check-h/indexation), durable poll
      3. COMPOSITE_MERGE      → composite-serp-merge.ts (дедуп base + arsenkin), subject-profile bootstrap
      4. ORION_PREPARE        → canonical-report-prepare.ts:
           аналитика (runOrionAnalyticsPipeline):
             subject-resolution-classifier → surface-analyzers → finding-synthesizer → executive-summary
           визуальные ассеты (canonical-visual-assets.ts, SVG→PNG через sharp)
           GPT stage 1 (gpt-case-analysis.ts — весь корпус одним вызовом)
           детерминированные fragment-builders (36 канонических слотов)
           GPT stage 2 (llm-slide-copy.ts — по одному вызову на фрагмент)
           deck-assembler → один render (HTTP Python renderer /orion/render-golden)
      5. REPORT_READY / COMPLETED_PARTIAL
```

Сильные стороны, которые стоит зафиксировать: fail-closed-гейты на каждом шаге, линейдж артефактов (caseId/datasetId/hash), идемпотентный resume, evidence-first контракты, продуманная защита от «чужих»/устаревших паков. Инженерная культура на уровне оркестрации высокая. Проблема не в надёжности доставки, а в том, **сколько контента доживает до слайдов**.

## 2. Главная проблема: полупустые слайды. Цепочка воронок потери данных

Слайды «проходят по фоллбеку» не из-за одного бага. Это суперпозиция 8–9 независимых воронок; на каждой теряется часть данных, и честные empty-state шаблоны («материалы не зафиксированы», «подтверждённых тем нет», VISUAL_ASSET_UNAVAILABLE) срабатывают одновременно на многих страницах. Ниже — воронки в порядке ущерба.

### F1. Сверхжёсткий классификатор идентичности субъекта — главный фильтр-«мясорубка»

`orion-golden/analytics/subject-resolution-classifier.ts:97-186`

Материал получает статус `SUBJECT_MATCH` **только если в title+snippet+URL одновременно найдены фамилия И (имя ИЛИ отчество ИЛИ строгий идентификатор)**. Поисковый запрос (`item.query`) в матчинг сознательно не входит (`itemText()`, строки 50-56).

Последствия:
- Заголовки/сниппеты SERP короткие и часто содержат только фамилию → решение `AMBIGUOUS (surname_only, confidence 0.4)`.
- `AMBIGUOUS` материал **исключается из KPI, findings, матрицы рисков и региональных выводов** (в `finding-synthesizer.ts` он попадает только в `ambiguousFindings` → приложение).
- Результат: в БД сотни собранных материалов, а `subjectMatchCount` — единицы. Executive summary становится `sparse`, матрица рисков рисует строку «Нет подтверждённых тем», региональные саммари — «подтверждённых тем не выявлено».

Это ровно симптом «информации достаточно, но слайды полупустые». Строгость сама по себе методологически оправдана (surname-only не должен быть доказательством), но:
- нет промежуточного уровня «вероятно субъект» с явной пометкой для клиентских страниц;
- контекст запроса полностью игнорируется, хотя выдача получена по запросу с полным именем — это байесовский сигнал, который сейчас выбрасывается;
- majoritized-решение принимает substring-матчинг со срезанием одной буквы (`matchesToken`) — и по-русски, и по-латински это даёт как ложные пропуски (склонения длиннее 1 буквы: «Петровым»), так и ложные конфликты.

### F2. Findings рождаются только из 7 захардкоженных регексов тем

`orion-golden/analytics/finding-synthesizer.ts:39-97`

Даже прошедший идентификацию материал не станет finding'ом, если его текст не матчится ни на одну из 7 тем (`security_scrutiny`, `criminal_legal`, `pep_rca_watchlist`, `political_exposure`, `offshore_corporate`, `family_associates`, `business_profile`). Кто не попал — просто не существует для матрицы рисков, executive summary и сайдбаров.

Отдельно: ключевые слова явно подогнаны под один конкретный прошлый кейс — `транспортн\w+ контур`, `логистик`, `оборон`, `девелоп` (см. также `UNVERIFIED_DOMAINS = /rucriminal|sledstvie|.../` в `run-analytics-pipeline.ts`). Для субъекта из другой отрасли (медицина, финтех, шоу-бизнес) детекция тем деградирует, и отчёт снова пустеет. Это генерализационный дефект, а не только полнота словаря.

### F3. GPT-слой по умолчанию выключен и не задокументирован в env

- `config.ts:143` — `DIGITAL_PROFILE_AI_ANALYST_ENABLED` по умолчанию `false`.
- В `.env.example` (223 строки), `.env.production.example` и `railway.app.json` **нет ни `DIGITAL_PROFILE_AI_ANALYST_ENABLED`, ни `OPENAI_API_KEY`** — деплой «по документации» гарантированно работает без GPT.
- Без GPT все слайды заполняются детерминированными шаблонными фразами из `fragment-builders.ts` («Существенных материалов не обнаружено», «Мониторить изменения выдачи») — текст выглядит как фоллбек, потому что это он и есть.

### F4. GPT-фоллбеки массовые и почти бесшумные

- **Stage 1** (`gpt-case-analysis.ts:135-190`): любая ошибка транспорта/схемы/санитайзера → `null` → весь отчёт без целостного анализа. Причина пишется только в `gpt-case-analysis-diagnostics.json` внутри job-каталога; в `job.warnings` и UI не поднимается.
- **Stage 2** (`llm-slide-copy.ts`): каждое поле проходит бюджет длины, скан internal-токенов (`\baudit\b`!), скан forbidden-токенов (включая **любой** snake_case через `ENUM_TOKEN_PATTERN`), domain-gate. Отклонённое поле молча остаётся черновиком. Статусы (`FALLBACK_ERROR`, `FALLBACK_VALIDATION`, `rejectedFields`) пишутся в `gpt-report-copy.json`, но не агрегируются ни в job-статус, ни в UI.
- **429 не ретраится**: `openai-json-client.ts:79` — `OpenAiRateLimitError` пробрасывается немедленно, без backoff. Stage 2 делает ~15–20 последовательных вызовов; первый 429 почти гарантирует, что весь хвост фрагментов уйдёт в `FALLBACK_ERROR` (цикл в `enhanceSectionPacksWithGptCopy` продолжится, но каждый следующий вызов снова словит 429).
- `maxOutputTokens` = 8000 при `reasoning.effort: low` — на большом корпусе stage 1 реально может обрезаться, что даёт invalid JSON → 3 ретрая с тем же лимитом → fail.

### F5. Дельта-манифест базового сбора: повторные прогоны теряют исторические данные

`services/base-collection-manifest.ts:43-91`

Манифест собирает **только ID, созданные во время текущего прогона** (снимок before/after). Агенты при этом дедупят по хэшу («re-runs are idempotent»). Итог для повторного запуска unified collection по уже наполненному кейсу:

- если дельта полностью пуста — есть фоллбек «взять все текущие ID» (ок);
- **если дельта частично непуста** (например, Яндекс отдал 3 новых результата и 50 уже существующих) — в манифест попадут только 3 новых, а 50 старых исчезнут из composite и из отчёта.

Костыль «case-corpus supplement» в `composite-serp-merge.ts:250-267` подмешивает старые строки **только** типов `IMAGE_RESULT` и `KNOWLEDGE_BLOCK`. Органика, подсказки, related-запросы прошлых прогонов теряются. Это второй по вероятности источник «в БД много, в отчёте пусто».

### F6. Комплаенс-данные и ручная разметка аналитика не доходят до канонического отчёта

Канонический inventory строится **исключительно** из composite-наблюдений (`canonical-report-prepare.ts:169-212` — SearchResult + SearchSurfaceItem + Arsenkin). В него не попадают:

- `DatabaseProfile` (LexisNexis/Dow Jones/World-Check импорты) — при этом surface-анализатор `compliance` (`surface-analyzers.ts:179-187`) ждёт `evidenceType: compliance_hit` / `source: database_profile`, которых в inventory не бывает → **слайды p33–p36 всегда рендерятся «Совпадений не зафиксировано»**, даже когда в БД лежит импортированный профиль;
- `RiskFinding` (детерминированный risk-classifier, стадия I) и его review-статусы;
- ручные переразметки результатов (`search-results/classify`, adverse/neutral overrides);
- решения manual review (`orion-golden/manual-review`, `admin-review-decisions` — маршруты и UI существуют, но канонический prepare их не читает; проверено grep'ом по analytics/deck-sections/prepare);
- реальные скриншоты (`Screenshot`) и `WikipediaCheck`.

То есть заявленный процесс «собрали → сохранили → **отфильтровали руками** → собрали презентацию» в каноническом пути разорван: этап ручной фильтрации ни на что не влияет.

### F7. Визуальные ассеты — единая точка отказа с тихой деградацией

`canonical-report-prepare.ts:459-483`: весь блок `buildCanonicalVisualAssets` обёрнут в один try/catch. Любое исключение (типичный кандидат — `sharp` без нативных бинарей на деплое: `media-asset-svg.ts:1`, `serp-snapshot/renderer.ts:10`; или сетевые fetch превью изображений) обнуляет **все** ассеты сразу → каждый визуальный слот (SERP-снимки, панели подсказок, гриды изображений, AI-панели — ~15 страниц) деградирует в текстовую карточку `VISUAL_ASSET_UNAVAILABLE`. Предупреждение попадает только в `canonical-prepare-summary.json` (`visualAssetWarning`), не в `job.warnings`, не в UI.

### F8. NETWORK_CALLS=0 и «честные пустые» Arsenkin-агенты

`unified-orion-collection-orchestrator.ts:766-769` + `arsenkin-enrichment-tick.ts:1029` — при `NETWORK_CALLS=0` все 5 агентов обогащения синтетически завершаются `EMPTY_VALID`. Пайплайн доходит до REPORT_READY, но страницы подсказок/PAA/AI-ответов/индексации заполняются coverage-empty шаблонами. Одна переменная окружения на проде/стейдже → внешне «успешный», но наполовину пустой отчёт. Аналогично `ARSENKIN_ENABLED=false` (дефолт в `.env.example`).

### F9. Fail-closed рендерер валит весь отчёт из-за одного токена

`renderer/orion_golden_renderer.py:783-926` — сайдбар-QA бросает `RuntimeError` на весь рендер, если в клиентском тексте встретились «…»/`...` или токен из banned-регекса (включая `\bAPI\b`, «движок»). Три разных набора запрещённых токенов (TS `client-text-sanitizer.ts`, TS `llm-slide-copy.ts`, Python banned-regex) не синхронизированы — текст, прошедший TS-фильтры, может уронить Python (`RENDER_FAILED` всего джоба). Слово «API» в русском клиентском тексте — реалистичный сценарий.

### F10. Сопутствующие мелочи, усиливающие «пустоту»

- `compositeObservationsToInventory` ставит всем материалам `collectedAt: new Date(0)` (1970 год) — любые будущие фичи со свежестью/датами сломаны заранее.
- KPI-карточки исполнительного резюме показывают «Материалов: N, О субъекте: 2, Тем риска: 0» — сама вёрстка честно подсвечивает воронку F1/F2 клиенту.
- SERP-таблицы (p09/p26) рисуют все строки выдачи, а выводы рядом строятся только из findings → визуальный контраст «таблица полная, выводы пустые» внутри одной страницы.
- Стадия `CLIENT_CONTENT` объявлена в стейт-машине, но нигде не устанавливается (обрабатывается тем же `stepPrepare`) — мёртвый стейт.

### Сводная схема воронки

```
Собрано в БД (сотни строк)
  → дельта-манифест (F5: −исторические строки)
  → composite merge (ок, дедуп)
  → subject resolution (F1: большинство → AMBIGUOUS/INSUFFICIENT)
  → finding synthesis (F2: −всё вне 7 регекс-тем)
  → fragment builders (честные empty-state при пустых findings)
  → GPT stage 1/2 (F3/F4: выключен или молча откатился)
  → визуальные ассеты (F7: все или ничего)
  → renderer (F9: может убить весь рендер)
= полупустая презентация при полной БД
```

Отдельно подчеркну: **системной телеметрии по этой воронке нет**. Каждый этап пишет свой локальный артефакт (`subject-resolution.json`, `gpt-report-copy.json`, `visual-assets-by-slot.json`, `emptyStateReason` на слайдах), но нигде нет сводки «из 480 собранных материалов до слайдов дошло 12, причины: …». Поэтому проблема и выглядит как мистика.

## 3. «Генерация частями»: что уже есть и чего не хватает

Хорошая новость: **почанковая генерация архитектурно уже реализована** — это не нужно строить с нуля:

- контент собирается независимыми fragment-builder'ами по 36 канональным слотам;
- GPT stage 2 делает **отдельный вызов на каждый фрагмент** со scoped-контекстом (только свои findings + черновик + общий caseAnalysis) — ровно та схема «части, чтобы модель не теряла контекст», которую вы описываете;
- есть кэш паков по contentHash (`loadPreviousPacks`) и render-only resume.

Реальные пробелы:

1. **Нет устойчивости цепочки вызовов.** Вызовы фрагментов идут строго последовательно без очереди, без ретраев на 429/5xx (429 явно пробрасывается без backoff). Долгий прогон = высокая вероятность, что половина фрагментов откатится к черновику. Нужно: очередь с ограничением конкуренции, экспоненциальный backoff на 429, персистентный чекпоинт «какие фрагменты уже улучшены» с дозапуском только неудачных (сейчас частично есть через `SKIPPED_CACHED`, но только в рамках одного prepare-цикла и без отдельного retry-эндпоинта).
2. **Stage 1 монолитен.** Весь корпус (все findings + все surface units + метрики) уходит одним вызовом с `maxOutputTokens=8000`. На больших кейсах это и токен-лимит, и потеря деталей. Логичное развитие: map-reduce — по-фрагментные мини-анализы → сводка.
3. **Фоллбек невидим.** Частичная генерация без отчёта о том, какие части «настоящие», а какие — черновик, неотличима от сломанной. Нужен агрегированный отчёт качества генерации в статусе джоба и в UI (см. рекомендации).

## 4. Архитектурные проблемы кодовой базы

### 4.1. Пять поколений пайплайнов отчёта сосуществуют

| Пайплайн | Статус | Код |
|---|---|---|
| report-builder v1/v2/v3 + Python `report_template_v1-3.py` | жив, вызывается из UI (`ReportPreviewPanel` → `/report/generate`) | ~5.6K строк TS + Python |
| orion-v2 (`orion-v2-report-service`) | жив, панель в UI | ~0.7K |
| orion-client-storyboard (R9.9–R9.12) | жив, панель в UI | ~3.9K |
| orion-report-spec (R9.7) | полуживой, вызывается из smoke | ~4.8K |
| orion-section-pipeline (микростейджи, supabase-план) | мёртвый в рантайме | ~5.6K |
| orion-golden canonical (unified) | канонический | ~36K |

Три маршрута помечены `RETIRED` и возвращают 410, но их клиентские панели и сервисы живы. UI одновременно предлагает 4 способа получить отчёт с разным содержимым — это гарантированная путаница для операторов и рассинхрон выводов. Prisma-схема несёт ~10 моделей мёртвого микростейдж-пайплайна (`OrionReportMacroSection`, `OrionSectionAgentRun`, `OrionSectionAnalysis`, …).

### 4.2. Файловое состояние вместо БД

Job store, все артефакты, лизы и чекпоинты живут в `process.cwd()/storage/...` (`unified-collection-job-store.ts:24`). Прогресс-поллинг — in-process `Set` + `setTimeout`. Следствия: невозможен горизонтальный масштаб (вторая реплика не видит лизов первой корректно, файловый лиз не атомарен между хостами), эфемерная ФС без volume теряет джобы, бэкапится только БД — артефакты нет. При этом `report-data-binding`, аналитика и решения по сути реляционные и просятся в Prisma (модели для этого частично уже есть и не используются).

### 4.3. Размеры и навигация

- Файлы-гиганты: `arsenkin-ui-orchestration-service.ts` (2280), `fragment-builders.ts` (1873), `orion_golden_renderer.py` (2017), `arsenkin-case-agent-execution.ts` (1403), оркестратор (1357).
- Имена артефактов эпох (`r98a-...`, `run-r99-...`, `smoke-orion-lexis-gpt55-e2e-r93.ts`) внутри `src/` — исследовательские прогоны конкретных кейсов лежат рядом с прод-кодом и экспортируются из `index.ts` модулей.
- 216 npm-скриптов, из них 144 smoke.

### 4.4. Отсутствие нормального тестового контура

Нет ни одного unit-test фреймворка (jest/vitest отсутствуют в зависимостях), нет скрипта `test`, нет CI-конфигурации в проекте. Вся проверка — самописные smoke-скрипты, которые (а) не дают структурированного прохода/провала по наборам, (б) во многом сами являются исследовательскими прогонами. Плюс **каталог не является git-репозиторием** — если это рабочая копия, история и ревью-процесс отсутствуют как класс.

### 4.5. Тройная дубликация клиентских санитайзеров

Списки запрещённых токенов и бюджеты длины реализованы независимо в трёх местах (TS-санитайзер, TS-фильтры stage 2, Python banned-regex + бюджеты рендерера). Они уже разъехались (см. F9). Единый контракт (общий JSON со списками/бюджетами, потребляемый обеими сторонами) снял бы целый класс `RENDER_FAILED`.

### 4.6. Жёсткая привязка к структуре «RU + UAE, 36 слотов»

Канонические слоты, регионы (`normalizeCompositeRegion` маппит всё нероссийское в «UAE»), лейблы движков и региональные фрагменты захардкожены под формат одного эталонного отчёта (report-72). Кейс «субъект из Казахстана/Европы» либо ляжет в неверный региональный контур, либо даст пустой UAE-раздел из шаблонов.

### 4.7. Прочее

- `digitalProfileConfig.aiAnalyst.model` по умолчанию `"gpt-5.5"` — строка, не валидируемая против реальных моделей; при опечатке в env всё тихо уходит в фоллбек (см. F4).
- `renderDeckViaHttp` таймаут 300 с на один вызов, без ретраев; холодный старт LibreOffice на Railway реально может дать первый `RENDER_FAILED` (потом лечится resume'ом, но это ручной шаг recover).
- `pumpResumableUnifiedCollections` работает только в кастомном лаунчере `scripts/start-with-arsenkin-readiness.ts` — запуск `next start` напрямую молча лишает систему авто-резюма.
- Смешение ответственности: `services/` содержит и оркестрацию, и доменную логику, и адаптеры провайдеров.

## 5. Проблемы бизнес-логики (сверх воронки)

1. **Ручная фильтрация не влияет на отчёт** (F6) — ключевой разрыв с заявленным процессом. Аналитик размечает, клиент получает отчёт, собранный без учёта разметки.
2. **Методологическая непрозрачность для клиента**: смесь «жёстко верифицированных» выводов (почти всегда пустых) и полных сырых таблиц на соседних страницах читается как противоречие. Нужен явный слой «наблюдения» между «сырьём» и «верифицированными findings».
3. **Отсутствие дат и свежести**: материалы без дат (1970), нет понятия «изменилось с прошлого прогона», хотя повторные прогоны — основной сценарий мониторинга.
4. **Экономика повторных прогонов**: `confirmPaidRecollection` защищает от случайной оплаты, но из-за F5 повторный платный сбор ещё и ухудшает отчёт — прямо противоположно ожиданиям заказчика.
5. **Захардкоженные под прошлый кейс словари** (F2, `UNVERIFIED_DOMAINS`, `REPUTABLE_DOMAINS`) — качество отчёта скрыто зависит от того, насколько новый субъект похож на эталонного.

## 6. Надёжность и безопасность (кратко)

Положительное: auth fail-closed в деплой-окружениях (`middleware.ts`), подписанные URL на скачивание, ключи не логируются, traversal-safe storage keys, санитизация ошибок рендерера, evidence soft-delete.

Замечания:
- `DIGITAL_PROFILE_AUTH_ENABLED=false` — дефолт; защита держится на эвристике `isDeployLikeEnvironment` (если окружение не распознано как deploy-like, админка открыта).
- Файловые артефакты (включая PII-содержащие composite-наблюдения и отчёты) вне контура БД-бэкапов и вне контроля доступа БД.
- В `llm-slide-copy`/`gpt-case-analysis` полные тексты findings уходят в OpenAI — это ок по модели, но нигде не зафиксировано в SECURITY.md (там описан только «LLM не источник истины»).

## 7. Рекомендации по приоритетам

### P0 — прямое лечение «полупустых слайдов»

1. **Наблюдаемость воронки.** Один сводный артефакт + блок в статусе джоба и в UI: сколько материалов на каждом этапе (собрано → в манифесте → в composite → SUBJECT_MATCH/AMBIGUOUS → в findings), статус GPT stage 1, per-fragment статусы stage 2, `visualAssetWarning`, счётчик слайдов с `emptyStateReason`. Это превращает «мистику» в диагноз за минуту. Почти все данные уже пишутся в разрозненные JSON — их нужно только агрегировать.
2. **Включить и задокументировать GPT-слой**: добавить `DIGITAL_PROFILE_AI_ANALYST_ENABLED`, `OPENAI_API_KEY`, модель и `ORION_GPT_REPORT_COPY` в `.env.example`, `.env.production.example`, `railway.app.json`; в env-validation — жёсткое предупреждение (или отказ) при генерации клиентского отчёта без AI, раз уж есть флаг `orionV2RequireAi` с той же семантикой.
3. **Смягчить воронку идентификации**: (а) учитывать текст запроса как сигнал (материал получен по запросу с полным именем); (б) ввести промежуточный уровень «вероятно субъект» и показывать такие материалы на страницах с явной маркировкой, не включая в KPI; (в) добавить опциональный LLM-этап идентификации для AMBIGUOUS с сохранением evidence-обоснования.
4. **Починить дельта-манифест**: манифест повторного прогона должен явно включать исторические ID кейса для всех типов поверхностей (как уже сделано для IMAGE/KNOWLEDGE), с пометкой «из корпуса кейса» в provenance.
5. **Подключить комплаенс и ручную разметку к каноническому inventory**: конвертировать `DatabaseProfile`, `RiskFinding` (approved), classification-overrides и manual-review решения в `RawInventoryItem`/фильтры до аналитики. Иначе слоты p33–p36 и этап ручной фильтрации остаются декоративными.

### P1 — генерация частями и устойчивость GPT

6. Очередь GPT-вызовов с конкуренцией 1–2, экспоненциальный retry на 429/5xx, персистентный чекпоинт по фрагментам + отдельная операция «дожать неудачные фрагменты» без пересборки колоды.

9. Гранулярность визуальных ассетов: try/catch вокруг каждого ассета, а не всего блока; warning каждого — в `job.warnings`.
10. Единый источник правды для forbidden-токенов/бюджетов TS и Python; в Python-рендерере — деградация проблемного блока вместо `RuntimeError` на весь рендер (с QA-отметкой в meta).

11. Удалить/заархивировать мёртвые пайплайны (orion-section-pipeline, orion-report-spec, storyboard, report v1–v3) и их панели UI и Prisma-модели; оставить один CTA.

13. Ввести unit-тест фреймворк + CI; конвертировать критичные smoke в тесты; вынести исследовательские `run-r9*`-скрипты из `src/`.

15. Инициализировать git (если это не артефакт копирования), настроить ревью-процесс.
