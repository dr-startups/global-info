# План исправления: насыщенная, читаемая и достоверная презентация

Основан на `PROJECT_AUDIT.md` (воронки F1–F10, приоритеты P0–P2). Цель программы:

> Из собранных по кейсу данных в презентацию попадает максимум фактического материала;
> каждый вывод обоснован evidence; пустой слайд возможен только когда данных
> действительно нет — и тогда он честно объясняет почему; оператор видит причину
> любой деградации за минуту.

## Как пользоваться планом

- Шаги атомарны: один шаг = одна ветка/сессия Claude Code = один проверяемый результат.
- У каждого шага: **Цель → Файлы → Что сделать → Приёмка** (offline-проверка без сети/платных API, если не указано иное).
- Зависимости указаны явно; внутри фазы шаги по возможности независимы.
- Метрики успеха программы — в конце документа; после каждой фазы прогоняется «золотой кейс» (см. Шаг 0.3).

Сквозные правила для всех шагов:
1. Не ломать fail-closed гейты и evidence-first инварианты — ослабляем фильтры добавлением *новых явных уровней*, а не отключением проверок.
2. Любая деградация (fallback, пропуск, пустой слот) обязана оставлять машиночитаемый след, агрегируемый в отчёт качества (Шаг 0.1).
3. Каждый шаг сопровождается offline-smoke или unit-тестом; существующие smoke не должны краснеть.
4. Клиентский текст — только русский, без внутренних токенов; бюджеты длины берём из единого контракта (Фаза 6).

# Фаза 0. Наблюдаемость воронки (фундамент, делается первой)

### Шаг 0.1. Сводный `report-quality-summary.json` + агрегатор воронки

**Что сделать:**

- Источники уже существуют: `subject-resolution.json`, `verified-finding-bundle.json`, `gpt-report-copy.json`, `gpt-case-analysis-diagnostics.json`, `visual-assets-by-slot.json`, `assembled-deck.json` (`emptyStateReason` на слайдах), `arsenkin-enrichment-state.json` — агрегатор их читает из job-каталога, ничего не пересчитывая.
- Для `dbSearchResults/dbSurfaceItems` — count-запросы Prisma по caseId (передавать prisma опционально, offline-тесты без него ставят null).
- Писать артефакт в job-каталог и класть компактную выжимку в `job.reportQuality` (расширить `UnifiedCollectionJob` в `unified-collection-types.ts`).
**Приёмка:** новый `scripts/smoke-report-quality-summary.ts` на фикстурах: подсунуть готовый job-каталог с разными артефактами → проверить корректность агрегатов; существующий `smoke:unified-orion-collection` зелёный.

**Цель:** стабильный полный набор входных данных, на котором меряем насыщенность отчёта до/после каждой фазы.

# Фаза 2. Идентификация: меньше ложных «не о субъекте», без потери строгости

### Шаг 2.1. Трёхуровневая модель принадлежности: LIKELY_SUBJECT
**Цель:**材ериалы «фамилия + сильный контекст» перестают проваливаться в небытие, но не смешиваются с подтверждёнными.
**Файлы:** `orion-golden/contracts/common.ts` (расширить `SubjectRelevanceDecision`), `subject-resolution-classifier.ts`, `surface-analyzers.ts`, `finding-synthesizer.ts`, `deck-sections/scoped-input.ts`, `fragment-builders.ts`.
**Что сделать:**
- Новое решение `LIKELY_SUBJECT` (confidence 0.6–0.7) для случаев: фамилия + ≥1 контекст-идентификатор (уже майнится в `subject-context-miner.ts`); фамилия + совпадение домена с доменами SUBJECT_MATCH-материалов того же прогона; подсказка/PAA, содержащая полное имя из запроса.
- KPI и «подтверждённые темы» остаются только SUBJECT_MATCH (инвариант не трогаем). LIKELY попадает: в SERP-таблицы с маркировкой «вероятно», в отдельный блок региональных саммари («материалы, вероятно относящиеся к субъекту: N»), в findings с `subjectMatch: "LIKELY"` → рендерятся в матрице отдельной секцией «Требует подтверждения» (не смешивать с verified).
- Все schema-версии артефактов, куда попадает новое значение, — bump + обратная совместимость чтения.
**Приёмка:** unit-набор на классификатор (таблица кейсов: фамилия+контекст → LIKELY; фамилия+конфликт → OTHER; и т.д.); золотой кейс: количество материалов, видимых на слайдах, растёт, KPI «О субъекте» не меняется.

### Шаг 2.2. Сигнал запроса в идентификации
**Цель:** использовать факт «выдача получена по запросу с полным именем», не превращая каждый результат в матч.
**Файлы:** `subject-resolution-classifier.ts` (+ тесты).
**Что сделать:** если `item.query` содержит фамилию+имя субъекта И текст материала содержит фамилию (surname_only сегодня) → повышать до LIKELY_SUBJECT с reasonCode `surname_with_subject_query` (не до SUBJECT_MATCH). Конфликтные сигналы (тёзки) по-прежнему сильнее. Задокументировать в комментарии методологическое обоснование.
**Приёмка:** unit: surname_only + subject-query → LIKELY; surname_only + чужой query → AMBIGUOUS; конфликт → OTHER.
**Зависимости:** 2.1.

### Шаг 2.3. Морфология без «обрезания последней буквы»
**Цель:** убрать класс ложных пропусков/срабатываний `matchesToken`.
**Файлы:** `subject-resolution-classifier.ts`.
**Что сделать:** заменить эвристику «стем −1 буква» на явную генерацию русских падежных форм для имён/фамилий (таблица окончаний -ов/-ев/-ин/-ая/-ий и т.п. — детерминированная функция, без библиотек) + word-boundary матчинг вместо substring (`\b` с учётом кириллицы через `\p{L}`). Сохранить транслит-ветку.
**Приёмка:** unit-таблица: «Петровым/Петрову/Петровой» матчится к «Петров»; «Петровский» — НЕ матчится; латинские варианты работают.

### Шаг 2.4 (опционально, за флагом). LLM-дизамбигуация AMBIGUOUS
**Статус:** реализовано (`ORION_GPT_IDENTITY`, default off). См. `docs/remediation-optional-2.4-3.3.md`.
**Цель:** дожать неоднозначные материалы с объяснимым обоснованием.
**Файлы:** новый `orion-golden/gpt/gpt-identity-resolver.ts`; вызов из `run-analytics-pipeline.ts` за флагом `ORION_GPT_IDENTITY=1`.
**Что сделать:** батчами по ~20 AMBIGUOUS-материалов: промпт с профилем субъекта (включая тёзок) → строгий JSON `{ref, decision: LIKELY|AMBIGUOUS|OTHER, reason}`; результат может только повышать до LIKELY или понижать до OTHER (никогда до SUBJECT_MATCH); reason сохраняется в артефакт и в evidence-обоснование. Fail-safe: ошибка → материалы остаются AMBIGUOUS. Использовать инфраструктуру очереди из Шага 4.2.
**Приёмка:** offline-тест с фейковым caller; проверка инварианта «не выше LIKELY».
**Зависимости:** 2.1, 4.2.

### Шаг 3.2. Catch-all тема «прочие материалы о субъекте»
**Цель:** SUBJECT_MATCH/LIKELY материал, не попавший ни в одну тему, всё равно виден в отчёте.

Региональное саммари добавляет секцию «Другие материалы о субъекте: N (примеры: …)» с evidence refs. В матрицу рисков это не попадает.
**Приёмка:** золотой кейс: нейтральные статьи о субъекте появляются в региональном саммари; unit на агрегацию.

### Шаг 3.3 (за флагом). LLM-тематизация с детерминированной верификацией
**Статус:** реализовано (`ORION_GPT_THEMES`, default off). См. `docs/remediation-optional-2.4-3.3.md`.
**Цель:** темы, которых нет в словаре, обнаруживаются моделью, но подтверждаются кодом.
**Файлы:** новый `orion-golden/gpt/gpt-theme-suggester.ts`; интеграция в `run-analytics-pipeline.ts` за `ORION_GPT_THEMES=1`.

**Приёмка:** offline-тест с фейковым caller: невалидные keywords отбрасываются; валидная тема появляется с пометкой.

### Шаг 4.4. Stage 1 → map-reduce по корпусу
**Цель:** большие кейсы не упираются в токен-лимит; анализ не теряет детали (главный запрос «генерация частями»).
**Файлы:** `gpt-case-analysis.ts` (+ новый `gpt-case-analysis-mapreduce.ts`), `canonical-report-prepare.ts`.
**Что сделать:**

- Иначе map: корпус делится на батчи по поверхностям/регионам (организика RU, организика UAE, подсказки+PAA, картинки+AI, комплаенс) → мини-анализ каждого батча тем же строгим JSON (усечённая схема: риски + факты + позитив). **Приёмка:** offline-тест с фейковым caller-ом, считающим вызовы: маленький корпус → 1 вызов; большой → K map + 1 reduce; отказ одного map не валит анализ. Схема выходного артефакта неизменна.

```
Веха G «Продукт»:               7.2 → 8.1 → 8.2 → 8.3
Гигиена (фоном, с 9.1 сразу):   9.1 → 9.2 → … → 9.3–9.5
```

После каждой вехи: прогон золотого кейса (0.3) + фиксация метрик.
