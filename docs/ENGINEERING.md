# Global Info — инженерный документ

Единственный документ проекта. До этого их было сорок: `docs/rework/*` (шестнадцать
файлов хода работ), `docs/digital-profile/*`, разборы отдельных прогонов и три
плана в корне. Они пересекались, устаревали по-разному и расходились между собой —
типичный случай, когда ответ на один вопрос лежит в трёх местах.

Ход работ и обоснования решений остались в истории git; сюда перенесено то, что
нужно, чтобы вести проект дальше.

Этот документ описывает **то, что есть**. План того, **что предстоит
изменить**, живёт в `docs/adr/NNNN-<slug>.md` — временно, пока шаг идёт, и
**из кода на него не ссылаются**: файл исчезнет, а комментарий останется. Шаг
закрыт — то, что стоит помнить дальше, переезжает сюда, план удаляется,
обоснование остаётся в истории git. Правило «один вопрос — один ответ» этим не
нарушается: действующее состояние по-прежнему описано в одном месте.

Так закрылась программа переработки 0001–0009: приёмочный контур, клиентский
текст, отказ от второй стадии Arsenkin, типографика и визуальный язык деки,
живой статус в кабинете. Всё это работает и описано ниже; планы удалены, потому
что документ, который выглядит как незакрытая задача, а описывает прошлое, хуже
отсутствующего.

## 1. Что это

Продукт готовит отчёт о цифровом профиле физического лица (due diligence):
собирает открытые источники, сверяет принадлежность материалов проверяемому лицу,
выделяет темы риска и собирает презентацию (PPTX + PDF).

Конвейер — один, называется unified:

```
BASE_COLLECTION → ARSENKIN_ENRICHMENT → COMPOSITE_MERGE → REPORT_PREPARE
                                                          → REPORT_READY | COMPLETED_PARTIAL
```

Каждый этап — строка в `dp_workflow_steps` с собственным расписанием, лизой и
бюджетом. Ни одна фаза не держится на таймере в памяти процесса: деплой посреди
сбора ничего не теряет.

### Правила, которые нельзя нарушать

Это не стиль, а требования к продукту — отчёт показывают банку.

- **LLM не источник правды.** Модель переписывает и связывает то, что уже
  собрано, и не добавляет фактов. Любое утверждение в отчёте прослеживается до
  наблюдения с URL и доменом.
- **Подмена реальных данных синтетикой запрещена.** Ни mock-агенты на реальном
  кейсе, ни «правдоподобные» совпадения по санкционным спискам.
- **Только законные API.** Никакого обхода блокировок и скрейпинга вопреки
  условиям сервиса.
- **Пустое состояние честнее выдуманного.** Если источник не дал данных, слайд
  говорит об этом словами и называет причину.
- **Совпадение по комплаенсу не подтверждается автоматически.** Оно попадает
  аналитику как `PENDING`.

## 2. Локальная разработка

Один compose-файл поднимает всё: Postgres, рендерер, приложение и воркер.

```bash
cp .env.example .env        # заполнить секреты
docker compose up -d --build
docker compose logs -f app
```

| Что | Где |
|---|---|
| Приложение | http://localhost:3000/admin/digital-profile |
| Рендерер | http://localhost:8080/health |
| Postgres | localhost:5432 |
| Артефакты прогонов | `./storage/digital-profile/` |

`.env` читается при **создании** контейнера. После правки — `docker compose up -d
--force-recreate app worker`, иначе значения останутся прежними, а провайдеры
начнут отвечать 401.

### Проверки

```bash
npm run typecheck     # tsc --noEmit, включая scripts/
npm test              # vitest, ~1400 тестов
npm run ci:smokes     # офлайн-смоки: сборка деки, качество, контракт текста
npm run build         # next build
npm run ci            # всё перечисленное разом
npm run ci:full       # то же плюс смоки, которым нужны Python-пакеты и база
```

`ci` обязан проходить на чистой машине: **без сети, без базы, без рендерера**.
Ни один смок офлайн-контура не делает сетевого вызова и не открывает соединение
с Postgres — это их условие, а не побочное свойство. `ci:full` добавляет то, для
чего нужны поднятые зависимости.

Смоки запускает `scripts/run-smokes.ts`, а не цепочка `&&`. Разница в трёх
вещах, и каждая появилась после того, как гейт соврал:

- выполняются **все** смоки, а не до первого падения — иначе об остальных
  узнаёшь по одному за прогон;
- **отменённый** подтест и прогон **без единой выполненной проверки** считаются
  провалом: нулевой код возврата сам по себе ничего не доказывает;
- пропуски сводятся в один список в конце. Пропуск объявляется строкой
  `# SKIP <что и почему>`; невидимый пропуск ничем не отличается от
  невыполненной проверки.

Правила исхода закреплены тестом (`tests/unit/smoke-runner.test.ts`): раннер сам
стал контуром, и его ошибка покрасила бы в зелёный весь проект.

### Эталоны золотого кейса

`fixtures/golden-case/` хранит два эталона, и они отвечают на разные вопросы:

| Файл | Следит за |
|---|---|
| `baseline.json` | счётчики наблюдений и метрики качества |
| `client-text.baseline.json` | формулировки, которые видит клиент |

Числовой эталон переживает полную переписку текста незамеченным — поэтому
текстовый заведён отдельно. Обе сверки идут в `npm run smoke:golden-case`, и обе
проверяются на детерминизм: два прогона обязаны дать одни и те же слова.

Снимок текста берётся с payload рендерера, и **имена полей у него — имена
payload, а не контракта слайда**. Дважды это стоило эталону целого носителя
текста: `highlightExplanations` лежат у payload внутри `visualAnalysis`, а не на
верхнем уровне (фразы «Почему выделено» не были закреплены ни одним словом), и
плитки дашборда лежат полем `metrics` — `kpis` контракта переименовывает
`run-deck-build.ts` до снятия снимка (в эталон не попадала ни одна плитка из 52
слайдов, хотя обзор печатает семь). Общее правило: новое поле снимка сверяется с
`toRendererPayload`, а не с `SlideContentContract`, и проверяется тем, что после
починки в эталоне появляются строки.

Намеренное изменение формулировок закрепляется явно:

```bash
NETWORK_CALLS=0 npx tsx scripts/run-golden-case-report.ts --update-baseline
```

Перед подготовкой золотой кейс сеет детерминированные превью в
`image-preview-cache` своего прогона: первой RU-сетке и сетке ОАЭ — целиком,
второй RU-сетке — четыре адреса из шести, третьей — ни одного. Так офлайн-контур
держит все три ветки отрисовки: полную страницу, частичную (четыре плитки и
строка о двух без превью — форма живого дефекта) и честную деградацию в текст с
причиной. Кэш не сеть, поэтому посев работает и при `NETWORK_CALLS=0`.

Отдельно от золотого кейса живёт эталон сборки деки — `baselines/report-72/`. После
любой его пересборки (`npx tsx scripts/run-orion-deck-sections-report72.ts`) фикстуру
визуальных ассетов надо пересобрать следом:

```bash
npm run fixture:deck-assets:rebuild
```

Иначе краснеет её тест-детектор `tests/unit/deck-asset-fixture-recovery.test.ts`: он
сверяет комитнутую фикстуру с построенной из свежих пакетов секций.

Реплей детерминирован, но не побайтово с первого прогона. Два прогона подряд дают
одинаковые пакеты секций, `assembled-deck.json`, `render-payload.json` и отчёты приёмки;
расходятся ровно три артефакта и только полем `generatedAt` — `report-deck-manifest.json`,
`report-section-manifest.json`, `deck-coverage-reconciliation.json`. Прогон, который пакеты
**регенерирует**, пишет их в порядке ключей построителя, а следующий — в порядке схемы
(пакеты читаются через `SectionPackV2Schema.safeParse`); содержимое одно и то же, и со
второго прогона файлы неподвижны. В коммит уходит эта, «кэшированная», форма.

## 3. Архитектура

```
src/app/                     маршруты и страницы Next (App Router)
src/modules/digital-profile/
  ├── providers/             внешние источники (Yandex, Serper, Arsenkin, Wikipedia, OpenSanctions)
  ├── services/              оркестрация сбора, подготовка отчёта, восстановление
  ├── workflow/              шаги как единица работы: реестр, воркер, лизы
  ├── orion-golden/          аналитика и сборка деки (секции, шаблоны, GPT-слой)
  ├── client/                админ-интерфейс
  └── storage/               приватное хранилище артефактов
renderer/                    рендерер на Python (FastAPI + python-pptx + LibreOffice)
prisma/                      схема и миграции
scripts/                     рабочие скрипты: воркер, вход в контейнер, смоки
tests/                       vitest
baselines/report-72/         золотой эталон сборки деки
```

### Кто что двигает

**Веб-процесс** создаёт прогон и отдаёт статус. Работу он не исполняет.

**Воркер** забирает готовые шаги (`FOR UPDATE SKIP LOCKED` с лизой) и исполняет
их. Он же подбирает после деплоя то, что осталось от прошлого процесса
(`workflow/deploy-resume.ts`). Масштабируется горизонтально: два экземпляра один
шаг не возьмут.

**Рендерер** превращает манифест деки в PPTX и PDF. Секретов не знает и наружу не
ходит.

### Ограничение, из-за которого воркер пока живёт внутри приложения

Артефакты лежат на диске, а том Railway монтируется к одному сервису. Пока это
так, отдельный сервис-воркер не сможет отдать собранный отчёт. Поэтому воркер
поднимается отдельным процессом внутри контейнера приложения — это поведение по
умолчанию, переменная для него не нужна. Расписание всё равно в БД, так что
деплой посреди сбора работу не теряет.

Когда артефакты переедут в общее хранилище (S3-совместимое), воркер станет
отдельным сервисом — конфиг для него уже есть (`railway.worker.json`).

## 4. Деплой на Railway

Два сервиса в одном проекте: **app** и **renderer**. Третий (**worker**) —
только после переезда артефактов в общее хранилище, см. выше.

| Сервис | Dockerfile | Конфиг | Healthcheck |
|---|---|---|---|
| app | `Dockerfile` | `railway.app.json` | `/api/digital-profile/health` |
| renderer | `renderer/Dockerfile` | `railway.renderer.json` | `/health` |
| worker | `Dockerfile` | `railway.worker.json` | нет: порт не слушает |

Миграции накатывает **только app**, через `preDeployCommand: npm run db:deploy`.
Два сервиса, гоняющиеся за одну миграцию, — гарантированная гонка.

### Почему вход в контейнер именно такой

`CMD ["node", "scripts/start.mjs"]` — exec-форма, без `npm` и `npx` в цепочке.
Причина конкретная: `npm run` не передаёт сигнал детям. Замер показал, что после
SIGTERM в `npm run` внуки остаются живы. При деплое Railway просил контейнер
остановиться, PID 1 умирал, сервер Next сигнала не получал вовсе — ни дренажа
соединений, ни штатного выхода. Контейнер добивался по таймауту, и это
записывалось как **Crashed на каждом деплое**.

Теперь PID 1 — обычный Node-процесс: сам получает сигнал, передаёт детям,
дожидается их выхода и уходит с нулём.

Инвариант закреплён тестом `tests/unit/container-entrypoint.test.ts`.

## 5. Переменные окружения

**В переменных окружения живут только секреты.**

Всё остальное — включатели провайдеров, выбор источника выдачи, пределы
частоты, адреса сервисов, настройки воркера — имеет значение по умолчанию в
`config/defaults.ts`, и это значение описывает работающий продукт целиком.
Причина конкретная: включение сборщика было собрано из цепочки переменных, у
ORION их пять, и пропуск любого звена гасил агента молча — `NOT_CONFIGURED`
для агента законный исход, в логе ничего. Один раз так и вышло: ключ
`SERPER_API_KEY` стоял, а `GOOGLE_EXTERNAL_SERP_PROVIDER` не был задан.

Включённые по умолчанию провайдеры ничего не открывают сами по себе:
**разрешением служит ключ, а не флаг**. Без ключа провайдер отдаёт
`NOT_CONFIGURED` с названной причиной и в сеть не ходит — то есть значение по
умолчанию не может ни потратить денег, ни включить источник втихаря.

### Обязательные

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Postgres. На Railway — ссылка на переменную сервиса базы |
| `DIGITAL_PROFILE_SIGNED_URL_SECRET` | подпись ссылок на скачивание, случайная строка ≥ 32 знаков |
| `DIGITAL_PROFILE_SESSION_SECRET` | сессии админки, своя случайная строка |

`PORT` назначает Railway; в коде его не хардкодить.

### Ключи источников

Каждый включает свой источник. Отсутствующий ключ — не ошибка: отчёт соберётся
без этой поверхности и назовёт, чего в нём нет.

| Переменная | Что даёт |
|---|---|
| `ARSENKIN_API_TOKEN` | подсказки, PAA, AI-выдача, позиции, аудит URL |
| `SERPER_API_KEY` | выдача Google и поверхности ORION (псевдоним `GOOGLE_EXTERNAL_SERP_API_KEY`) |
| `YANDEX_SEARCH_API_KEY`, `YANDEX_SEARCH_FOLDER_ID` | Yandex Cloud Search API v2: органика **и** нейро-ответ (`/v2/gen/search`) — своих переменных у нейро-ответа нет |
| `OPENAI_API_KEY` | слой текста отчёта |
| `OPEN_SANCTIONS_API_KEY` | санкционные и PEP-наборы |

### Что решает код, а не окружение

| Настройка | Значение | Почему так |
|---|---|---|
| источник выдачи Google | `serper` | единственный реализованный в этой сборке |
| стратегия Google | `external_serp` | прежний `disabled` не работал даже при живом ключе |
| все реальные коннекторы | включены | ключ и есть разрешение |
| Arsenkin | включён | разрешение — токен |
| AI-аналитик | включён | без него текст вырождается в шаблон |
| демо-агенты | выключены | на реальном кейсе недопустимы |
| вход в админку | обязателен | незакрытая админка — открытый доступ к делам клиентов |
| хранилище прогонов | база | файловый режим не виден второму процессу |
| воркер внутри контейнера | да | том Railway монтируется к одному сервису |
| адрес рендерера | внутреннее имя на Railway | зависит от площадки, а не от секрета |
| путь тома | `/data/digital-profile` на Railway | то же самое |
| Arsenkin: 4 обращения, 24 запроса в минуту | | предел аккаунта — 5 задач и 30 запросов на **все** вызовы вместе; один слот оставлен про запас |

Отключить источник по-прежнему можно — значения по умолчанию не запрет, а
разумная отправная точка. Полный список переопределений — в `.env.example`.

### Проверка на старте

Контейнер печатает готовность каждого сборщика и, если тот выключен, называет
недостающую переменную:

```
[digital-profile][env] ГОТОВ   Arsenkin (5 агентов обогащения) — готов
[digital-profile][env] ВЫКЛ    AI-аналитик (текст отчёта) — нет OPENAI_API_KEY
```

Правило собрано в `describeCapabilityReadiness` и закреплено тестом
`capability-readiness-names-missing-var.test.ts`, который проверяет главное:
**выключить сборщик может только отсутствующий секрет**. Значения переменных в
лог не попадают — только имена.

### Рендерер

Кроме `DATA_ROOT` и `PORT` ему ничего не нужно. Секретов у него нет и быть не
должно — наружу он не ходит.

## 6. CI

`.github/workflows/ci.yml`, на каждый push и pull request:

1. типы (`tsc --noEmit`);
2. тесты (`vitest`);
3. офлайн-смоки (`ci:smokes`);
4. **сборка приложения** (`next build`);
5. **сборка обоих образов** тем же Dockerfile, которым собирает Railway.

Пункты 4 и 5 добавлены не для полноты: прежний CI их не делал, и он мог быть
зелёным, когда деплой уже не собирался. Образы никуда не публикуются — цель
узнать о поломке здесь, а не в Railway.

Линтера пока нет: ESLint в проекте не был установлен вовсе, а `next lint`
сваливался в интерактивную настройку. Ставить его имеет смысл на очищенном коде.

### Офлайн-контур и Python

Обещание «проходит на чистой машине без рендерера» держится тем, что **ни один
смок уровня `offline` не падает из-за отсутствия Python**: интерпретатор ищется
не бросающим `findPythonInterpreter()` (`scripts/lib/python.ts` — один ответ на
весь репозиторий), а проверка, которой он нужен, объявляет пропуск строкой
`# SKIP <имя теста> — <причина>`.

Имя теста в объявлении обязательно: раннер по нему вытесняет штатный TAP-маркер
node, иначе одна невыполненная проверка считается дважды.

Проверено прогоном под `PATH` без Python: восемь смоков, ноль провалов, три
названных пропуска (сверка реализаций контракта, число страниц PPTX/PDF/PNG,
импорты пакета рендерера). До правки два смока падали и роняли контур целиком —
и это было состояние `HEAD`, а не чьего-то шага.

Проверка формы закреплена `tests/unit/offline-smokes-do-not-require-python.test.ts`:
список смоков она берёт из `run-smokes.ts` (копия рядом разошлась бы), а в
исходниках ищет бросающий вариант и зашитое имя интерпретатора — комментарии при
этом снимаются, проверка смотрит на вызовы, а не на прозу.

### Накат с нуля на Railway

Мы не в продакшене, поэтому проще снести базу целиком, чем догонять её
миграциями. Схема пересоздаётся из единственной миграции.

```bash
# 1. Схема сносится целиком. Данные при этом теряются — это и есть цель.
railway run --service <postgres> psql "$DATABASE_URL" -c \
  'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'

# 2. Деплой сам накатит миграцию (preDeployCommand: npm run db:deploy)
railway up --service <app>

# 3. Убедиться, что таблиц ровно столько, сколько описано схемой
DATABASE_URL=<railway-url> npm run db:audit

# 4. Завести администратора заново
railway run --service <app> npm run admin:create
```

Команда из шага 1 намеренно не завёрнута в npm-скрипт: снос базы должен быть
осознанным действием, а не одним словом в консоли.

### Проверка на мёртвые таблицы

`prisma migrate status` смотрит на список применённых миграций, а не на то, что
в базе лежит на самом деле, поэтому таблицы от прошлых итераций им не видны.

```bash
npm run db:audit                       # текущая база
DATABASE_URL=<railway-url> npm run db:audit
```

Сверка только читает. Она называет таблицы, которых в схеме нет, вместе с числом
строк в каждой — видно, пустая она или с данными.

### Накат схемы с нуля

Все миграции схлопнуты в одну (`20260625104420_init`): двадцать шесть шагов
описывали путь, который больше никому не нужно проходить, а мешали они дважды —
на чтении и при попытке понять, что в базе должно быть.

Схлопывание проверено посимвольно: схема из одной миграции и схема из прежних
двадцати шести совпадают полностью — 429 колонок, 109 индексов, 69 ограничений.

**Пустая база** (новое окружение, сброшенная Railway-база):

```bash
npm run db:deploy      # применит единственную миграцию
npm run db:audit       # убедиться, что расхождений нет
```

**База, где прежние миграции уже применены.** Разбирается само: `npm run
db:deploy` — это не `prisma migrate deploy`, а `scripts/db-deploy.ts`, который
сначала смотрит на состояние базы.

`prisma migrate deploy` умеет ровно один случай: в базе применено то же, что
лежит в `prisma/migrations`. После схлопывания истории он на существующей базе
видит незнакомую начальную миграцию, пытается её применить и падает
(`P3018 ... type "CaseStatus" already exists`), а неудачная попытка
**записывается** в `_prisma_migrations` и блокирует все следующие деплои. На
Railway это pre-deploy — руками туда не вмешаться, и деплой встаёт совсем.

Скрипт разбирает три состояния:

| Состояние базы | Что делает |
|---|---|
| пустая | обычный `migrate deploy` |
| схема есть, записи о начальной миграции нет | отмечает её применённой, затем `deploy` |
| записана неудачная попытка | снимает её, дальше как строкой выше |

Отметить базу применённой он может, только если её схема **действительно**
совпадает с ожидаемой. Не совпало — останавливается и называет, каких таблиц не
хватает: иначе это спрятало бы настоящее расхождение.

**Если сверка нашла мёртвые таблицы.** Удалять их надо миграцией, а не руками:
тогда изменение повторится на всех окружениях и останется в истории.

```bash
npx prisma migrate dev --name drop_dead_tables    # dev; правим SQL руками
```

`prisma migrate reset` **удаляет данные** — на проде им пользоваться нельзя.
Только: снять дамп → `db:deploy` → удалить лишнее отдельной миграцией.

## 8. Решения, которые стоит помнить

Это не история, а грабли: каждое из них уже стоило прогона или деплоя.

**Один вопрос — один ответ.** Почти все дефекты этого проекта были одной формы:
на один вопрос отвечали в двух-трёх местах, и ответы расходились. Стадия прогона,
покрытие слотов деки, прогресс обогащения, ёмкость страницы — каждый раз лечилось
не согласованием ответов, а устранением лишних.

**Ожидание — не попытка.** У шага два разных бюджета: `maxAttempts` ограничивает
отказы, `maxWaitMs` — ожидание. Пока это была одна величина, здоровый прогон
умирал на сороковом опросе живого провайдера.

**Область видимости — цепочка вызовов, а не процесс.** Авторизация платных
вызовов Arsenkin жила в переменной модуля и делала процесс однопоточным: пока один
агент отправлял задачи, поллер другого получал отказ. Теперь `AsyncLocalStorage`.

**Тихая потеря содержимого хуже пустоты.** Рендерер молча выбрасывал блоки, не
влезшие на страницу: до клиента доходила одна тема риска из четырёх. Теперь
выброшенное поднимает `CONTENT_DROPPED_BY_RENDERER` уровня CRITICAL — и на пути
карточек, и на пути буллетов: `ctx.bullets` пишет телеметрию не только о блоке,
выброшенном по высоте, но и о том, который опустел после ножниц или потерял
хвост (там код `text-clipping`, тоже CRITICAL).

**Сколько влезает на лист, отвечает рендерер — и отвечает до выпуска.** Ёмкость
страницы предсказывали числа реестра (`maxBulletLinesPerSlide`,
`charsPerRenderedLine: 85`), а расходовал её код отрисовки по высоте: на живом
прогоне 19.08 расхождение стоило шести страниц содержимого, причём на стр. 11
промах был 0,37 % — это предел жанра, а не недокалиброванность (калибровка уже
выполнялась дважды). Теперь построитель меру не пересказывает, а спрашивает:
собранная дека → пейлоад → **мерный прогон** (`POST /orion/measure-layout`, тот
же `_render_slide`, рисование в память, ни файлов, ни экспорта, под тем же
`_GOLDEN_RENDER_LOCK`) → перекладка блоков по измеренным высотам → пересборка,
до чистой меры. Потолок — 4 меры, и **пересборок не бывает больше, чем мер**:
сборка, которую померить уже нечем, — выброшенная работа и приговор тому, чего
никто не смотрел. Пересборка идёт на готовых паках и не стоит ни одного вызова
модели. Не сошлось — прогон останавливается тем же
`CONTENT_DROPPED_BY_RENDERER`: остановленный прогон честнее урезанного отчёта.
Прежние ворота телеметрии не ослаблены ни на йоту — они стали страховкой
инварианта, а не местом смерти прогона.

Что из этого устройства держится на решениях, а не на удобстве:

- **пагинация остаётся в построителе, дека — документ записи.** «Рендерер сам
  переносит на новый лист» отвергнуто: тогда число и состав страниц рождались бы
  при отрисовке, и всё, что закреплено на деке — байтовый штамп приёмки,
  `assembledDeckHashOf`, ворота текста и доменов по страницам, `pageParity`,
  телеметрия по номерам, колонтитулы, — получило бы второго автора. Сегодня
  расходится предсказание ёмкости; стало бы расходиться само содержание;
- **«общая мера в общем месте» отвергнута** по той же причине, по какой удалена
  счётная модель строк: у «сколько влезает» два слагаемых — высота блока
  (перенос глифов Inter, кегль и жирность по строкам, отбивки) и остаток листа
  (высота обвязки, которую производит код рисования). Общее место обязано
  содержать перенос и макет обвязки, то есть вторую реализацию рендерера на
  другом языке либо замороженную таблицу его ответов;
- **счётные капы реестра остались сидом, а не ёмкостью** (`maxBulletsPerSlide`,
  `maxBulletsPerContinuation`): они нужны первой итерации и офлайн-сборкам, где
  рендерера нет и ничего не публикуется (голден-кейс, юниты). Чинить ими потерю
  содержимого бесполезно — числом на вопрос о высоте уже отвечали;
- **перекладка складывает высоты, а не выводит их.** Сумма отдельных высот
  заведомо не меньше высоты того же набора одним куском (постоянная добавка
  входит в каждое слагаемое), поэтому укладка ошибается только в сторону
  «страница чуть свободнее». Блоки едут **только вперёд**; ёмкость ещё не
  существующего листа — допущение, которое проверит следующая итерация;
- **план цикла копится, а не заменяется.** `runDeckBuild` каждую итерацию
  выводит раскладку из паков заново (паки хранят сид) и применяет только
  переданное. Цепочка, уже развезённая и ставшая чистой, в новый план не
  попадает — без накопления она откатывалась бы к сиду и гоняла цикл по кругу;
- **новый лист клонирует последнее продолжение цепочки, а не её основу.** У
  основы бывает свой шаблон и свой визуал (страница «почему выделено»: основа
  рисует снимок выдачи, продолжения — только фразы). Клон основы получил бы её
  визуал, а страница с визуалом в пейлоаде списка не несёт вовсе — положенный на
  неё текст исчез бы **до** рендерера, мимо телеметрии и мимо меры;
- **несобравшаяся дека до меры не доезжает.** Отказ обязательной секции
  останавливает сборку, и дека выходит пустой — ноль слайдов, `pageCount: 0`;
  рендерер на таком манифесте законно отвечает 500 «finalSlides is empty», и
  наружу уезжает **его** отказ вместо кода сборки и имени секции. На живом
  прогоне 20.08 оператор прочитал именно 500, четвёртое звено цепочки. Цикл
  теперь проверяет `assembly.errors` перед каждой мерой и возвращает сборку
  тому, кто её судит (`acceptAssembledDeck` → `ASSEMBLY_FAILED` с названной
  секцией; в приёмочном скрипте — «ПРИЁМКА НЕ ПРОЙДЕНА: дека не собралась»).
  Второго ответа о годности сборки при этом не заводится: цикл только не
  подменяет приговор своим. Признак покрывает все восемь источников
  `assembly.errors` — отказ обязательной секции, отсутствующий/чужой/устаревший
  пак, провал секционной проверки, осиротевшее продолжение и дубль
  `slideId`/`baseSlotId`: каждый из них отдаёт пустой манифест. Разбор цикла
  (`bullet-fit-report.json`) на этом пути так и говорит:
  `outcome: NOT_MEASURED_ASSEMBLY_FAILED`. Исход — **один** признак словом, а не
  пара булевых: `measured`/`converged` по умолчанию утверждали «мера выполнялась
  и сошлась» там, где рендерера не звали ни разу, — и врали ровно в том файле,
  куда лезут разбираться, когда всё сломалось. «Меры не было» (`NOT_MEASURED_*`,
  с названной причиной: нет адаптера — офлайн-сборка, нет слайдов — дека не
  собралась) не значит «мера провалилась»: её отказ громкий и приезжает кодом
  `RENDER_FAILED`;
- **отказ меры — громкий и возобновляемый** (`RENDER_FAILED`), а не пропуск
  цикла: иначе исход сборки зависел бы от здоровья рендерера невидимо.
  Оборачивается ровно вызов адаптера: обернув сборку целиком, под тем же
  диагнозом получили бы и падение модели, и крик перекладки о потерянном
  содержимом. Мера ждёт `/health` и повторяет запрос один раз — она первый
  контакт прогона с рендерером, и холодный старт сервиса не должен ронять
  подготовку. Ответ разбирается по объявленной версии
  (`orion-bullet-measure-v1`): ответ 200 с чужим телом — названный отказ, а не
  `TypeError` в арифметике;
- **`ctx.bullets` слышен до конца.** Потеря считается одним вычитанием «подано
  минус нарисовано»: пока слагаемых было три, элементы сверх `max_items`
  исчезали, не попадая ни в одно из них. Срезы `slice(0, 2)` (маппинг дашборда)
  и `findings[:2]` (сам дашборд) удалены — они были вторым и третьим ответом на
  вопрос о ёмкости и резали **до** рендерера, мимо телеметрии;
- **дека прежней версии построителя не рендерится повторно.** Манифест деки
  несёт `contentVersion`; загрузчик реюза сверяет его и отказывает
  `stale-content-version`, в том числе при отсутствии поля — все деки, собранные
  до этого шага, поля не несут и содержат ровно то, что новая версия чинила.
  Кнопка «Повторить рендер» после подъёма версии ведёт в слышимую пересборку
  (`render-resume-reassembly:stale-content-version`), и это цена честности кэша:
  любая старая дека платит стадии GPT заново.

Поправка к разделу о телеметрии, чтобы «зелёные ворота» не читались как «весь
текст доезжает»: потери **пути буллетов** после этого шага возможны только при
несходимости цикла, и тогда прогон остановлен. У `ctx.body` (нарратив) и у
хвостов боковой панели ножницы свои, и они по-прежнему молчат — это отдельные
пункты бэклога, а не свойство закрытого механизма.

**Карточка меряется тем, чем рисуется.** Высота строки — из метрик шрифта
(`font_line_step_emu`: натуральная строка начертания × выставленный межстрочный).
«1,12» у карточки матрицы — множитель к натуральной строке, а не к кеглю: для
11 pt Inter это ~190 500 EMU, замерено по растру эталона и закреплено смоком с
допуском. Стиль строки при замере берётся тем же `_card_line_style`, что при
выводе (мета-строка рисуется кеглем подписи, а мерилась кеглем тела), запас один
и именованный. Общие **умолчания** `measure_text_height` при этом не трогаются: у
неё десятки потребителей на всех шаблонах, и её ×1,18 остаётся консервативным
запасом остальных путей.

**Но одна правка того же шага глобальна, и это надо знать.** `_wrapped_line_count`
раньше считал неразрывный токен любой длины одной строкой; теперь он ломает токен
шире рамки по знакам. Функция сидит **под** `measure_text_height`, то есть под
таблицами, буллетами, боковыми карточками, Википедией и комплаенсом — счёт
переноса изменился у всех, а не только у матрицы. Замер по 907 строкам деки: при
полной полосе (`CONTENT_W`) расхождений нет вовсе, при карточной — одно, и лишь на
узких рамках счёт заметно растёт (при 1 000 000 EMU расходятся ~350 строк). На
эталоне 72 это подтверждено пофигурно: изменились ровно страницы 6 и 7, остальные
47 не двинулись ни на EMU. **Но это свойство корпуса, а не гарантия:** в узком
контейнере выросшая мера понижает кегль (`content_card`) или снимает буллет
(`ctx.bullets`) — первый молча, второй как потерю. Направление правки верное —
прежний счёт занижал, — но соседние пути ей затронуты, и утверждать обратное
нельзя.

Отсюда два правила, каждое куплено потерей на живом прогоне:

- **ёмкость страницы в реестре выводится из худшей легальной карточки**, какую
  способен выпустить построитель, а не из типичной. Для матрицы это 3: худшая
  карточка (заголовок 72 знака, «в чём проблема» 160 и «Что делать» на остатке —
  по две строки каждая) стоит 1 307 808 EMU при 4 925 200 под сеткой, типичная —
  906 117, и посчитанная по типичной ёмкость 4 дважды теряла карточки. Плата:
  лишняя страница матрицы начиная с четырёх тем (четыре темы при ёмкости 4
  лежали на одном листе, при трёх правило хвоста делит их на 2 + 2);
- **рендерер карточку не ужимает молча**: она либо влезает целиком, либо не
  рисуется и посчитана в `droppedBullets`. Предрисовочные «умные ножницы» внутри
  карточки убраны сознательно — они выбрасывали мета-строки и снимали строки с
  конца молча, и на живом прогоне съели «Что делать». Тесно карточке всё-таки
  бывает, и каждый оставшийся рез слышен: бюджет знаков рендерера
  (`_clip_structured_bullet`, 900 — в него упирается не живой пак, а
  замороженный или чужой) и страховка `_fit_lines_to_height` пишут снятое в
  `droppedLines`, а понижение кегля до подписи содержимого не теряет и потому
  записано клипом, а не потерей. Считается при этом **рез**, а не уборка: тело
  без обрубков модели и без повисшего двоеточия — это то, что обязано доехать,
  и разница с ним, а не с сырым текстом, есть потеря. Мера у страховки — от
  вызывающего: одна мера, одно решение «что влезло».

Поправка к ожиданиям, чтобы её не переоткрыли: «пять-шесть карточек на листе»
верно только для двухстрочных сводных карточек; карточка с «Что делать» стоит
1,3 МEMU, и честная гарантированная ёмкость — три.

**Сетка изображений рисует только полученные превью; счёт и `visibleItems` — по
нарисованному.** Плитка-заглушка «Превью недоступно: источник не отдал
изображение» удалена решением владельца (18.08.2026): на живом прогоне в PDF
было 30 плиток при 16 полученных превью — не меньше четырнадцати серых, — а
каждая страница при этом говорила «Показано 6». Лечится это данными, а не
подписью: `buildGrid` кладёт в `visibleItems` ровно те строки, что попали в PNG,
а `previewBase64` у элемента сетки обязателен — вернуть заглушку можно теперь
только ошибкой компиляции. Если превью нет ни у одной строки набора, ассет не
создаётся вовсе: слот получает мету без картинки, страница уходит в текстовую
ветку, а сама потеря попадает в `failed` — оператор видит её в
`report-quality-summary`, а не только в консоли.

Оговорка, без которой правило читается неверно: **потолок в шесть плиток на
странице изображений жив** (`GRID_TILE_CAPACITY` в `fragment-builders/images.ts`)
и ограничивает и число показанного, и число выделенного. Продукту он уже не
нужен — `visibleItems` там ровно нарисованное, — но замороженная фикстура
эталона 72 старше починки: в её мете лежат все строки набора (у слота ОАЭ — 42
на шесть плиток), и без потолка приёмочная дека напечатала бы «42». Снимать его
можно только вместе с пересборкой `baselines/report-72/artifacts/report-assets`.

Не показанное называется словами — счётом, причиной и доменами, — причём
`offline` значит «превью в этом прогоне не запрашивались», а не «источник не
отдал»; отдельные причины есть и у исчерпанного бюджета выборки, и у непригодного
адреса, потому что «мы не спрашивали» и «площадка отказала» — разные новости для
банка. Негативная строка без превью названа отдельно **и посчитана**: заголовок
страницы и её статус считают весь негатив, а не только выделенный рамкой, —
компромат-площадки чаще прочих отвечают отказом на запрос картинки, и «негативных
источников нет» над строкой о компромате было бы худшей из ошибок отчёта. Фраза о
негативе стоит **перед** перечислением источников: строка сайдбара режется по
границе предложения с конца, и платить за длину нужно доменами, а не сигналом.

Домены не показанных строк берутся из индекса доказательств самой страницы, а
ссылки на них остаются в `evidenceRefs` слайда: домен в клиентском тексте, не
выводимый из доказательств своей страницы, — отказ обязательной секции
(`sidebar domain not derived from page evidence`), то есть пустая дека. Строка,
которой в индексе страницы нет, не печатается вовсе: сослаться на неё нечем.

**Кэш превью — не сеть.** Он читается и при `NETWORK_CALLS=0`, и при явно
запрещённой сети (`allowImagePreviewNetwork: false`); сетевой запрет живёт внутри
самой выборки — отказом `offline` на некэшированный адрес. **Право вето — у
окружения, а не у вызывающего:** `NETWORK_CALLS=0` не перебивается никаким
`allowNetwork: true`, иначе смок с самым естественным прочтением имени начнёт
ходить в сеть под `npm run ci` и сломает условие офлайн-контура. Это и было
однажды сломано: `opts?.allowNetwork ?? (env)` отдавал решение вызывающему. Поэтому пересборка
оплаченного прогона получает свои купленные превью из `image-preview-cache`
каталога прогона: ровно для этого кэш и заведён.

**Потери рендерера слышны и на живом пути.** Телеметрия разметки — часть
контракта `/orion/render-golden`: эндпоинт отдаёт её полем `layoutTelemetry`,
`renderDeckViaHttp` пишет её в `render/layout-telemetry.json`, и после успешного
рендера подготовка отчёта судит файл. Правило ворот
(`services/render-telemetry-gate.ts`):

- потеря целых блоков — блокер `CONTENT_DROPPED_BY_RENDERER`: чекпоинт рендера
  `FAILED`, отчёт клиенту не выдаётся. Рендер бесплатен и детерминирован, после
  починки ёмкости пересборка дорисует;
- клип-коды — только предупреждения `renderer-clip:page=<N>:<код>` в
  `job.warnings`, **потому что** клип — это сработавшая защита (понижение кегля,
  ножницы предложений), а не потеря: содержимое при нём либо доехало, либо
  посчитано отдельно в `droppedBullets`/`droppedLines` — и тогда блокирует по
  правилу выше. Плюс к тому на всех текстовых путях, кроме карточного, мера
  по-прежнему консервативна (запас ×1,18 в `measure_text_height`), и её
  предсказание «не влезет» — не повод останавливать оплаченный прогон.
  Несработавшая мера (`TABLE_WORD_BREAK`, «обрезка не доказана») клипом не
  является и ходит под своим префиксом — `renderer-layout:page=<N>:<код>`;
- отсутствие файла, нечитаемый файл (в том числе одна битая запись) и пустой
  список записей после настоящего рендера — блокер `RENDER_TELEMETRY_MISSING`:
  сказать «потерь нет» на таком входе не может никто, а отказ разбора,
  выданный предупреждением, прячет вместе с собой настоящую потерю;
- офлайн-фейки не судятся: адаптер, назвавший себя фейком, не обязан ни класть
  клиентские файлы, ни отчитываться телеметрией. Признак один на оба требования.

При обоих кодах сбор цел и оплачен, лечится пересборкой, и запирать его в
`FAILED_TERMINAL` без выхода нельзя.

**Годность пересборки решают данные, а не имя кода отказа.**
`evaluateUnifiedReportRebuildEligibility` разделяет два вопроса. Первый — «идёт
ли работа прямо сейчас»: стадия и статус плюс `autoResumeState` по шагам
(`JOB_PROGRESSING`), тот же предикат, что и у кнопки восстановления, — пока
конвейер вернётся сам, звать оператора нельзя ни к одной из кнопок. Второй —
«мешает ли что-нибудь в данных», и на него отвечает `rebuildDataBlockerReason`:
неподведённое обогащение (`ARSENKIN_INGEST_PENDING`), наличие входов подготовки
(`REBUILD_INPUTS_MISSING`), текущность набора (`COMPOSITE_NOT_CURRENT`) и
происхождение (`REBUILD_LINEAGE_MISMATCH`).

Список `POST_COLLECTION_ERROR_CODES` был вторым ответом на второй вопрос и
удалён вместе со своим модулем: он старел молча. Прогон, вставший на воротах
рендерера и закрытый сторожем возраста (`STALE_NO_PROGRESS`), в список не
попадал — пересборка отвечала `JOB_NOT_COMPLETED`, и у оператора оставалась одна
кнопка, платный сбор заново.

Два случая, где данные возражают, стоят денег и потому названы отдельно.
`COMPOSITE_NOT_CURRENT`: восстановление подводки Arsenkin снимает
`compositeDatasetId` намеренно — файлы прошлого слияния остаются на диске, но
годными быть перестают. `ARSENKIN_INGEST_PENDING`: точечный платный повтор
ставит задачу и `compositeDatasetId` **не** снимает, так что по файлам прогон
неотличим от готового к пересборке — а нажатие сняло бы чекпоинт подводки и
бросило оплаченные наблюдения. Признак здесь именно `enrichmentComplete`, а не
чекпоинт `ARSENKIN_RESULT_INGEST`: последний ставит любой упавший тик, в том
числе на подготовке, где пересборка как раз и есть верное действие.

**Сторож возраста не выдаёт себя за первопричину.** Прогон, не двигавшийся шесть
часов, закрывается терминально, но `lastErrorCode` при этом сохраняет прежний код
отказа, а сам факт возрастного останова уходит в `warnings`
(`STALE_NO_PROGRESS`, успешную подготовку эта отметка не переживает). Код нужен
целым, потому что по нему решают подписи кнопок в кабинете и — у прогонов без
конвейера — прежняя эвристика восстановления. Совет в `lastError` спрашивает тот
же `rebuildDataBlockerReason`, что и кнопка: обещать пересборку там, где кнопки
не будет, нельзя.

**Всякий перезапуск работы обнуляет `startedAt`.** Сторож меряет возраст именно
от этой отметки, а «Пересобрать отчёт» и «Возобновить» нажимают как раз на
прогоне, который простоял ночь: без обнуления первый же тик закрывал бы работу,
не начав её, — и, поскольку восстановление код отказа обнуляет, первопричина
терялась бы целиком. `createdAt` при этом остаётся историей прогона, а
`restoreStateAfterFailedRebuild` возвращает прежний `startedAt` вместе со
стадией: неудавшаяся пересборка не должна дарить прогону лишние шесть часов.

Выход из обоих кодов — `RENDER_RESUME`: возобновление с чекпоинта RENDER, без
повторного сбора. У прогона с конвейером так отвечает шаг
`REPORT_PREPARE` (`planResumeFromSteps`) — по имени шага, на `lastErrorCode` он не
смотрит вовсе. У прогонов без конвейера отвечает
`unified-recovery-legacy-heuristic.ts`, и там **два разных предиката, которые нельзя
сводить в один**: за кнопку отвечает узкий `offersRenderResume` (ровно `RENDER_FAILED`,
`CONTENT_DROPPED_BY_RENDERER`, `RENDER_TELEMETRY_MISSING`) — кнопка положена лишь
тем отказам, которые рендером и лечатся, иначе она приглашает к работе, которая
помочь не может;
а широкий `isRenderFailure` (плюс чекпоинт `RENDER`, плюс `/render failed/i` по
свободному тексту) остался управлять исключением из `needsArsenkinIngest` и веткой
`FAILED_RETRYABLE`. Оба кода добавлены в узкий предикат.

**Повторный рендер дешевле пересборки: 0 сборок, 0 вызовов GPT, 1 рендер.**
`resumeFrom: "render"` переиспользует собранную деку, и полный блок сборки —
вместе с аналитикой и обеими стадиями GPT — не выполняется вовсе. Работает это
потому, что **идентификатор набора один**: `composite-<unifiedJobId>`,
отчеканенный один раз в `mergeCompositeSerp`. Аналитика получает его обязательным
параметром (`AnalyticsPipelineInput.datasetId`) и наследует во все свои артефакты
и в деку; своего не чеканит. Второй ответ (`composite-<caseId>-<хэш наблюдений>`
из `composite-dataset-builder.ts`) удалён — из-за него реюз отбивался всегда, и
«повторный рендер» платил ровно столько же, сколько «Пересобрать отчёт».
Содержательный отпечаток набора при этом не потерян: он живёт отдельным полем
`sourceHashes` — это данные, а не идентичность, и смешение их в одной строке и
породило второй ответ. Каталоги прогонов, собранных до сведения форм, законно
несут старый идентификатор: их лечит первая же пересборка, адаптера старой формы
нет намеренно.

Фолбэк в полную сборку остаётся законным (дека бывает инвалидирована, бита,
отсутствует, негодна или от другого набора) и **слышим**:
`loadReusableAssembledDeck` возвращает годную сборку либо названную причину
отказа. Причины перечислены типом `AssembledDeckRefusal` — там же, а не по
файлам: `missing-files`, `binding-missing` (её выносит вызыватель: привязки
джобы нет, сверять не с чем), `stale-marker`, `corrupt:*`,
`stale-content-version`, `dataset-missing`, `coverage-incomplete`,
`deck-manifest-mismatch`, `not-accepted`, а также `case-mismatch` и
`dataset-mismatch` — эти две с обоими идентификаторами в строке. На пути `resumeFrom: "render"` причина уезжает в `qualityWarnings`
подготовки и оттуда в `job.warnings` строкой
`render-resume-reassembly:<причина>`, и она же кладётся в **каждую** запись
`render-checkpoint.json` этой попытки — попытка, упавшая до результата, ничего
не возвращает, и чекпоинт остаётся единственным её следом; восстановление пишет
причину туда же рядом с `NEEDS_ASSEMBLY`. Жалобы попытки описывают её, а не
прогон, поэтому успешная подготовка снимает чужие
(`PREPARE_ATTEMPT_WARNING_STARTS` + `warningsSurvivingSuccessfulPrepare`;
префиксный список `mergeJobWarnings` этих токенов не знает и сам их не заменит).
`forceGptCopy` внутри полной сборки остаётся безусловным — намеренно: кэш
стадии 2 иначе оживал бы после живой пересборки.

**Годность деки загрузчик измеряет, а не принимает на слово.** `runDeckBuild`
пишет деку и манифест на диск **до** того, как подготовка её судит, поэтому
забракованная воротами сборка (`ASSEMBLY_QA_FAILED`, `REQUIRED_SECTION_FAILED`,
неполное покрытие) остаётся лежать целой, с непустыми слайдами и покрытием 36 в
манифесте. Структурно её от принятой не отличить — ворота качества текста
говорят о словах на безупречных страницах, — поэтому реюз требует **штампа
приёмки** `deck/assembly-accepted.json`, который ставит тот, кто вердикт вынес
(`acceptAssembledDeck` — единственное место, где судят обе ветки сборки). Штамп
положительный намеренно: прогон, умерший между записью деки и судом,
отрицательной отметки не оставил бы, и его деку реюз принял бы несудимой.
**Ключ штампа — байтовый хэш пары `assembled-deck.json` + манифест**, тот же,
что сравнивает идемпотентный повтор рендера. Отпечатком укладки его ключить
нельзя: `assembledDeckHashOf` хеширует `slideId:pageNumber` и слов не видит, а
ворота судят как раз слова — пересборка с той же раскладкой и другим текстом
унаследовала бы приёмку предыдущей и уехала бы клиенту забракованной. Сверх
штампа загрузчик сверяет `baseSlotCoverage` манифеста с 36 и отпечаток укладки:
манифест и дека пишутся двумя записями, и урезанная дека под целым манифестом
иначе называлась бы просто «непринятой», а не тем, что с ней случилось.
Покрытие в ответе подготовки при реюзе берётся из манифеста принятой деки, а не
утверждается константой. Штамп лежит в `deck/`, а стоп-маркер той же деки — в
корне каталога прогона (`writeUnifiedArtifact` не знает о подкаталогах).

**Стоп-маркеры `*.stale.json` перестали быть write-only.** Загрузчик реюза
отказывает по маркеру `assembled-deck.json.stale.json` с `doNotReuse: true` — это
спроектированная защита от реюза деки, собранной **до** дозагрузки наблюдений;
раньше её случайно выполняло несовпадение форм идентификатора. Имя маркера
выводит писатель (`staleMarkerFileName` в `unified-downstream-invalidation.ts`),
читатель импортирует его оттуда — две копии строки развели бы стороны молча.
Маркер снимает **принятая полная пересборка**, которая на него и ответила,
прочитав наблюдения заново: резюме `gpt-copy` его не трогает (оно читает
аналитику с диска и новых наблюдений не видело), а пересборка, забракованная
воротами, — тем более: погасив маркер, она сняла бы защиту, ничем её не
заменив. Не снятый маркер (отказ `unlinkSync`) называет себя предупреждением
`deck-stale-marker-not-cleared`: молча он закрыл бы прогону дешёвый повтор
навсегда.

**Идемпотентный ранний возврат рендера недостижим на обоих путях, и это
записанное ограничение, а не баг.** Между двумя *полными* подготовками — из-за
байтового хэша сборки: в манифест деки пишется `generatedAt`, и без замороженных
часов хэши не совпадают. На пути `resumeFrom: "render"` — из-за порядка: ветка
резюме сама пишет чекпоинт `READY` до проверки, а та требует `SUCCEEDED`.
Стоит это одного локального рендера при повторе шага после падения воркера:
денег не стоит, детерминизма не ломает. Содержательный (времянезависимый) хэш —
отдельная работа.

**После забракованного рендера каталог `render/` рассинхронизирован с
опубликованным документом.** Клиентские файлы публикуются только после чистого
вердикта, а `pages-png/`, `golden-render-meta.json` и `layout-telemetry.json`
пишутся рендером сразу — и принадлежат забракованному. Наружу это не отдаётся
(скачиваемых видов ровно три), но инженер поддержки, читающий диагностический
бандл, увидит `rendered-client.*` от принятого рендера и его страницы с
телеметрией — от отвергнутого.

**Приборов по-прежнему два, и они расходятся.** Живые ворота и TS-инспектор
геометрии зовут один классификатор (`classifyLayoutTelemetryRows`), а приёмка
деки читает ту же телеметрию своим python-инспектором
(`scripts/inspect-first36-pptx-geometry.py`). Общее у них одно — блокирующее
правило потери (`CONTENT_DROPPED_BY_RENDERER`, закреплено
`tests/unit/telemetry-inspectors-agree.test.ts`). Дальше ответы разные: TS
различает клипы по имени фигуры (`text-clipping`, `TABLE_ROW_PARTIALLY_VISIBLE`,
`TABLE_STATUS_CLIPPED`) и знает `TABLE_WORD_BREAK`, python — свои коды, поэтому
токен `renderer-layout:…:TABLE_WORD_BREAK` приёмка не производит никогда.
Сведение инспекторов в один — отдельная работа; писать, что прибор один, нельзя.

Транспорт при этом ничего не выдумывает: нет поля в ответе — нет файла на диске,
а старый файл удаляется перед рендером, иначе ворота осудили бы прошлый
документ. **Конечные имена клиентских документов занимаются только после суда:**
рендер пишет `rendered-client.pending.pptx|pdf`, и подготовка переименовывает их
после чистого вердикта. Иначе забракованный документ уже лежит там, куда смотрят
`reportLinks`, и неудачная пересборка (`restoreAfterFailedRebuild` возвращает
джобу в прежнее состояние — у завершённого прогона это `REPORT_READY` с прежними
ссылками) отдаёт клиенту деку с потерянными карточками — происхождения байтов проверка скачивания не знает.

**Рендеры `/orion/render-golden` сериализованы модульным локом.** Лок
**глобальный, а не покейсовый**, потому что телеметрия — глобальный список
процесса, а синхронные эндпоинты FastAPI исполняются в пуле потоков: два
одновременных рендера перемешали бы записи, и ворота судили бы не тот документ.
Размен принят сознательно: целость доказательства дороже параллелизма. Лизы
шагов поштучные на кейс, поэтому два кейса реально доходят до `ORION_PREPARE`
одновременно, и «второй запрос ждёт, а не падает» верно ровно до тех пор, пока
ожидание плюс рендер укладываются в бюджет клиента (300 с в `postGoldenRender`).
Исчерпан бюджет — отказ громкий (`RENDER_FAILED`, стадия возобновляема с
чекпоинта RENDER), а не тихий.

**Диагностический бандл называет пропущенное поимённо.** Лимит `MAX_FILE_BYTES`
= 2 МБ остаётся: он защищает поддержку от base64-вложений в JSON
(`render-payload.json` и `report-assets.json` живого прогона — около 3 МБ, почти
целиком картинки внутри полей). Но пропуск больше не молчалив:
`bundle-manifest.json` (версия `unified-diagnostics-bundle-v2`) несёт
`skippedOversize` с путями и размерами, `skippedBinary`, `skippedFileCap` (что не
влезло под потолок `MAX_FILES`), `skippedUnreadable` (обход увидел, прочитать не
смог: исчез между обходом и чтением, права, сбой диска) и `fileCapReached` —
списки отсортированы, и каждый увиденный обходом файл либо в зипе, либо назван в
одном из них. Размер берётся из того же `statSync`, которым обход и нашёл файл:
второй замер в цикле сборки был вторым ответом на один вопрос и ещё одним
молчаливым пропуском. Молчаливый счётчик однажды уже дал неверный диагноз:
телеметрию рендерера сочли «срезанной лимитом», хотя на живом пути её не
существовало вовсе.

**Отказ одного источника не обнуляет оплаченный сбор.** Прогон доходит до
`COMPLETED_PARTIAL` и отдаёт то, что собрано, назвав, чего не хватает.

**Кнопка, скрытая в UI, ничего не гарантирует.** Каждый такой запрет закрывается
и на сервере.

**Пользователь не должен дожимать прогон руками.** Система ждёт сама и сама
повторяет. Если человеку предлагают кнопку — значит, мы чего-то не доделали.

**Состояние — это данные, а не название.** `QUEUED` у задачи Arsenkin значило
сразу «мы ещё не отправили» и «Arsenkin поставил в очередь». Стоило `/check`
один раз ответить «в очереди» — задача переставала опрашиваться навсегда, и
сразу в трёх местах: в опросе, в ожидании завершения и в выборке фонового
обхода. Прогон выглядел замершим при исправном провайдере. Признак теперь
задан данными — есть внешний идентификатор, значит есть что спрашивать, — и
двух смыслов иметь не может.

**Ширины колонок таблиц выбираются по смыслу заголовков, а не по длине строки.**
Единственное место — `_add_search_table` в `renderer/orion_golden_render/visual.py`. Пока
ветка выбиралась по длине первого заголовка, таблица «о чём публикации в ТОП-20» отдавала
двум счётчикам 86 % ширины, а текстовой колонке «Тема» — 14 %; высота строки при этом
мерилась по одной колонке, всегда цифровой, и объявлялась в 2–4 раза меньше настоящей.
Теперь текстовая колонка ведёт, номерная узнаётся регулярным выражением, а высота строки —
максимум оценки по **всем** колонкам: отдельного списка «измеряемых колонок», который надо
синхронизировать с пропорциями, больше не существует. Считая доли, помни про поля ячейки
python-pptx (2×91 440 EMU): расчёт «по ширине колонки» без них ошибается на треть, и адрес,
который по бумаге влезал в две строки, рисуется в три и выносит таблицу за границу контента.
Прямая проверка — `renderer/smoke_search_table_layout.py` (уровень `full`); растровый смок
зажатую колонку не видит по построению и служит только регрессией.

**Приёмка собирает вход теми же функциями, что продукт.** Реплей-скрипт эталона
(`scripts/run-orion-deck-sections-report72.ts`) держал собственный загрузчик входов деки.
Тот отстал от продуктового на джойн провенанса — не разрешал `inventory:`-ссылки юнитов
поверхностей — и приёмка собирала деку, где под снимком панели с четырьмя связанными
запросами стояло «0 связанных запросов», а таблица ТОП-20 вырождалась в одну строку.
Девятнадцать ворот из девятнадцати были зелёные: проверки мерили тем же сломанным
индексом. Вход реплея — `loadDeckInputsFromAnalyticsDir`; в скрипте живут только фикстуры
самого прогона: субъект, привязка ассетов, рендер, ворота. Страницу с панелью сверяют с
её же картинкой ворота `panelPagesMatchDrawnRows`; **в приёмочном прогоне отсутствие
входа для них — отказ, а не пропуск**. На живом пути этого свойства нет: там `visualAssets`
передаётся всегда, в том числе пустым объектом при нечитаемом `visual-assets-by-slot.json`,
и ворота выходят вакуумно зелёными — обещать больше приёмки они пока не могут.

**Доля негатива по региону — одно определение и одно место счёта.** Числитель —
уникальные прочитанные страницы региона с вердиктом «о субъекте, нежелательно»;
знаменатель — прочитанные страницы региона минус признанные чужими. `likely` и
`unclear` остаются в знаменателе (они не подтверждены как чужие, и читатель
видит их в выдаче), непрочитанные не входят никуда, кроме числа отобранных.
Округление — `max(1, round())` при ненулевом числителе: «0 %» имеет право
означать только измеренный ноль. Считает `countLinkReadByRegion`
(`load-deck-inputs.ts`), печатают два помощника в `fragment-builders/shared.ts`
— страница региона и одна строка резюме. Словарный процент
`executiveSummary.regionalOverview[].oneLiner` в клиентский текст не
подмешивать: это другой ответ на тот же вопрос (доля по субъектным материалам
региона, а не по прочитанным страницам), и он уже расходился с этим — 7 % при
нуле прочитанных страниц. Без чтения страниц доля не печатается вовсе — словами
о причине, а не нулём.

**Непрочитанный вердикт — не решение.** Вердикт с заполненным `readFailure`
ничего не переопределяет: ни словарную метку, ни тон, ни тему, ни цитату.
«Решение по прочитанной странице сильнее заголовка» относится только к
прочитанным; обратное гасило словарные метки не открывшихся страниц —
`tone: "neutral"` из честного «не знаем» превращался в утверждение о
нейтральности.

**«Проверено, совпадений нет» и «проверка не выполнялась» — разные страницы.**
Комплаенс-страница выбирает формулировку по данным: последний ран базы из
`dp_compliance_screening_runs` едет в артефакт блоком `screenings`, и по нему
различаются успешная проверка без совпадений, сорвавшаяся проверка с названной
причиной и отсутствие проверки вовсе. Пока ответ был один на все случаи,
страницы Dow Jones и LexisNexis печатали «проверка выполнена: записей не
зафиксировано» при трёх фактических совпадениях — провайдер лежал в наблюдении,
а построитель искал его в артефакте, которого в замороженных данных нет, и три
базы схлопывались дедупом в одну безымянную строку.

Поля записи печатаются те, что есть, и ни одной колонки под то, чего нет:
`Sub-Category`, `Level` и связанные лица эталон отрасли показывает, а у нас их
не наполняет ни один источник. Статус виден словами и рядом с каждой записью —
**совпадение по комплаенсу не подтверждается автоматически**, и таблица полей не
должна читаться как утверждение «субъект в санкционном списке».

**«Не спрашивали» — не «спросили, ответа нет», и различает их слово исхода.**
Инструмент, не вошедший в состав прогона, получал от тика тот же `EMPTY_VALID`,
что и настоящая пустота: страница «AI-ответы поисковых систем» печатала
«проверены: материалов нет» про нейро-ответы, которых никто не запрашивал, а
счётчики покрытия записывали две поверхности в «спрошено, пусто». Выключенный
составом агент отвечает `DISABLED` (в счётчиках — `notSupported`), а `scheduled`,
`terminal` и `ingested` у него по-прежнему истинны: на них держатся гейты
завершения стадии, и без них прогон снова ждал бы отключённых вечно. Оффлайн
старше состава — там `EMPTY_VALID` у всех, потому что вопросов не задавали
вообще. Предикат «поверхность не спрашивали» один на конвейер
(`agentWasDisabled`) и читает **данные прогона**, а не текущий `ARSENKIN_TOOLS`:
иначе пересборка старого отчёта на машине с другой конфигурацией переписала бы
историю. Он же знает легаси-форму прогонов до `deck-sections-v91` (`EMPTY_VALID`
без прогона и без задач **при условии**, что хоть один агент этого прогона нёс
реальный `enrichmentRunId`, — без этой оговорки оффлайн-состояния читались бы
как «всё выключено»).

**Маркер это или материал — решают данные, где они есть.** Сборщик пишет вид
строки (`contentKind`: `answer_text` / `answer_source` / `absent` /
`answer_rejected`), и он едет от `dp_search_surface_items.rawMetadata` через
наблюдение слияния до `RawInventoryItem`; `isEmptyMarker` читает его первым.
Разбор по словам остаётся **фолбэком** для поверхностей, вид строк которых
никто не объявил: признак ищется в заголовке — либо в сниппете, но только пока
весь сниппет и есть служебная пометка (`MAX_MARKER_SNIPPET_CHARS` = 240).
Сверять сниппет любой длины нельзя с тех пор, как в него едет текст
нейро-ответа: живой ответ почти наверняка содержит оборот «в открытых
источниках не найдено». Только заголовок тоже нельзя: у записи проверки
Википедии он нейтральный («Wikipedia»), и признак живёт ровно в сниппете. Пока
и то и другое было гаданием, короткий ответ-отрицание расходился с декой:
анализатор считал его пустотой, а страница печатала его с подписью — над
напечатанным ответом стояло «Показано 0 результатов».

**У пустой страницы четыре состояния, и выбирают их данные.** `MEASURED_EMPTY`
(спросили, пусто), `MEASURED_PARTIAL` (одну поисковую систему спросили, другую
нет), `NOT_COLLECTED` (не спрашивали, с названной причиной), `COLLECTION_FAILED`
(сбор сорвался). Единственный канал, которым дека узнаёт о не собиравшихся
поверхностях, — ячейки `NOT_COLLECTED` в `nonOkCoverageCells`: `coverageRows`
строятся из существующих наблюдений и об отсутствующих не знают ничего.
«Проверено» печатается с точностью до поисковой системы: ячейки несут `engine`,
и измеренный факт по одному движку не распространяется на другой. Обратная
сторона того же правила: ячейка «не спрашивали» по Яндексу не глушит выведенную
подсказку о разобранной выдаче Google — иначе честность по одной системе
покупалась бы потерей факта по другой. Отвеченность региона для этой подсказки
считается **по-движково**: собранный нейро-ответ Яндекса не отменяет факта
«Google спрошен, готового ответа в его выдаче нет». Заслоняет выведенный факт
только запись о Google либо запись без названного движка — про неё неизвестно,
чья она.

Когда причин «не спрашивали» несколько (на составе по умолчанию по паре
RU/YANDEX/`ai_answers` приходят и «инструмент вне состава», и «провайдер не
настроен»), печатается та, по которой владелец может действовать: непригодный
ключ сильнее выключенного состава. Выбор — правило, а не порядок конкатенации
`coverageRows`.

**Сводка не спорит со слайдами.** Пробел покрытия в `dataLimitations`
(`coverageDataGaps` в `run-analytics-pipeline.ts`) не печатается, если у той же
пары «регион + поверхность-группа» есть измеренная ячейка. Группировка — той же
функцией `normalizeCoverageSurface`, что у деки, и `knowledge_block` в ней
сходится с `ai_answers`: пока грейдеров было два с разными линейками,
`executive-summary.json` объявлял «ответы ИИ-поиска (UAE): поверхность не
собрана» на том же отчёте, где слайд 55 показывал один собранный ответ.

**Пересборка не уничтожает оплаченную работу.** Полная подготовка отчёта
переписывает артефакты целиком, поэтому каждый из них обязан либо наполниться не
хуже прежнего, либо остаться нетронутым, либо громко назвать потерю. Какая форма
верна — решает не вкус автора, а место, где живёт правда.

*Правда в базе* (`compliance-inventory.json` с записями и итогами скринингов,
`evidence-supplement.json`, аналитические оверрайды и через них состав
`verified-finding-bundle`, счётчики воронки в `report-quality-summary.json`) —
пересборка **перечитывает базу**. Реюз снимка здесь неверен: подтверждение
аналитика могло появиться после прошлой подготовки. Делегаты собирает один
модуль `prepare-prisma-bundle.ts`, и оба боевых вызова (воркер и кнопка
«Golden Prepare») берут бандл только у него: ручной список в вызывающем — это
история `complianceScreeningRun`, реализованного, покрытого юнитом и мёртвого на
каждом живом прогоне, потому что вход `Partial` и забытый делегат не ошибка
типов, а тихая ветка «данных нет». Клиента базы получить не удалось — подготовка
отказывает кодом `PREPARE_DB_UNAVAILABLE` (у джобы это `FAILED_RETRYABLE`), а не
собирает отчёт, отрицающий выполненный скрининг: отказ до первой записи на диск
ничего не теряет, ложное утверждение банку — теряет доверие ко всему отчёту.

*Правда только в артефакте прогона* — это `link-verdicts.json`, и он один такой:
таблицы прочитанных страниц и вердиктов в схеме нет, пересоздать их можно только
заплатив ещё раз за чужие страницы и модель. Поэтому купленный артефакт
**переиспользуется, и реюз сильнее флага**: `DIGITAL_PROFILE_LINK_READING`
разрешает только **первую** покупку, а дальше вердикты не перечитываются и не
затираются, каким бы ни было его значение. Оба положения флага были дефектом:
выключенный затирал решения пустым артефактом, включённый молча покупал их
заново — и второе не замечали, потому что отчёт от этого не ломается, а просто
дорожает. Реюз узкий (своя версия схемы, свой кейс, непустые вердикты) и
видимый: артефакт несёт блок `reuse`. Купленное, которое переиспользовать не
вышло, подменяется громко — `superseded` в артефакте и
`link-verdicts-lost:<причина>` в предупреждениях качества обоих путей
пересборки, — и это верно в обоих исходах: и когда нового чтения не было, и
когда за него заплатили заново. Свежесть не выдумывается: реюз ограничен
каталогом джобы, новый аудит — новый каталог — чтение заново.

*Производные* (все прочие артефакты аналитики, `deck/`, `render/`) не чинятся
отдельно: они пересчитываются сами, когда входы перестают беднеть.

**Оговорка о неполноте — часть утверждения, а не украшение к нему.** Первый живой
прогон запросил 120 страниц, прочитал 74, получил 46 отказов — и отчёт напечатал
«Публикации из ТОП-20 прочитаны», не сказав об этом нигде. Обе копии честной
оговорки погибли по-разному: строку покрытия срезал двухпредложный лимит шаблона,
а процент и базу на российской странице переписала стадия GPT-копирайта — причём
соседнюю страницу ОАЭ она не тронула, то есть честность отчёта зависела от того,
как модель повела себя на конкретном листе. Отсюда два носителя. Строка покрытия
собирается в **первые два предложения**, которые лимит не срезает; фраза доли
живёт в `content.statusNote` — поле не входит в payload для модели и не
принимается от неё, поэтому переписать его нечем. Если оговорка не помещается,
сокращать надо утверждение, а не оговорку.

**Число, единожды посчитанное, моделью не переписывается.** Гейт стадии 2
отклоняет полем переписку, потерявшую числовой токен черновика, — и то же правило
теперь применяется к **укороченному списку буллетов**: пропавший буллет сверяется
с пустой строкой, потому что потеря буллета есть потеря всего, что в нём сказано.
Той же строкой закрылась дыра в гарде цитат: он стоял в том же цикле по ответу
модели, и выброшенный хвост уносил цитаты вместе с их источниками. Цена названа:
переписки с укороченным списком теперь отклоняются целиком, и доля применённых
переписок на живом прогоне ниже — направление отказа безопасное, остаётся
детерминированный черновик.

Границы гейта, названные вслух, чтобы на них не опирались как на большее:
он **односторонний** — ловит потерю числа, но не перестановку («50 из 86» →
«86 из 50» пройдёт, и это единственный из известных случаев, дающий не пропуск, а
неверное утверждение; достижим он только для чисел, оставшихся в нарративе и
буллетах, — фраза доли модели не видна вовсе). Сравнивает **множество** токенов, а
не мультимножество, поэтому повторившееся в черновике число можно потерять
однажды; мультимножество отклоняло бы законное слияние повторного упоминания.
И последнее: защищено то, что можно опознать. Хвостовой буллет **без чисел и без
цитаты с доменом** — «Каждый материал прошёл проверку принадлежности…» — теряется
по-прежнему молча: обеим сверкам на нём не за что зацепиться.

**Резюме называет сюжеты, и ни один из них не сочиняется на месте.** Сюжет —
это строка `summary.themes` из `link-verdicts.json`: фразу написал аналитик
вердиктов по прочитанной странице, кластеризация свела похожие. Резюме её
**копирует** вместе с числами и несёт `evidenceRefs` участников; сюжет без ссылок
или со ссылкой чужого прогона роняет сборку воротами, а не печатается с оговоркой.
Стадия GPT-копирайта составленное резюме не переписывает вовсе — и это не про
гладкость текста: название сюжета было единственным местом отчёта, где модель
могла подменить проверенное непроверенным, оставив ссылку на наблюдение нетронутой,
и никакая проверка прослеживаемости этого не увидела бы. Поэтому вопрос «каким
текстом написано резюме» отвечается один раз, устройством тракта, а не гардом,
который парсит собственный вывод модели.

Тема, у которой страницы прочитаны, уходит из резюме в свой сюжет — решение по
прочитанной странице сильнее заголовка из выдачи. Остальные остаются словарными
блоками и **называют своё основание**: «Страницы по этой теме прочитать не
удалось, тема приведена по заголовкам выдачи». Прогон, где чтения не было вовсе,
печатает ровно те же рубрики, что и до появления сюжетов, — путь не выродился, и
это закреплено регресс-пином. Признак, по которому выбирается путь, лежит в
данных артефакта, а не в названии режима.

**Шаблон, который сам решает «не рисовать», обязан писать телеметрию.** Правило
«выброшенное содержимое — CRITICAL» было записано и механизм построен, но карточная
сетка матрицы рисков телеметрию не писала ни одной записью, поэтому для неё правило
не исполнялось никогда: на эталоне карточка «PEP / RCA / watchlist-сигналы» не была
нарисована нигде в деке при двадцати зелёных воротах. Причина была ниже — `_safe`
плющил переносы, мера высоты работала по схлопнутой строке. Теперь страницы матрицы
пишут запись всегда, а приёмка отдельными воротами проверяет **присутствие** записей:
их отсутствие — отказ, а не пропуск. Проверка, которую забыли подключить, выглядит
точно так же, как проверка, которая проходит.

**Матрица рисков — сводка, а не место для цитат.** Карточка печатает тему, степень,
строку «в чём проблема» и «Что делать»; цитаты живут в тематических блоках
региональных резюме, объяснение риска — в буллетах резюме. Сколько карточек влезает
на лист, отвечает одно место — реестр шаблонов, и число там подобрано **замером**
рендерера, а не расчётом по кеглю: мера высоты щедрее отрисовки, и расчёт «по бумаге»
ошибается на треть в большую сторону.

**Проверка Википедии сверяет имя, а не личность.** Провайдер отвечает на вопрос
«есть ли статья с таким заголовком», и только. На реальном кейсе он вернул
«статья есть» по статье о дворянском роде — однофамильцах, — а разрешение
субъекта пометило её `AMBIGUOUS`. Поэтому страница печатает полное «статья о
проверяемом лице найдена» и рекомендацию контролировать её содержимое **только
при подтверждённой принадлежности**; иначе она честно говорит, что найдена
статья с совпадающим именем, принадлежность не подтверждена, и предлагает
сначала её установить. Опасность при этом настоящая и от принадлежности не
зависит: панель знаний покажет такую статью на запрос об имени, и читатель
примет её за биографию субъекта.

**Подтверждённость принадлежности не чеканится из `exists`.** До 20.08.2026
адаптер дополнения ставил каждой записи проверки
`skipTextClassifier / identityFromReview / reviewStatus: exists ? "MATCH_CONFIRMED"`,
и классификатор по этой мете отдавал `SUBJECT_MATCH @0.95
compliance_match_confirmed`. То есть гарантия абзацем выше в коде **не
исполнялась**: подтверждённость выводилась из того же факта «статья с
совпадающим именем нашлась», который она обязана проверять, — инструмент,
создающий дефект, измерял сам себя, а ветка тёзки была недостижима на живом пути
при живых юнитах. Чеканка удалена и заведена быть не может. Ответчиков за
принадлежность чек-рефа ровно три, и они не спорят:

1. **Классификатор по тексту заголовка** — основной. ФИО в заголовке →
   `SUBJECT_MATCH @0.85 full_name_match`; одна фамилия («Глинка (дворянский
   род)») — не `SUBJECT_MATCH`, лестница решений это уже умеет.
2. **Наследование по межъязыковой ссылке** (`inheritLanglinkDecisions`) — статья,
   найденная через `prop=langlinks`, получает решение статьи-источника: это одна
   сущность Викиданных, и двух ответов о ней быть не может. Токенная
   классификация латинского заголовка («Alexei Mordashov») дала бы
   «не подтверждено» рядом с подтверждённой ru-статьёй. Направление безопасно по
   построению: тёзка-источник передаёт сестре свою неподтверждённость.
3. **Разбор текста статьи** — только **вниз**: `subjectMatch: "other"` понижает
   решение чек-рефа до `OTHER_SUBJECT` там же, где понижают вердикты
   (`load-deck-inputs.ts`). Повышения мнением модели нет — тем же правилом, что
   у вердиктов: полный тёзка проходит модельную проверку насквозь, и
   подтверждённость печати обязана опираться на детерминированный признак.

**Ёмкость листа объявляется там, где её померили.** У страницы Википедии в
реестре шаблонов стоит `maxBulletCharsPerSlide` — сколько знаков списка входит в
**первый** лист. Раньше разбивка шла только по счёту буллетов и молчала, когда
счёт помещается, а знаки нет: три блока по 300 знаков — это «три из четырёх»,
лист их принимал, а рендерер рисовал один и писал `droppedBullets: 2`. Число
взято замером `/orion/measure-layout` на реальной полезной нагрузке
(`availableHeight` 1 542 687 EMU, блок в 253–331 знак — 822 784 EMU, то есть один
блок на лист), а не расчётом «счёт × бюджет знака»: высота блока растёт не
пропорционально числу строк, и произведение ошибается в разы. Шаблоны без
объявленной меры сохраняют прежнее поведение — подставить им расчётное число
значило бы завести второй, неизмеренный ответ о ёмкости.

**Разбор статьи Википедии.** Артефакт `wikipedia-article-review-v1`
(`analytics/wikipedia-article-review.json`) отвечает на вопрос «что в самой
статье», который до 20.08.2026 не задавался вовсе: страница знала только, что
статья есть.

- **Дословность — инвариант.** Модель выбирает и категоризирует
  (`negative` / `needs_update`) **только дословные цитаты** и даёт русскую
  подпись; детерминированный аудит сверяет каждую подстрокой с `articleText`
  готовым `quoteFoundInText`, снимает не подтвердившиеся с записью причины,
  укорачивает переросшие кап до границы предложения с повторной сверкой и держит
  пол принадлежности якорем фамилии (`subjectMentioned`).
- **Рекомендация — детерминированный шаблон по категории**, то есть «что сделать
  с фрагментом», а не «что написать вместо него». Писать за клиента новый текст
  статьи означало бы утверждать биографические факты, которых нет ни в одном
  наблюдении. Сверка «фрагмент противоречит наблюдению N» — честный кандидат на
  отдельный шаг: корпус собранного — заголовки выдачи и ≤120 прочитанных страниц,
  а не база фактов, и такой связке нужен свой аудит ссылок.
- **Состояния честные.** Без ключа модели или офлайн — `NOT_REVIEWED` с
  причиной, и страница печатает её словами; «не выделено» разрешено только при
  `REVIEWED`. Кап входа модели ~60 000 знаков, при срезе — `truncated: true` и
  оговорка «разобраны первые N знаков».
- **«Не выделено» разрешено только при нулевом снятом.** Фраза страницы смотрит
  не на число напечатанного, а на `audit.dropped`: разбор, чьи фрагменты аудит
  снял как непроверяемые, — это не чистая статья. Отчёт аудита поэтому обязан
  доезжать до построителя (`ScopedEvidenceIndex.articleReview.audit`); без него
  «инструмент отработал, а вывод выброшен» и «выделять было нечего» выглядят
  одинаково. Если часть снята при непустом остатке, страница называет число
  неприведённых.
- **Фрагменты не печатаются без подтверждённой принадлежности** — и построителем,
  и **серверными воротами** секционной валидации: ворота, повторяющие вывод
  построителя, подтверждают сами себя. Признак фрагмента — метка категории
  **плюс шаблон страницы** (`wikipedia-check`): «Требует проверки: …» —
  общеупотребительная фраза (статус ручного ревью, уровень риска, подпись
  комплаенса), и одной метки хватило бы, чтобы чужой буллет уронил обязательную
  секцию, то есть деку целиком. Спрашивается принадлежность **той** записи, о
  которой страница печатает (`pickWikipediaCheckEntry` — общий выбор с
  построителем): «подтверждена хоть одна» позволяло бы записи «статьи нет»
  оправдывать фрагменты неподтверждённой найденной статьи.
- **Лид и фрагменты идут буллетами, потому что карточка режет молча.** Карточка
  `content_card` при нехватке места отбрасывает предложения с предупреждением в
  лог и зелёной приёмкой; путь буллетов после перехода на меру рендерера слышен.
  Метка «дословно» стоит на **каждом** листе лида: лид биографии — 700–1500
  знаков, он разъезжается на несколько буллетов, и второй без метки читается как
  утверждение отчёта — рядом со строками «Риск смешения с другим лицом» это
  прямая подмена авторства.
- **Домен внутри дословного текста статьи не вырезается.** Здесь стоял гард
  построителя, обоснованный тем, что иначе доменные ворота уронят обязательную
  секцию. Это неправда: и `section-validation`, и `assembly-validation` берут
  буллеты в разбор только у **унаследованной** области
  (`inheritedScope && !ownScope`), а `wikipedia-check` — own scope и на базовом
  листе, и на продолжении. Гард ничего не предотвращал, зато удалял дословный
  текст и ложно срабатывал на обычной прозе: «предприниматель.Он», «г.Москва»,
  «им.Пушкина» — домен для `DOMAIN_TOKEN_RE`. По существу правило не нарушается:
  домен внутри цитаты — часть текста статьи, а не наша ссылка на источник, и
  источник строки назван на том же слайде адресом самой статьи. Собственную прозу
  страницы (`sourceNote`, «Что обнаружено», объяснения рамок) ворота проверяют
  по-прежнему.
- **Купленный разбор переживает пересборку** (`loadReusableWikipediaArticleReview`)
  — зеркало правил вердиктов: чужой кейс, чужая схема и неразобранный файл реюзом
  не считаются. Но **покупкой был только состоявшийся разбор**: у вердиктов
  неудача даёт пустой массив и решается заново, а у разбора — непустой массив
  честных `NOT_REVIEWED`, и без отдельного условия один транзиентный отказ модели
  или один офлайн-прогон навсегда зафиксировал бы в отчёте «разбор не
  выполнялся». Купленное входит в стадию параметром `previous`, а не подменяет
  её: переиспользуется модельная часть (выбор фрагментов, мнение о
  принадлежности), детерминированная считается по нынешнему снимку, цитаты
  проходят аудит заново.
- **Понижение идёт по ребру наследования.** `subjectMatch: "other"` понижает не
  только свою запись, но и её межъязыковую сестру — в обе стороны. Иначе
  ru-статья становится «о другом лице», а её en-сестра остаётся подтверждённой:
  ровно то расхождение двух записей об одной сущности, ради которого наследование
  и заводилось.

**Первый живой прогон после этого шага читается глазами.** Автоматика не
проверяет ни качества модельного выбора фрагментов на реальной статье, ни тракта
«живая статья → снимок → разбор → лист» одним куском. Что смотреть на первом же
платном прогоне: страницы p13 и p29 целиком (основное описание дословно, блок
фрагментов с категориями и рекомендациями, отсутствие многоточий); находку
en-статьи по межъязыковой ссылке — она обязана быть названа способом находки
рядом с дословным поисковым запросом, который статью не нашёл; и отсутствие
чужого негатива там, где принадлежность не подтверждена.

**Факты API Википедии, добытые наблюдением 20.08.2026** (документация о них
молчит). `action=query&prop=extracts&explaintext=1&formatversion=2&redirects=1`
отдаёт **полный** плейнтекст статьи с заголовками вида `== Санкции ==` — 28,5
тыс. знаков на живой статье, без поля warnings. Один вызов даёт и лид (текст до
первого `== `), и структуру разделов, и тело для разбора; читалка страниц здесь
хуже — «хром» разметки и кап 12 000 знаков. `prop=langlinks&lllimit=50` отдаёт
массив `{lang, title}`; так находится en-статья, которую поиск не нашёл. REST
summary срезает скобки первого предложения (у Мордашова так исчезла дата
рождения, и «основное описание» вышло в 76 знаков) — лидом служить не должен и
остаётся в снимке как есть.

**Маркер «статья не найдена» — не материал.** На поверхности Википедии признак
пустой строки живёт в одном месте — `isEmptyMarker` анализатора, который видит и
заголовок, и сниппет; единицы поверхности несут `emptyMarkerRefs`, и страница
читает их, а не угадывает по заголовку. Строки выдачи (`serp.ts`) свой маркер
пока выводят сами по `NOT_FOUND_PATTERNS` — там заголовок действительно несёт
маркерный текст; свести их к одному признаку стоит, но это отдельная работа. Пока признак был вторым, регэксп в построителе выдавал
два маркера «статья не найдена» за «энциклопедические материалы о проверяемом
субъекте» на странице ОАЭ. Замороженные артефакты старых прогонов поля не несут:
там маркеры из плиток не исключаются, и это осознанный выбор — «не знаем»
честнее второго, расходящегося ответа.

**Ножницы не имеют права возвращать пусто.** `_clip_structured_bullet` ищет
последнюю границу предложения **в пределах бюджета** (тем же правилом, что и
`_clip_words`), а не по всей строке. Пока `rfind` смотрел на строку целиком, у
нарратива в 1387 знаков последняя точка лежала за 900-м, условие «граница
помещается» не выполнялось — и функция возвращала пустую строку. Страница
«Россия — Википедия» живого отчёта пришла с двумя буллетами из трёх: исчезнувший
нёс метод проверки, дату и ссылку на статью, а `ctx.bullets` пропускал его молча.
Состояние «прозаический буллет длиннее бюджета» на эталонах не встречается
(0 из 62 буллетов report-72), поэтому регрессию ловит только смок ножниц
`renderer/smoke_bullet_clip_keeps_head.py` — он же проверяет, что потеря слышна.

**Страницы фактических проверок модель не переписывает.** Идентификация
(Википедия) и комплаенс — `deterministicPrompt`: стадия копирайта переписывает
ровно те поля, где у страницы проверки лежат факты, и однажды выбросила из
нарратива метод, дату и URL найденной статьи, хотя URL был в данных. Полировать
можно интерпретацию, но не страницу, чья ценность — дословность. Второй половиной
того же решения страницы Википедии переведены на структурный шаблон
`wikipedia-check` (`orion_golden_wikipedia_check`): статус проверки, строки
выдачи, рекомендация и футнот методологии печатаются **полями**, а не одним
абзацем, вклеенным в первый буллет. Реестровую запись `wikipedia-knowledge`
переиспользовать нельзя — её же держит слот панели знаний p18 с привязанным
визуалом.

**Языковой раздел спрашивают на его языке.** en-проверка Википедии кириллическим
запросом вернула `exists=false` при существующей статье
`en.wikipedia.org/wiki/Viktor_Rashnikov`, и отчёт напечатал «не найдена» рядом с
той же статьёй в таблице выдачи шестью страницами раньше. Провайдер выбирает
запрос по языку раздела (`queryForLanguage`), латинские варианты строит
транслитерация планировщика запросов (`transliterateRuToEn`) — шестой
транслитерации в проекте не заводится. Запрос проверки пишется в данные
(`snapshot.raw.query` → поле `query` записи → индекс доказательств) и печатается
на странице дословно: «статья не найдена» верно ровно про тот запрос, которым
спрашивали. Артефакт без поля печатает прежнюю формулу «по имени субъекта».

**Утверждение «не найдено» не спорит с собственными наблюдениями отчёта.**
Секционная валидация не пропускает пак Википедии, который отрицает статью,
лежащую в доказательствах его же слайда (строка о субъекте в том же языковом
разделе, что и проверка), пока страница не назовёт её адресом. Сама страница
называет наблюдение дословно — «при этом в поисковой выдаче зафиксирована статья
… (Google, позиция 1)», — а не выводит из выдачи наличие статьи: запрет §1.4 на
SERP-инференцию остаётся в силе.

**Предикат этой оговорки уже обещания — и это принято.** И построитель
(`identity.ts`), и ворота (`section-validation.ts`) требуют от спорящей строки
`subjectDecision === "SUBJECT_MATCH"`, а живая строка en-статьи в бандле имела
`LIKELY_SUBJECT @0.62` (`surname_with_subject_query`) — то есть на прогоне
Мордашова оговорка не сработала и страница ОАЭ отрицала статью **над**
собственными буллетами с этим адресом. Корень закрыт иначе: langlink-проход
провайдера находит такую статью сам, и проверка перестаёт быть отрицательной.
Расширять предикат до `LIKELY_SUBJECT` не стали — вероятная принадлежность не
основание требовать от страницы назвать чужую статью адресом; узость оставлена
осознанно и названа здесь, чтобы не выглядеть недосмотром.

**Фраза о содержании статьи — только из разбора.** Словарь заголовков
(`ADVERSE_PATTERNS`) говорит о **заголовках строк выдачи** и о тексте статьи
ничего не знает. Пока фраза звучала как «существенных негативных или спорных
формулировок в них не выявлено», она читалась как утверждение о статье: на
прогоне Мордашова она стояла на той же странице, где `link-verdicts.json` по
прочитанной ru-статье записал `tone: "adverse"` с цитатами про банк «Россия» и
падение состояния на 11 млрд долларов, а statusNote двумя строками ниже считал
«1 негативный заголовок». Теперь о статье говорит разбор и только он, а словарная
фраза явно названа фразой о заголовках строк.

**Снимок клиентского текста берёт и рекомендации, и карточки.**
`client-text-snapshot.ts` захватывает `actions[].label` и `keyFindings` (версия v2), а не
только тексты слайда. Пока не захватывал, без эталона жили сначала рекомендации пустых
страниц («Что проверить»), потом карточки матрицы рисков: их формулировки можно было
переписать целиком, и ни одна сверка бы не заметила. Поднимая версию снимка, помни, что
старый эталон становится устаревшим по определению — это и есть смысл версии.

**Колонки, под которые нет данных, не заводятся.** Эталон отрасли печатает в матрице
рисков «Возможные последствия»; у нас такого поля нет ни в находке, ни в анализе модели,
и колонка осталась незаведённой. Догадка на месте данных выглядит в отчёте ровно так же,
как факт, — а отвечать за неё некому.

**Ключ без включателя не работает.** Сборщик поднимается цепочкой флагов и
ключей, и пропуск любого звена гасит его тихо: `NOT_CONFIGURED` — законный
исход, в логе ничего. Поэтому контейнер печатает готовность каждого сборщика на
старте и называет недостающую переменную.

**Чужой негатив не работает на профиль субъекта.** На живом прогоне санкционная
подсказка о другом человеке («viktor feliksovich vekselberg ofac») попала в «4
негативные формулировки» профиля Рашникова: классификатор различал только
«недостаточно признаков», а счёт страницы брал красные рамки панели, не глядя на
принадлежность. Теперь: (1) на поверхностях-строках (`autocomplete`, подсказки,
PAA, связанные) имя субъекта плюс чужое отчество — в обоих алфавитах — даёт
`OTHER_SUBJECT` с причиной `suggestion_foreign_patronymic`; правило включается
**только** при непустых структурных `patronymics` профиля — «молчим, а не
гадаем», — а сравнивается кандидат со всеми своими формами, включая похожие на
отчество токены алиасов и транслитераций, через ту же таблицу транслитерации,
которой профиль их порождает. Два набора здесь разные не случайно: фамилия по
форме от отчества неотличима («Абрамович»), поэтому в признак «отчество у
субъекта есть» её пускать нельзя, а в набор для сравнения — нужно, иначе
«roman abramovich sanctions» объявится строкой о другом лице; (2) в счёт негатива
страницы входит только строка, не признанная чужой, — предикат один
(`countsTowardSubjectNegative` в `fragment-builders/shared.ts`) и применяется
заголовком, статусом, метрикой и приёмкой, поэтому даже устаревший ассет со
старой рамкой не вернёт чужую строку в счёт; (3) чужая строка печатается —
панель воспроизводит то, что показывает поисковик, — но нейтральной, с тегом
«о другом лице», с префиксом «Относится к другому лицу:» в буллетах и с
предложением-исключением в статусной строке. Снятая рамка не теряет факт
негативной формулировки: он остаётся в `visibleItems.adverseWording`, иначе
исключённая строка исчезла бы из чисел молча. Строка вовсе без токенов субъекта
чужой **не объявляется** — «требует уточнения принадлежности» честнее догадки;
именованный шум заносится в `negativeIdentitySignals.unrelatedKnownPersons` или
оверрайдом аналитика, дальше пометка и исключение срабатывают сами. Заголовок и
`statusNote` недоступны GPT-стадии — счёт и раскрытие живут именно там.

**Позиция выдачи — свойство пары «наблюдение × движок × запрос».** Место имеет
смысл только внутри нумерации одного поисковика по одному запросу: обогатитель
(Arsenkin) идёт поверх чужой выдачи и считает её по-своему. Источник позиции
вычисляется один раз (`rankInOneScale` в слиянии композита) и дальше едет
**данными** — через `rawMetadata.rankSource` инвентаря и поле `rankSource`
analytics-контракта до индекса доказательств деки. Пока поле умирало на переходе
в инвентарь, защита таблицы «только свои позиции» была истинной вакуумно: на
прогоне 76 из девятнадцати печатных строк «ОАЭ — Google» двенадцать несли
нумерацию обогатителя, а серперные №3 (opensanctions.org), №4 (bloomberg.com) и
№10 (wikidata.org) не печатались вовсе. Отсюда же правила таблицы: она
собирается из наблюдений **своего** движка (одна страница может стоять в обеих
таблицах со своими номерами), запросы сравниваются регистронезависимо
(`normalizeSerpQuery` — тот же ответ, что уже дан на уровне ключей наблюдений), а
политика «источник не назван» — **датасетная**: набор без поля вовсе работает
целиком (старые прогоны не теряют таблиц), в смешанном наборе безымянная позиция
не печатается. Ранг наблюдения без запроса берётся только тогда, когда запроса
нет ни у одного наблюдения таблицы, — иначе безымянная строка агентского
сборщика печаталась чужим номером («7 lenta.ru» прогона 76).

**Движок — часть идентичности строки выдачи** (`searchResultDedupHash`). Пока
`dedupHash` считался без движка, `createMany({skipDuplicates})` выбрасывал строки
того поисковика, который отработал вторым: на прогоне 76 Яндекс шёл первым, и
дыры 1, 2, 3, 5 в таблице «Россия — Google» — это ненаписанные строки, которых
пересборкой не вернуть. Схему это не трогает (меняется значение поля), но после
деплоя повторный сбор уже собранного кейса на короткое время даст в
`search_results` строки со старым и новым хешем; до отчёта дубли не доходят —
слияние композита дедупит по ключу с движком.

**Глубина выдачи — просьба вызывающего и свойство назначения запроса.**
Настройка провайдера задаёт умолчание, потолок задаёт API; правило записано один
раз в `providers/search-depth.ts`. Адаптеров три — google, yandex, serper;
коммит `6e66ef8` починил два, третий нашёлся по прогону 76 (ни одной серперной
строки глубже десятой при яндексовых до двадцати). Потолок Serper — 100, и `num`
> 10 стоит там **два кредита** вместо одного (по сторонним разборам тарифа;
подтвердить счётом первого живого прогона). Отсюда правило сбора
(`organicSearchDepth`): **глубину экономят там, где за неё платят**. У Serper
двадцатку просят только запросы `subject_lookup` — те, по которым строятся
позиционные таблицы, — а пробы (негативная, деловая, медийная) остаются на
умолчании провайдера. У Яндекса глубина входит в стоимость запроса, и просится
всегда, включая пробы: урезанная бесплатная проба — это вдвое меньший корпус
без всякой выгоды.

**Строка плана запросов — то, что набрал бы человек.** Перевёртыш — не написание
имени: по строке «юрьевич олег тиньков» на живом прогоне была куплена выдача (10
наблюдений с настоящими URL), и она же напечаталась клиенту подписью к слайду. В
отборе запроса подсказок перевёрнутое ФИО тоже не имеет собственного балла.
Наборы у планов при этом разные, и это не расхождение, а разная цена строки:
arsenkin-план (`arsenkin-subject-query-plan`) даёт «Фамилия Имя Отчество», «Имя
Отчество Фамилия» и «Имя Фамилия», а orion-план (`ruBaseVariants`) — только ФИО и
«Имя Отчество Фамилия». Добавить «Имя Фамилия» в orion-план значит изменить
состав платного сбора Serper и Яндекса — это отдельное решение, а не выравнивание
формулировок.

**Переставлять части имени можно только у собственной транслитерации ФИО.**
Латиница arsenkin-плана — полное написание и «Имя Фамилия» (отчество за
пределами русскоязычной среды не набирают), но строится это **только** из
транслитерации кириллического `fullName`: её порядок частей задали мы сами, и
двухчастное ФИО даёт «Имя Фамилия» по тому же правилу, а не потому, что фамилия
неизвестна.
Подтверждённый латинский алиас и латинское имя субъекта уходят в план как
записаны. Перестановка «любой латинской строки» давала «bin Mohammed» из
«Mohammed bin Rashid Al Maktoum» и «Yuryevich Oleg» из алиаса «Oleg Yuryevich
Tinkov» — платный `check-top` ОАЭ и подпись клиенту. Генераторов вариантов имени
всё ещё три (`orion-query-plan`, `arsenkin-subject-query-plan`,
`subject-identity-profile-builder`) — все дают человеческие порядки, но вопрос
отвечён трижды: слияние в один — незакрытая задолженность, а дефект такого рода
искать сразу во всех трёх.

**Запрос записывается тем написанием, которым отправлялся.** Эхо Arsenkin
нормализовано в нижний регистр, и запись эха раздваивала написание одного запроса
в корпусе (в живом прогоне 57 строк «тиньков олег юрьевич» против 24 «Тиньков
Олег Юрьевич»), а печатная форма выбирает самое частое — то есть нижний регистр.
Ингест сверяет эхо с запросами заявки без учёта регистра и лишних пробелов и
пишет написание заявки; несовпавшую строку сохраняет как пришла — придумывать
написание, которого не отправляли, нельзя. Сырое эхо остаётся в `responseJson`
задачи. Правило пока выполнено на органике (`check-top` в обоих трактах), а
**три** адаптера всё ещё берут `query` из `response.query`, то есть из эха:
`adaptSuggestions`, `adaptPaa` и `adaptAiSearch` (последний — платный `ai-serp`,
у которого запрос есть). Та же правка ждёт их всех разом; починить два и счесть
вопрос закрытым — значит завести очередной второй ответ. Ложный след:
`adaptUrlAudit` тоже читает `response.query`, но у `check-h`/`indexation` в
заявке `urls`, а не `queries`, — поле пустое, и править там нечего.

**Вторичная ингестия дополняет индекс доказательств, а не переписывает его.**
Примеры «прочих материалов» писались в `evidenceIndex` записью целиком и стирали
позицию, запрос и движок строки выдачи — так №3 выдачи ОАЭ исчез из таблицы при
зелёных воротах. Единственный режим записи для таких ингестий — «только то,
чего в индексе нет»; принадлежность к перечню примеров — отдельный признак
(`uncategorizedExample`), а не подменённый `kind`.

**Печатная таблица выдачи сверяется с артефактом наблюдений, а не с собой.**
Проверка `serpPrintMatchesObservations` в `assembly-validation.ts` смотрит в обе
стороны: каждый напечатанный номер подтверждён наблюдением этого движка по
этому запросу с его же `rankSource`, и каждое такое наблюдение с позицией не
глубже двадцатой напечатано. Движок и запрос она берёт из метрик пака (печатный
факт), а не пересчитывает пикером — иначе сломанный пикер согласился бы сам с
собой. Допустимые потери названы поимённо: дубль позиции и маркер «ничего не
найдено». Сверяются только таблицы, объявившие себя позиционными
(`serpPositional` в метриках пака): у движка без единой своей позиции таблица
честно вырождается в «собранную выдачу» с порядковыми номерами, и прочитанные
как позиции они уронили бы приёмку здорового прогона. На наборе без
`rankSource` (и на деке без позиционных таблиц) проверка **объявляет пропуск
строкой** в `assembly-validation-report.json`: тихий пропуск неотличим от
пройденной проверки.

**Неполная позиционная таблица говорит о себе словами.** Когда собранных позиций
меньше обещанных двадцати, заголовок называет фактический диапазон
(«…Google, ТОП-20: позиции 1–10»), а под таблицей стоит строка о том, что
отсутствующие номера потеряны при сборе, а не пусты в выдаче. Данные,
не записанные при сборе, вернуть нечем, и молчание о них читается как факт о
субъекте.

Порядок прозы на такой странице — не оформление: шаблон
`orion_golden_search_table` рисует **два первых законченных предложения**
нарратива, поэтому перед выводом страницы стоит только необходимое (чей запрос
и почему дыры), а тематическая строка и справка о наборе запросов идут после
(`serpTablePageProse`). Справка не печатается, когда запрос в прогоне один: она
дословно повторяла заголовок выдачи и вытесняла с листа вывод.

### Что нужно знать про API Arsenkin

Документация (`help.arsenkin.ru/api`) описывает вызовы, но **не приводит тел
ответов**. Фикстуры `check-*.json`, лежавшие в репозитории, были выдуманы:
формата `{"status":"done","progress":100}` у провайдера нет — судя по `/get` и
ответу об ошибке, он отвечает полем `code` вида `TASK_RESULT`. Поэтому разбор
ответа `/check` устроен так: узнаётся завершение, всё прочее означает «ещё не
готово, спросить снова», а неузнанная форма пишется в лог событием
`arsenkin_check_shape_unknown` — чтобы контракт можно было записать по факту, а
не по догадке.

Жёсткие пределы аккаунта, которые документация называет прямо:

- **не более 5 задач одновременно**, очередь — до 50;
- **не более 30 запросов в минуту** на все обращения вместе: `/set`, `/check`,
  `/get`, `/info`. Превышение — `429`.

Второй предел определяет частоту опроса. Опрос раз в две секунды — это 30
запросов в минуту на одну задачу, то есть весь бюджет аккаунта на неё одну;
отправкам не остаётся ничего, и прогон встаёт при исправном провайдере.
Инструменты идут минутами (`check-top` — три-шесть), поэтому пауза растёт
5с → 30с. Общий ограничитель на аккаунт (`account-rate-limit.ts`) держит 24
запроса в минуту и живёт в базе — он общий на все процессы, а не на экземпляр
клиента.

Исходы агента различают смыслы, а не только успех и отказ: `SUCCESS` —
наблюдения есть, `NO_RESULTS`/`EMPTY_VALID` — спросили, ответа нет, `DISABLED` —
инструмент не входил в состав прогона, `FAILED`/`SUBMIT_UNKNOWN_UNRECONCILED` —
разбираемся. Составом по умолчанию работают трое (`check-top`, `suggest`,
`paa`); `ai-serp` и `check-h`/`indexation` выключены, и это **не** вывод о
тарифе аккаунта: на эталоне report-72 тот же `ai-serp` задачи принимал и вернул
`NO_RESULTS`. Из данных прогона выводится только состав, и только он называется
в отчёте причиной.

Откуда берётся ИИ-ответ. Три источника, и они не заменяют друг друга:
`answerBox` ответа serper (читается сейчас; поле Google **AI Overview** наш
адаптер не читает и утверждать о нём нечего), арсенкинский `ai-serp` (Алиса на
поиске + Google AI Overview; составом по умолчанию выключен) и **нейро-ответ
Яндекса — его собирает базовый сбор**. Скрейпинг выдачи и «похожая справка»
своей моделью запрещены § 1: первое — обход правил сервиса, второе —
выдуманный факт в отчёте банку.

**Нейро-ответ Яндекса собирается официальным `POST /v2/gen/search`** тем же
ключом и каталогом, что органика (`YANDEX_SEARCH_API_KEY` /
`YANDEX_SEARCH_FOLDER_ID`; собственных переменных у него нет). Один вызов на
прогон, контур RU, запрос — первый субъектный запрос RU-плана; он выводится тем
же построителем, что и план, а не читается из `dp_search_queries`, потому что
`createMany` не гарантирует порядок выборки. `fixMisspell` выключен намеренно:
«исправленное» ФИО — это другой субъект.

Контур вопроса зафиксирован российским (`SEARCH_TYPE_RU`) независимо от
`YANDEX_SEARCH_REGION`: наблюдение приписывается RU, и спрашивать чужой индекс
из-за настройки органики значило бы назвать турецкую выдачу российской.

Ответ и названные Яндексом источники — строки `dp_search_surface_items` типа
`AI_ANSWER` (у тела синтетический адрес `yandex-gen://answer/<hash>` и полный
текст в `snippet`, у источников — настоящие адреса). Исход попытки — поле
`yandexGenAnswerProbe` в `base-collection-manifest.json`, и **из него читаются
только не-успешные исходы**: успех доказывают сами строки, второго ответа на
вопрос «собрано ли» не заводится. Отказ модели (`is_answer_rejected`) — это
измеренная пустота со словами «ответ не предоставлен…» (паттерн в
`NOT_FOUND_PATTERNS` расширен), а не сбой и не находка.

Форма REST-стрима документацией описана, но живым ответом **не подтверждена**,
поэтому парсер (`providers/yandex-gen-search.ts`) терпим намеренно: единый
JSON, поток JSON Lines, обёртка `result`, оба регистра полей, старые
`links`/`titles`. Сузить его можно только по сырому ответу, сохранённому в
`rawMetadata` строки-тела, — как и с фикстурами Arsenkin, формат снимается с
прогона, а не с документации.

Из потока берётся **последний объект, несущий исход** (текст либо отказ), а не
последний вообще: grpc-gateway закрывает поток служебной строкой, и безусловный
«последний» выбрасывал бы готовый ответ, превращая его в измеренную пустоту без
следа. Ошибка в любом объекте потока — сбой разбора: оборванный поток обязан
выглядеть сбоем и на странице, и в записи о попытке.

Подпись под ответом печатается у **каждого** ИИ-ответа, а не только у
собранного официальным API, и выводится из данных наблюдения (провайдер и
движок), а не из схемы адреса: без подписи текст поисковика читается как
утверждение отчёта о человеке. Поисковая система называется, только когда она
известна: `mapEngineBucket` отдаёт `UNKNOWN` при пустом движке, и приписать
такой ответ Яндексу значило бы соврать о происхождении в клиентском тексте. Ключ дедупликации строки — синтетический адрес
(`тип|источник|url`), поэтому у тела и у маркеров он разный, а у тела в него
входит и сам текст: изменившийся ответ — новое наблюдение, повторный сбор того
же — нет.

Что до сих пор не сделано: таблица метрик региона молчит о невыполненном аудите
URL — строка появляется только при существующих единицах
(`fragment-builders/regional-summary.ts`), и явное «не выполнялся» там ещё
предстоит написать.

### «Негативна ли строка» и «почему она выделена» — по одному ответу на отчёт

**Решение по прочитанной странице — единственный ответ на «негативна ли
строка»**, и для деки, и для снимка выдачи. Словарь ключевых слов в заголовке
(`serp-observation/resolve-observation-highlights.ts`) остаётся фолбэком для
строк, которых не читали. До этого правила рамку на снимке ставил словарь, а
вердикты видела только дека: один лист мог нести красную рамку, которую текст
рядом опровергал. Карта решений едет в визуальный слой параметром
`verdictByRef` — тем же образцом, что `subjectDecisionByRef`.

**Фраза «Почему выделено» собирается детерминированно** (`highlightPhrase` в
`fragment-builders/shared.ts`): сюжет страницы, дословная цитата, прошедшая
аудитора, и адрес наблюдения. Модель на сборке деки её не пишет и не правит —
`highlightExplanations` не входят в payload ни одной GPT-стадии, и это
закреплено тестом. Непрочитанная строка объясняется рубрикой справочника и
названной причиной непрочтения, без цитаты и без сюжета: сочинять содержимое
страницы, которую не открывали, нельзя.

**Язык тем клиентского документа — сюжеты прочитанных страниц** (кластерные
ярлыки `link-theme-clustering`): резюме, страница тем и легенда снимка говорят
одними словами. Рубрики `config/finding-themes` остаются языком классификации
находок (матрица рисков) и фолбэком для непрочитанного.

**Сайдбар несёт две фразы по 240 знаков** (`SIDEBAR_HIGHLIGHT_BUDGET` и
`SIDEBAR_HIGHLIGHT_SLOTS` в `template-registry.ts` — одно число на построитель и
на сборку payload). Внутри фразы цитата уступает адресу: укороченная по границе
предложения цитата остаётся дословной, а без адреса утверждение нечем проверить.
Цитата с многоточием в панель не идёт вовсе — панель многоточий не допускает, и
подгонка под неё правила бы цитату внутри кавычек.

Что не поместилось, забирает **слайд-продолжение «…: почему выделено» — и он
есть только у снимка выдачи** (`serp.ts`): по буллету на каждую выделенную
строку, с полной цитатой и полным адресом. Страницы изображений и подсказок
пользуются тем же строителем фраз, но продолжения не выпускают: там видны
первые две фразы, а остаток объявлен строкой «Ещё N похожих сигналов»
(`visual.py`). Так на `p30_uae_images` эталона: четыре фразы в пакете, две на
листе. Распространить продолжение на эти страницы — отдельное продуктовое
решение, а не недоделка.

**Напечатанный адрес проверяется целиком, но только свой.** Ворота «домен
выведен из доказательств страницы» разбирают текст одной функцией
(`undeclaredClientTextDomains`) — и секционная валидация, и проверка сборки.
Раньше у них были свои выражения (ASCII против юникода), а сегмент пути вида
`otchet.html` читался как отдельный домен: его нет среди доказательств, и
обязательная секция получала отказ, то есть дека не собиралась вовсе.

Освобождён от разбора не любой адрес, а тот, что действительно есть у страницы,
и **сверка идёт точным совпадением печатных строк** (`clientAddress`), а не
разбором границ. У пути нет «конца слова»: в нём законны пробел (из `%20`),
точка с запятой, апостроф, скобки, и любой набор терминаторов на них
промахивается — тогда хвост собственного адреса уходит в общий разбор и роняет
обязательную секцию на совершенно корректных данных. У чужого адреса
проверяется и хост, и каждый домен в пути.

**Область страницы наследуется продолжением:** список проверяемых слайдов
строится по свойству слайда, а не по перечню шаблонов, — иначе новый тип листа
выводит текст из-под fail-closed ворот целиком, как это и случилось со страницей
«почему выделено».

Под воротами при этом **не весь текст слайда, а названные поля**:
`whatWasFound`, `sourceNote`, `highlightExplanations`, и `bullets` — только у
страницы, унаследовавшей область (там в буллетах живёт весь её текст). Остальное
делится надвое, и причины у половин разные.

`narrative`, `whyItMatters`, `whatToCheck`, `statusNote` печатают голые домены,
которым точное совпадение не нужно; завести их под ворота можно хоть сегодня, и
единственная причина, по которой их там нет, — что шаг расширял разбор ровно
там, где вводил новый текст. Это дешёвый долг, а не решение.

Строки таблиц (`serp.ts`) и буллеты страницы идентичности (`identity.ts`) —
другое дело: они печатают ссылку **обрезанной** формой (`clientLink` с
многоточием), которая точному совпадению не поддаётся, поэтому включение их в
разбор вернуло бы отказ обязательной секции. Их можно заводить только вместе с
единой формой печати адреса.

### Клиентская шкала риска — три ступени

**В данных уровней четыре, клиенту печатаются три.** `none/low/medium/high/critical`
в контрактах и `CRITICAL` в схеме — это порядок и пороги, они остаются: сортировки
(`RISK_ORDER`) работают по уровню данных, поэтому бывший CRITICAL стоит первым внутри
«Высокого». Схлопывание (`critical|high → высокий`, `medium → средний`,
`low|none → низкий`) и все словоформы — в
`orion-golden/client/risk-scale.ts`, и **только там**: новое место печати уровня
обязано импортировать модуль, а не заводить свою таблицу. Пока таблиц было девять,
плашка резюме печатала «Повышенный риск» рядом с трёхсловными карточками матрицы —
две шкалы в одном документе. Слово «Нет» из печати ушло: подтверждённая тема без
негатива — это низкий уровень внимания, а не пустая клетка.

**Семантика ступеней.** Высокий — подтверждённое совпадение по санкциям/PEP либо
уголовный или судебный сюжет с прослеженным негативом. Средний — негативная тема без
судебного или санкционного признака. Низкий — всё остальное. Печать этой семантике
следует не везде. Ниже — расхождения, найденные на сегодня; список **не объявляется
исчерпывающим**: деривация уровня живёт в `finding-synthesizer.ts`, и каждое её правило
надо сверять с таблицей отдельно.

- совпадение комплаенса в `PENDING` печатается статусом «Требует ручной проверки» и
  уровень находки не поднимает;
- доля негатива региона (`metricSnapshot.linkReadByRegion`) печатается фактом и
  тональности не задаёт — это вход будущей оценки профиля региона;
- **данные строже метрики на счёте негатива:** `finding-synthesizer.ts` поднимает
  тему до `high` при трёх и более негативных свидетельствах
  (`adverseCount >= 3 ? "high" : theme.baseRisk`), поэтому негативная тема без
  судебного и санкционного признака печатается «Высоким», а не «Средним». Занижать
  печать под метрику нельзя: тогда отчёт сказал бы о находке меньше, чем знают
  данные.
- **там же, в другую сторону:** `if (adverseCount === 0) return theme.baseRisk === "high"
  ? "medium" : "low"` — судебная тема (`criminal_legal`, `security_scrutiny`, у обеих
  `baseRisk: "high"`) при **нуле** негативных свидетельств печатается «Средним», хотя
  таблица отправляет её в «Низкий»: под определение среднего она не подходит ни по одному
  признаку. Направление то же — строже метрики, — и по той же причине не занижается.

Проведение первых двух и пересмотр третьего — изменение деривации данных, то есть
отдельные шаги.

**«Требует подтверждения» — статус идентификации, а не ступень.** Тональности он не
печатает, в полезной нагрузке получает тон `warn` и **не рисует делений** шкалы
степени: пока деления выбирались по тону карточки, непроверенный материал стоял ровно
на середине шкалы риска (3 из 5), как и «Нет данных» пустой матрицы. В рендерере
ступень узнаёт одно место (`layout_cleeq.level_step`), делений по ступени
5 / 3 / 2, у не-ступени ноль — и при нуле шкала не рисуется вовсе. По тону это решать
нельзя: тон `warn` носит и «Средний». Словарь ступеней в рендерере при этом
**свой** — подстроки «высок / сред / низк», связи с `risk-scale.ts` у него нет:
рендерер получает готовые слова и языковой границы не переходит. Переименование
ступени поэтому требует правки обеих сторон. Порядок задан **уровнем данных**:
`packRiskMatrixPages` сортирует и подтверждённые находки, и блок LIKELY по
`RISK_ORDER`, то есть статус тоже упорядочен уровнем — просто на печать этот
уровень у него не выходит.

**Рендерер знает оба словаря тонов, и это осознанно.** Плитки метрик говорят
`risk|warn|good|accent`, клиентская шкала риска — `danger|warn|neutral`. Пока
`_tone_fill` знал только первый, `danger` красился дефолтом, то есть **белым**:
карточка «Высокий» выходила единственной без тревожного фона — при пяти красных
делениях шкалы рядом. Теперь `danger` красится той же подложкой, что `risk`, а
`neutral` — белым намеренно: нижняя ступень тревоги не несёт. Закреплено
`renderer/smoke_risk_matrix_cards.py`.

**Что осталось разрывом и ждёт владельца:** «Требует подтверждения» и «Нет
данных» получают тон `warn` и печатаются на тёплой подложке. Честная пустота на
фоне, близком к тревожному, — вопрос палитры, а не незнакомого токена, и решать
его должен владелец.

**Плашка вердикта печатается теми же тремя словами:** `HIGH` и `ELEVATED` —
«Высокий риск», `MIXED` — «Средний риск», `LOW` — «Низкий риск»,
`INSUFFICIENT_DATA` — «Недостаточно данных» (это не ступень, а честное «вывода
нет»); неизвестный вердикт печатается как «Требует уточнения», сырой enum в плашку не
уходит.

Нюанс вердикта живёт в предложении вывода — но **только на детерминированном пути**:
`verdictWording` (`executive-summary/deterministic-composer.ts`) различает `HIGH`
(«подтверждённые существенные риски») и `ELEVATED` («значимые риски, требующие
внимания»). На пути составленного резюме (`ComposedClientSummary`) такого
предложения нет вовсе, и после схлопывания `HIGH` и `ELEVATED` там **неразличимы** —
раньше их различало слово «повышенный» в самом выводе. Это названная потеря, а не
недосмотр: возвращать различие значит писать в вывод новое клиентское предложение,
а его состав — продуктовое решение, а не следствие схлопывания.

**Ступень называет тот, кто её вычислил.** `client-summary-composer` своей оценки к
выводу пакета не приписывает: пока приписывал, пакет без единой существенной темы
получал «Итоговая оценка: низкий риск» перед собственной фразой «существенных
рисковых тем не выделено; вывод ограничен доступностью данных», а вердикт аналитики
на этом пути не участвовал вовсе — плашка могла сказать «Недостаточно данных» над
текстом про «низкий риск».

**GPT-словарь: промпты предлагают три слова, схемы принимают четыре.** Ответ модели
с привычным «критический» нормализуется к «высокий»; сузить словарь приёма значило
бы уронить валидацию на эхе модели и молча потерять GPT-копию секции целиком.

**Оценка профиля региона, когда появится, обязана переиспользовать `risk-scale.ts`** —
вторая шкала серьёзности в одном документе запрещена этим же решением, и буква A–E
рядом с тремя словами была бы именно ею.

### Машинные коды в клиентском тексте

**Коду провайдера на слайде взяться неоткуда.** Детектор внутренних кодов ловит
подчёркивания (`role.pep`, `us_ofac_sdn`), и всё, что на них не похоже, проезжало
мимо: на живом прогоне 20.08 (стр. 61) банк читал «Страны в записи: ru, ch» и
«источники: ext_gb_coh_psc, wd_oligarchs, …», а страница обзора — плитку
«Региональные контуры: RU · UAE». Имя набора данных теперь называется числом
(«источника в записи: 2»), прослеживаемость держит ссылка на карточку записи
строкой ниже; контуры называются словами через `regionClientLabel`.

**Страны называет лестница в `fragment-builders/shared.ts`** (`countryNamesRu`),
первый ответ выигрывает:

1. alpha-2 через ICU — «ru» → «Россия»;
2. `EXTRA_TERRITORY_NAMES_RU` — **только то, чего в ICU нет вовсе**: коды
   территорий FollowTheMoney (`gb-sct`, `so-som`, `cy-trnc`, `ge-ab`, `az-nk`, …)
   и четырёхбуквенные ISO 3166-3 (`suhh`, `ddde`, `yucs`, `cshh`). На них
   `Intl.DisplayNames` **бросает**, а не возвращает код;
3. обратный указатель «название → русское название», построенный из самого ICU, —
   «Iran», «Cuba», «Germany», «россия». Своего списка стран в проекте нет: полный
   ICU в контейнере — часть контракта клиентского текста, и урезанный обязан
   ронять `npm run ci` (закреплено тестом карточки, а не тестом функции);
4. не разобрали и похоже на машинный код (включая дефисный `xx-yyy`) — одна общая
   формулировка «страна не распознана», без счёта: «ru» и «RUS» могут быть одной
   страной, и число назвало бы две;
5. иначе — дословно: «Швеция» из ручного импорта уже клиентский текст.

**Alpha-3 (`RUS`, `CHE`) остаётся нераспознанным намеренно.** Свести его к
alpha-2 усечением нельзя: `CHN` → `CH` это Швейцария вместо Китая, `ARE` → `AR` —
Аргентина вместо ОАЭ, `IRL` → `IR` — Иран вместо Ирландии. Таблицы alpha-3 в ICU
нет, а руками это весь список стран заново — и опечатка в нём напечатает банку не
ту страну, что хуже общей формулировки. Полная таблица — отдельное продуктовое
решение, а не побочный шаг.

**Строка «Страны в записи» ограничена 200 знаками**, как соседняя строка алиасов и
по той же причине: после перевода кодов в названия значения выросли втрое-вшестеро.

**`report/i18n/plural-ru.ts` входит в отпечаток построителей** (`EXTRA_SOURCES` в
`tests/unit/deck-content-version.test.ts`). Построители зовут склонение на каждой
странице со счётом; пока файл лежал вне отпечатка, правка склонения не сдвинула бы
версию, и пересборка отдала бы кэш со старой формулировкой. Единственный экземпляр
правила живёт там же — реэкспорта из `finding-synthesizer.ts` больше нет.

### Сниппет справочника — не утверждение о человеке

Карточка человека в реестре или каталоге перечисляет разделы, которые на ней
есть, и поисковик забирает этот перечень в сниппет. На живом прогоне 20.08 (кейс
Прохоров) банк получил **ключевым риском №1** «Криминальные / судебные
материалы»: под находкой стояла одна карточка `bizfiles.org` с двадцатого места
Яндекса, страница не читалась, а весь «криминал» был словом «суды» в строке
«Сводка информации, аффилированность, финансы, суды». Такой перечень стоит на
карточке любого человека на этом сайте.

**`itemText()` в `finding-synthesizer.ts` не берёт сниппет у площадок, чей тип —
«База данных / реестр» или «Агрегатор / каталог».** Тип спрашивается у
`analytics/source-type.ts`; второго списка доменов в аналитике нет. Заголовок,
классификация и адрес участвуют по-прежнему: режется сниппет, а не домен целиком,
и заголовок карточки реестра («Суд взыскал с …») темой остаётся.

Прочитанная страница здесь ничего не теряет — её темы идут своим путём,
`run-link-verdicts.ts` → `link-theme-clustering.ts`, и `itemText` в него не
входит: вердикт кладёт сниппет наблюдения в поле `serpSnippet` и текстом страницы
его не подменяет.

**Тема, оставшаяся без материалов, из отчёта исчезает** — ни карточки в матрице,
ни строки в резюме (решение владельца 21.08). Сама страница остаётся в таблице
выдачи нейтральной строкой: клиент её видит, но как справочник, а не как криминал.

**Рядом остался известный и не взятый дефект:** `riskFor()` поднимает тему до
`critical` по правилу `adverseCount / total > 0.5`, а на одном материале эта доля
равна единице всегда. Владелец выбрал резать только по типу источника; пункт
назван в бэклоге.

**Ни один офлайн-контур эту ветку не исполняет.** Ни в золотом кейсе, ни в
`report-72` нет наблюдения со справочного домена, чей сниппет давал бы тему:
пересборка обоих эталонов не сдвинула ни одного слова клиентского текста. Правило
держит только юнит-тест `directory-snippet-is-not-a-risk-theme.test.ts`, и
проверить его на настоящих данных можно лишь живым прогоном.

### Сюжет прочитанных страниц — сколько его видно клиенту

Блок сюжета в резюме печатает название, счётную фразу («по сюжету прочитано 9
публикаций, 9 из них нежелательных»), домены участников и цитаты. Цитат было
**две**, и на отчёте Прохорова (20.08) это скрыло ровно то, ради чего сюжет
собирается: из девяти публикаций сюжета «Скандалы, конфликты и критика деловой
репутации» клиент видел Википедию и Куршевель, а разбор файлов Эпштейна — нет;
из пяти публикаций «Санкции, гражданство и зарубежные активы» не было видно
виллы на Ибице. Обе страницы были прочитаны и имели вердикт `subject` +
`adverse` с дословными цитатами — терялись они на печати, а не на сборе.

**Предел объявлен один раз — `READ_PLOT_QUOTE_LIMIT` в
`contracts/client-summary-pack.ts`,** и его берут оба места, которые раньше
отвечали на этот вопрос порознь: цикл `buildReadPlots` и `max()` схемы. Сейчас
шесть. Не «все»: резюме обязано сказать, о чём сюжет, а не пересказать его —
масштаб даёт счётная фраза.

**Срез не молчит.** Когда процитированы не все прочитанные публикации, блок
называет это числом: «Процитировано 6 публикаций сюжета из 9 прочитанных».
Молчаливый срез читается как «это всё, что нашли».

Длинный блок раскладывается по страницам сам: `semantic-summary-pagination.ts`
режет его по предложениям (`packSentencesNoTruncate`) и раскладывает по
страницам продолжения, ничего не выбрасывая. Ограничения на число страниц
продолжения нет — это осознанно.

**Ветку не исполняет ни один офлайн-контур:** ни у золотого кейса, ни у
`report-72` нет `link-verdicts` — страниц там никто не читал, сюжетов не
возникает. Всё, что держит этот блок, — юниты
(`read-plot-quotes-come-from-its-pages`, `summary-plots-reach-client-text`,
`summary-of-plots-is-worded-verbatim`). Увидеть его целиком можно только на
живом прогоне.

### Источник называется полным адресом

Правило владельца (21.08): «источник нужно указывать полной ссылкой, а не только
домен. А то логика такая, что „где-то на сайте есть, ищите сами“». До этого
рядом с цитатой стоял домен — `«Прохоров Михаил Дмитриевич Москва» — источник
bizfiles.org`, — а `clientAddress` вдобавок **выбрасывал строку параметров**, и
на странице печаталось `youtube.com/watch`, то есть ссылка в никуда.

**Правило одно на весь отчёт:**

1. Адрес — это хост, путь, строка параметров и якорь. Без протокола: в тексте он
   ничего не добавляет, а восемь знаков ширины отнимает.
2. Метки отслеживания (`utm_*`, `fbclid`) не вычищаются. Решать, какой параметр
   адресует страницу, значит гадать, а адрес, который открывается, дороже
   короткого.
3. **В тексте адрес стоит в круглых скобках, знак препинания — снаружи.**
   `lenta.ru/tags/persons/prohorov-mihail.` не читается: то ли точка часть
   адреса, то ли конец предложения. Закрывающая скобка кончает адрес.
4. Адреса нет — называется домен. Нет и его — источник не называется вовсе;
   прочерка не ставится.

**Одно место — `orion-golden/client/client-address.ts`** (`clientAddress`,
`clientAddressText`, `sourceAttribution`). Раньше разбор лежал в
`deck-sections/fragment-builders/shared.ts`, куда аналитике ходить нельзя, —
отсюда и домены в её тексте. Файл входит в `EXTRA_SOURCES` отпечатка
построителей по тому же основанию, что и `risk-scale.ts`: он решает слова
страницы.

**Колонка таблицы — единственное исключение по ширине.** `clientLink` при
нехватке места сначала снимает строку параметров и только потом режет с
многоточием: обрезанный адрес не открывается, а тот же адрес без параметров
ведёт на ту же страницу. Порядок именно такой, потому что параметры нужны там,
где без них страницы нет (`youtube.com/watch?v=…`), — а такие адреса коротки.

**Готовый текст ищут по `SOURCE_ATTRIBUTION_SOURCE`** (там же). Перекладка
тематического буллета и сторож, следящий, что модель не потеряла источник, оба
искали `источник <домен>` и на форме `источник (адрес)` строку не видели вовсе.
Совпадение обязано покрывать адрес целиком: опознанная наполовину строка рвалась
при перекладке, и путь уезжал в конец абзаца отдельно от своей цитаты.

**`clampClientText` снимает обрубленный хвост, начатый ярлыком.** «Где видно:»,
«Что делать:», «Всего по теме:» обещают содержимое; рез посреди него давал либо
голый ярлык («…Где видно:» и сразу маркер находки), либо список, оборванный на
первом имени. Второе хуже: читатель не видит, что список неполон. Правило
срабатывает только когда рез пришёлся не на конец предложения.

**Буллеты плитки обзора подгоняются `bulletWithFindingId`, а не резом по
знакам.** Прежний рез плющил буллет в одну строку и отрезал хвост; с полными
адресами это уносило вторую цитату раньше служебных строк — ровно наоборот к
порядку сброса, ради которого `fitStructuredBullet` и заведён.

### Сторож внутренних кодов читает слайд целиком

`clientVisibleStrings` (`deck-sections/internal-code-scan.ts`) читал пять полей
из шестнадцати — `title`, `subtitle`, `narrative`, `staticBlocks`, `table`.
«Замечаний нет» в `assembly-validation-report.json` поэтому не означало «в
клиентском тексте кода нет»: вне проверки оставались буллеты (самый
содержательный текст отчёта — фрагменты статьи Википедии, строки нейро-ответа,
источники карточек), все четыре поля панели, статусная строка, легенда, плитки,
методика и фразы «Почему выделено».

**Список полей ведётся по типу `RendererSlide`** (`deck-assembler.ts`). Поле,
которое видит клиент, обязано попадать в проверку; у составных полей берётся
только клиентская часть — `clientReason` у объяснений (но не `frameTone`),
`label` и `value` у плиток (но не `tone`).

**`emptyStateReason` не читается намеренно.** Это машинное поле контракта
(`no-organic-data`, `VISUAL_ASSET_UNAVAILABLE`); рендерер его не рисует вовсе —
имени нет ни в одном файле `renderer/*.py`, — и значения там кодовые по замыслу.
Оно объявлено в интерфейсе именно затем, чтобы было видно: о нём подумали.

**Что нашлось при расширении:** ничего нового. Ни на эталоне `report-72`, ни на
золотом кейсе, ни на живой деке Прохорова (68 страниц) расширенные поля кода не
содержат. Пять находок на живой деке — имена наборов OpenSanctions в `table`
(`ext_gb_coh_psc`, `wd_oligarchs`, …); их видел и прежний сторож, и починены они
у источника шагом «машинные коды вон из клиентского текста».

**Рядом живёт второй список клиентских полей** — `TEXT_FIELDS` и соседние
разборы в `scripts/lib/client-text-snapshot.ts`. Он читает **полезную нагрузку
рендерера**, а сторож — контракт слайда, поэтому имена полей у них разные
(`kpis` против `metrics`, `highlightExplanations` на верхнем уровне против
`visualAnalysis.highlightExplanations`). Свести их в один список нельзя без
общего представления слайда; расходиться они при этом могут — держать в уме.

### Ответ поискового ИИ печатается текстом, а не разметкой

Нейро-ответ Яндекса приходит размеченным Markdown. На живом прогоне 20.08 это
доехало до бумаги дословно: `**Михаил Дмитриевич Прохоров**` со звёздочками,
соседний буллет, начинающийся со сноски «[2]», и строки со звёздочкой-маркером
списка. Владелец прочитал страницу как «в целом каша».

Разметка была не только уродством, но и причиной разъезда: страница печатает
ответ, разложенный по границам предложений (`packSentencesNoTruncate`), а в
размеченном тексте после точки идёт `\n\n**Заголовок**` и сноска — разрыв
приходился **между** предложением и его сноской.

**Одно место снимает разметку — `orion-golden/client/ai-answer-text.ts`**
(`plainAiAnswerText`), и его зовут оба пути: построитель страницы
(`knowledge-ai.ts`) и сборка картинки-панели (`canonical-visual-assets.ts`).
Снимаются `**жирный**`, `__жирный__`, заголовки `#`, маркеры списка в начале
строки и оставшиеся одиночные `*`. Слова не трогаются.

**Сноски `[1]`, `[2][3]` убираются.** Они ссылаются на нумерованный список
источников Яндекса, которого в отчёте нет: у нас источники печатаются строками
«Источник: … — домен» и в другом порядке. Номер, ведущий в никуда, — то же
самое, что машинный код.

**Строка списка получает точку.** Без неё следующий пункт приклеивается к
предыдущему, и разбивка по предложениям снова разъезжается. Заголовок с
двоеточием точки не получает.

**Сырое наблюдение не трогается:** в `snippet` ответ остаётся дословным —
прослеживаемость до первоисточника важнее удобства печати.

**Панель рисует абзац** (`buildKnowledgePanelSvg` через `wrapToWidth`): до семи
строк рядом с фактами и до одиннадцати без них. Высота картинки прежняя —
рендерер вписывает её в тот же бокс, и более высокая картинка означала бы мельче
текст; полный ответ по-прежнему несёт текст страницы.

**Источник ответа менять нельзя** (решение владельца 20.08): официальный Yandex
Search API и `answerBox` Google. Блок «Алисы» и Google AI Overview законным API
не отдаются, а скрейпящих посредников (SerpApi, DataForSEO) мы не берём.

**Ни один офлайн-контур эту ветку не исполняет:** ни у золотого кейса, ни у
`report-72` нет нейро-ответа, и пересборка обоих эталонов не сдвинула ни одного
слова. Правило держат юниты; на настоящем ответе прогона 20.08 чистка проверена
отдельно — 1676 знаков разметки превратились в 1574 знака связного текста, без
единой звёздочки и сноски.

### Трасса ссылок: потеря и учёт — разные состояния

`link-usage-trace.json` отвечает на вопрос «что модель сказала о ссылке и что из
этого дошло до отчёта». Состояний пять, и **потеря — только последнее**:

| Состояние | Что значит |
|---|---|
| `цитата со страницы` | напечатана цитата с прочитанной страницы |
| `заголовок из выдачи` | напечатан заголовок |
| `без цитаты` | адрес виден в тексте страницы, цитаты нет |
| `в составе страницы` | своих слов в отчёте нет, но страница стоит на этом наблюдении |
| `не дошла` | ни слов, ни ссылки в основаниях страницы |

Четвёртое состояние заведено потому, что трасса ищет материал **по словам** —
по началу цитаты, по заголовку, по адресу, — а материал, свёрнутый в сюжет,
входит в отчёт числом публикаций и доменом и ни одного из этих следов не
оставляет. На живом прогоне 20.08 из-за этого сводка объявила «не дошло — 42»
при **нуле** настоящих потерь: все 42 ссылки стояли в `evidenceRefs` страниц
резюме и региональных сводок. Ошибка дорогая — она заставляет искать
несуществующий дефект, и на разборе на неё уже попались.

Признак нового состояния — `evidenceRefs` слайда, а не совпадение по тексту:
список оснований страницы точен и не зависит от того, как сложился её текст.

Тот же прогон 20.08 после правки: «цитата со страницы — 23, заголовок — 15, без
цитаты — 0, в составе страницы — 42, не дошло — 0».

### Повисшее двоеточие: снимается обещание, а не текст

Строка вида «…В выборке присутствует материал «X» (Y):» получает двоеточие как
ввод к списку, который карточка с ограниченной высотой отбрасывает. Уборка
(`_close_dangling_lead_in`, `renderer/orion_golden_render/common.py`) снимает
обещание: чистый ввод («Найдены публикации:») выбрасывается целиком, строка с
содержанием кончается точкой.

**Признак — содержание строки, а не её длина.** Прежний порог в 80 знаков делил
один дефект надвое: «Что делать: Проверить статусы дел, …направлениям:»
сохранялся, а «Что делать: Проверить следующее:» исчезал целиком, унося текст
аналитика. Так же терялась короткая строка с цитатой и адресом. Содержанием
считается цитата, адрес, число или собственный ярлык с текстом после него — во
всех четырёх случаях строка уже что-то сказала.

Контур это ловит `renderer/smoke_text_measurement.py`; на эталоне `report-72`
таких строк нет, и правка его страниц не меняет.

### Предупреждения прогона и предупреждения задания — разные вещи

`job.warnings` копит два рода токенов, и путать их нельзя. Одни описывают
**задание** и живут до тех пор, пока причина не устранена
(`compliance-hits-pending-review:*`, `arsenkin-*`). Другие описывают **прогон**:
клип на четвёртой странице, откат стадии GPT, число пустых страниц.

Второй род перечислен в `REFRESHED_WARNING_FAMILIES`
(`services/report-quality-summary.ts`) и на границе «состояние задания ↔ итог
прогона» снимается **целиком**, а не по одному: этим занимается
`refreshRunWarnings`, и зовёт его `warningsSurvivingSuccessfulPrepare`. Пока
снятие происходило только при появлении нового токена того же семейства,
починенный прогон оставлял клипы висеть навсегда — новых-то нет, — и оператор
читал завершённый отчёт как сломанный (пункт AV).

**`mergeJobWarnings` этого не делает и не должен.** Он соединяет два источника
**одного** прогона (потери подготовки и сводку качества), и свежие токены ворот
приезжают туда первым аргументом — снятие семейств стёрло бы их.

**Ворота телеметрии — единственное многотокенное семейство:** клип бывает на
нескольких страницах сразу. Поэтому замена «по одному», которую делает
`mergeJobWarnings` для однотокенных семейств, для них не годится — от семейства
осталась бы последняя страница. Это и есть та «очевидная правка», которую пункт
AV назвал неверной.

### Страница изображений считает всё, что на ней нашли

Строка, которой нет в индексе доказательств страницы, домена и ссылки среди
доказательств не получает: сослаться не на что, а домен, добытый другим
способом (хост CDN у строки без адреса страницы), обрушил бы ворота области.

**Но в число она входит.** Прежде фильтр `if (!e) return []` отбрасывал такую
строку целиком, и она не оставляла следа нигде — ни в «Из N строк этой
страницы», ни в перечне причин, ни в негативе, ни в предупреждениях (пункт BK).
Правило проекта требует, чтобы потеря была слышна, и «Из 4 строк» вместо «Из 3»
— самый дешёвый способ её услышать: отдельного канала предупреждений у
построителей фрагментов нет, а заводить его ради ветки, достижимость которой на
живых данных не доказана, дороже пользы.

Причина у такой строки — общая формулировка «причина не установлена»:
предъявить настоящую нечем, самой строки в доказательствах страницы нет.

**Сигнал о негативе не платит за длину.** Строка «что обнаружено» собирается
вариантами, и за бюджет платят по очереди: сначала перечень источников, потом
перечисление причин, потом домены при самой фразе о негативе. Сама фраза «среди
них N с негативным признаком» остаётся всегда. Прежде перечисление причин
ничем не ограничивалось и стояло **до** фразы: свойство держалось совпадением
длин — замер ревью дал 388 знаков из 400, — и на трёх негативных строках с
доменами под сорок знаков плюс семи прочих сигнал терялся (пункт BL).
Проверяется свойством, а не экземпляром: тест гоняет весь диапазон числа
непоказанных строк.

### Объяснение — на каждую рамку

Фраза «Почему выделено» пишется по одной на **выделенный результат**, а не на
пару «находка + домен». Прежний ключ дедупликации был `находка|домен`, а
сопоставление строки с находкой идёт **в том числе по домену**
(`findingForVisibleRow`, `specificity = 1` при попадании в `f.sourceDomains`), —
поэтому для двух видимых строк одного источника совпадение ключа было правилом,
а не совпадением. Выходило три рамки на картинке и два объяснения под ней, и
схлопнутая строка не попадала даже на слайд-продолжение (пункт BO).

Осталась одна защита — от строки, попавшей в видимые дважды: это уже не два
выделенных результата, а один.

Цена видна на золотом кейсе: страница «ОАЭ — снимок выдачи: почему выделено»
разошлась на два продолжения, и отчёт вырос с 52 страниц до 53. Две строки

### Пробуждение конвейера принадлежит принятой работе

`rebuildUnifiedReport` и `recoverUnifiedOrionCollectionJob` берут лизу и держат
работу в `try/finally`. В `finally` остаётся **только снятие лизы**;
`requeueStepsForRebuild` / `requeueResumeStep` вызываются после `try/finally`,
куда отказ не доходит по устройству языка, а не по флагу.

Пока пробуждение стояло в `finally`, шаги перепоставлялись и на отказе **после**
взятия лизы: повторная проверка годности, пропавший артефакт, любой сбой записи.
Ранние отказы (негодность, занятая лиза) брошены до `try` — поэтому дефект и не
был виден. А `requeueStepsForRebuild` не только будит: она ставит строкам
`PENDING`, обнуляет `attempts` и стирает `lastError`/`lastErrorCode`, то есть
уносит память о том, кто упал.

Что пробуждение принадлежит успеху, видно и по идемпотентным ранним возвратам
восстановления: они всегда будили себя сами, отдельной строкой.

### Конечная стадия джобы даёт шагу один ответ

`outcomeForStoppedJob` (`workflow/unified-step-handlers.ts`) — единственное место,
где сказано, что конечная стадия значит для шага: `CANCELLED` — пропуск,
`FAILED_TERMINAL` — отказ с кодом и текстом джобы, `REPORT_READY`
и `COMPLETED_PARTIAL` — «сделано». Её зовут оба места: и проверка перед вызовом
тика, и `outcomeFromJob` после него.

Раньше отвечали двое, и до-вызовный отвечал неправдой: любая конечная стадия
давала `done`. Цена — не косметика. `completeStep` на `DONE` будит следующий шаг,
поэтому один неверный `done` идёт каскадом до конца конвейера; все строки `DONE`
дают `deriveJobStage` → `REPORT_READY` при джобе в `FAILED_TERMINAL`
(`workflow-stage-drift` в логе), а `planResumeFromSteps` отвечает `completed`
**навсегда**: восстановление отдаёт `JOB_ALREADY_COMPLETED`, и кнопки
«Возобновить» у оператора больше нет. Так на прогоне 19.08 у владельца работала
ровно одна кнопка — не потому, что так задумано.

Платный тик на остановленном прогоне по-прежнему не запускается: ради этого
короткое замыкание и заводили. Изменился только вердикт — шаг, который не
работал, сделанным не называется.

`cancelRequested` в общую функцию не входит намеренно. Перед вызовом тика его
спрашивать нельзя: в `CANCELLED` джобу переводит сам тик, и пропуск шага до
вызова оставил бы отмену невыполненной. В `outcomeFromJob` он остаётся отдельной
строкой — это признак джобы, а не стадия.

### Адрес источника может содержать пробел

`parseClientAddress` раскодирует путь (`decodeURIComponent`), поэтому `%20` в ссылке
становится пробелом в напечатанном адресе: `interfax.ru/tags/Татьяна Ким`. Это обычная
форма, а не редкость — так выглядит любая ссылка тега или поискового запроса.

Отсюда правило для `SOURCE_ATTRIBUTION_SOURCE`: **хвост адреса описывается закрывающей
скобкой, а не отсутствием пробелов.** Внутри `(…)` живёт что угодно, кроме скобок, плюс один
уровень вложенных — `…Person:Kim_Tatyana_Vladimirovna_(formerly_Bakalchuk)` встречается
по-настоящему. Голая форма (`— источник bizfiles.org`, без скобок) хвоста не получает:
иначе разбор дотянулся бы до первой попавшейся скобки дальше по тексту и съел бы чужое
предложение.

Ветвей у выражения две, поэтому индекс группы зависит от формы печати. Домен читается
`sourceHostFromMatch`, а не `m[1]`: прямое чтение индекса молча теряет голую форму.

Цена ошибки измерена на живом отчёте 21.08: совпадение обрывалось на хосте, а
`reflowThemeBullet` пересобирает буллет **из совпадений** — хвост адреса вместе с
закрывающей скобкой исчезал молча. Клиент читал `— источник (interfax.ru «Глава…`: минус 18
знаков и незакрытая скобка на странице, которую показывают банку. Ни один эталон этого не
ловил: ни у `report-72`, ни у золотого кейса нет адресов с пробелом.

### Пересборка буллета ничего не выбрасывает

`reflowThemeBullet` собирает буллет из совпадений «цитата + источник». Всё, что стоит между
ними, живёт ровно до тех пор, пока его кто-нибудь не назовёт: пока названа была одна строка
«О чём: …», остальное пропадало молча. Специальной ветки больше нет — правило одно на любой
кусок:

- кусок с буквой или цифрой становится своей строкой;
- кусок из одних знаков препинания приклеивается к **предыдущей** строке: точка принадлежит
  предложению, которое закончилось, а не тому, которое начинается. Без этого клиент читал
  `(rusprofile.ru/ip/323774600121451) . «Партнеры…` — цитата с вложенными кавычками не
  подходит под `«[^»]{8,}»`, остаток уезжает в хвост, и точка начинала собой новую строку.

Молча пропавшее клиентское предложение не поднимает ни одних ворот — потому правило и
записано здесь, а не оставлено на внимательность.

### Проверка темы говорит о теме

`recommendedChecks` темы попадают в общий список «Следующие проверки» наравне с глобальными
шагами, а `collapseRecommendations` склеивает пункты **по форме предложения** — с
подстановкой перечня в кавычки. Поэтому строка, одинаковая у всех тем, склейкой не
собирается: у неё нет кавычек, по которым перечислять, и она просто стоит в списке рядом с
глобальной строкой о том же самом.

Так на живом отчёте 21.08 клиент читал подряд «2) Подготовить согласованную позицию для KYC
и партнёрских запросов» и «4) Подготовить единый пакет документов для KYC и партнёрских
запросов» — один вопрос, два ответа.

Правило: **в проверках темы остаётся только то, что называет тему.** Общее для отчёта
действие живёт в глобальном хвосте `nextSteps` и названо там один раз. Закреплено
`tests/unit/client-summary-pack.test.ts` — обеими сторонами: подготовка к KYC встречается
ровно однажды, и каждая проверка темы содержит её название.

### Заголовок называет то, что перечисляет

Итоговая оценка перечисляет **сюжеты прочитанных страниц**, когда они есть, и рубрики
словаря, когда чтения не было. Это разные сущности с разными счётчиками: плитка «Тем риска»
на той же странице считает строки матрицы, то есть рубрики.

Пока обе ветви шли под словом «Основные основания», читатель живого отчёта 21.08 видел
плитку «3 Темы риска» и тут же четыре названия — два счёта одного, на первый взгляд, вопроса.
Оба числа при этом верны, менять было нечего: развести надо слова.

- сюжеты → «Основные сюжеты в выдаче: …»;
- рубрики словаря → «Основные основания: …» (та же сущность, что строки матрицы).

Решение владельца 21.08. Закреплено с двух сторон:
`tests/unit/summary-of-plots-is-worded-verbatim.test.ts` (ветка сюжетов, дословно) и
`tests/unit/client-summary-pack.test.ts` (ветка словаря). **Ветку сюжетов не исполняет ни
один эталон** — ни у золотого кейса, ни у `report-72` нет решений по ссылкам, — поэтому
единственный её сторож это дословный юнит.

### Строка матрицы с неподтверждённой принадлежностью

Тема словаря у неподтверждённой находки та же, что у подтверждённой, поэтому в матрице
выходили две карточки с одинаковым заголовком и разными вердиктами. Читатель просматривает
заголовки, а не чипы уровня, и видел тему дважды без объяснения.

Заголовок теперь называет статус: `«<тема> — принадлежность не подтверждена»`. Сказан он
при этом **один раз в теле**: оговорка сокращена до следствия — «До уточнения идентификации
материал не включён в итог „об этом лице"». Заголовок, чип уровня и оговорка перестали
говорить одно и то же трижды.

Суффикс получают только тематические строки. Синтетический агрегат вероятных материалов
(`RISK_MATRIX_LIKELY_AGGREGATE_ID`) его не получает: его собственная тема — «Материалы с
вероятной принадлежностью» — ни с чем не совпадает и статус называет сама. Условие одно на
оба места, `isUnconfirmedRow`.

Решение владельца 21.08. **У `report-72` строк с неподтверждённой принадлежностью нет
вовсе** (шесть подтверждённых), поэтому эталон об этой правке молчит — держит её юнит
`tests/unit/risk-matrix-likely-row-names-itself.test.ts`.

### Знаменатель доли негатива объясняется там же, где печатается

Знаменатель — **прочитанные страницы региона минус признанные материалами о других людях**
(`readShareDenominator`). Страница региона это говорит словами: «Страницы о других людях (N)
в долю не входят». Строка резюме печатала те же числа молча.

На живом отчёте 21.08 читатель складывал «21 из 51» и «15 из 28», получал 79 при 80
прочитанных и не находил объяснения. Числа были верны — необъяснённой была разница, а
необъяснённое число в отчёте для банка читается как ошибка (пункт CS).

Теперь обе строки объясняют исключение одной и той же фразой, и она появляется только тогда,
когда исключать было что. **Ни один эталон эту строку не содержит вовсе** — ни у `report-72`,
ни у золотого кейса нет чтения ссылок, — держит её
`tests/unit/executive-prints-read-share-line.test.ts`.

### Форма ответа Arsenkin `/check`

Документация тел ответа не приводит, поэтому контракт записывается **по наблюдению**.
Известны два тела, оба с живых прогонов:

```json
{"code":"TASK_STATUS","status":"process","progress":5,"msg":"Статус состояния задачи!"}
{"code":"TASK_STATUS","status":"finish","progress":100,"msg":"Статус состояния задачи!"}
```

Они лежат фикстурами `check-pending.json` и `check-done.json`. **Кода, который бы их читал,
нет — это документация**, и до шага 0026 вторая из них содержала выдуманную форму
`{"status":"done","progress":100}`.

`finish` распознаётся началом слова (`unfinished` под правило не попадает) и **до** запасного
пути `progress >= 100`. Пока готовность держалась только на `progress`, тело без этого поля
читалось бы как «ещё считается» до конца бюджета ожидания.

**Форма отказа не наблюдалась ни разу и не выдумана.** Незнакомое тело читается как
`RUNNING`: ждать безопаснее, чем считать задачу проваленной, а ожидание ограничено
`maxWaitMs` шага, то есть временем, а не числом опросов. Каждое такое тело печатается строкой
`arsenkin_check_shape_unknown` — это и есть способ однажды его записать (пункт CT бэклога).

### Пересборка, которая уже провалилась так же, не предлагается

`paidRecollectionRequired` возвращает `false`, пока доступна пересборка, — правило верное:
платить за то, что уже собрано, предлагать нельзя. Но пересборка воспроизводит отказ, причина
которого записана **на сборе**: она читает те же строки из базы и падает тем же кодом.
Счётчика попыток у неё нет, поэтому цикл замыкался — провал, снова доступна, снова провал, —
и платной кнопки оператор не видел никогда. Владелец упёрся в это 20.08.

Признак лежит на самой джобе и второго ответа не требует: неудачная попытка оставляет
`report-rebuild-failed:<код>`, а причину прогона возвращает на место
`restoreStateAfterFailedRebuild`. Совпали коды — пересборка повторит отказ, и предлагать её
нечестно; блокер называется `REBUILD_ALREADY_FAILED`.

Закрывает пересборку только **та же** причина. Отказ мог быть случайным — сорванная запись,
недоступный рендерер, — и на такой её не запирают.

**Обратно отметка не снимается** (пункт CU): оператор, изменивший вход, который пересборка
читает, остаётся с платной кнопкой. Разомкнуть цикл важнее, чем сохранить редкий бесплатный
повтор, но об ограничении надо помнить.

### Пауза прогона

Отмена значит **паузу** (решение владельца 21.08): приостановленный прогон и возобновляется с
места остановки, и позволяет собрать отчёт из уже собранного. Оплаченный сбор не теряется ни
в одном из двух направлений.

Признак `cancelRequested` выставляет ровно одна ручка — `POST .../unified-collection/pause`.
До этого его во всём коде только инициализировали `false` и проверяли: оркестратор его
honors, хранилище переживает перезапуск, а выставить было некому.

Ручка стадию не трогает: в `CANCELLED` прогон переводит ближайший тик — тот же, который
двигает работу. Так пауза не обрывает шаг посередине и не спорит с лизой. Годность считается
одной функцией и для статуса, и для ручки: интерфейс не показывает кнопку, которую сервер
откажется исполнить.

**Шаг приостановленного прогона получает отказ (`RUN_PAUSED`), а не пропуск.** Пропуск
считается улаженным состоянием: `completeStep` будит следующий шаг, тот тоже пропускается, и
каскад `SKIPPED` до конца конвейера давал `planResumeFromSteps` ответ `completed` —
возобновить паузу было бы нечем **никогда**, а собранное осталось бы оплаченным и
недоступным. Из шести состояний шага отказ единственный умеет и остановить конвейер
(`nextRunnableStep` возвращает `null` на `FAILED`), и сохранить место остановки. Слово
`FAILED` внутреннее и клиенту не печатается.

`CANCELLED` входит в улаженные стадии пересборки и не блокирует восстановление, а
возобновление **снимает** признак: иначе первый же тик остановил бы прогон снова.

**Дрейфа стадии у паузы нет** — `detectStageDrift` исключает `CANCELLED` списком
`RESULT_STAGES`. Пункт CO бэклога утверждал обратное и был неверен; опасность была в каскаде
пропусков, описанном выше.

### Латинское имя ищется латиницей и в русском контуре

У субъекта с латинским именем и без кириллических алиасов `queriesRu` оставался пуст, и
заявка уходила с единственной строкой `"subject"` — **платный `check-top` по английскому
слову**. Блокер `empty-queries-ru` не спасает: план блокируется только когда пусты **оба**
набора.

Решение владельца 19.08: искать латинское имя. Русскоязычные источники часто пишут имя
латиницей, риск нулевой — ищем то, что точно существует. Отвергнуты транслитерация в
кириллицу (неоднозначна, можно заплатить за написание, которым его никто не называет) и отказ
от русского сбора вовсе (теряет русскоязычное покрытие целиком).

Порядок частей при этом не трогается — правило модуля остаётся: переставлять можно только
собственное ФИО, чей порядок мы знаем. «Mohammed bin Rashid Al Maktoum» дало бы «bin
Mohammed», то есть выдуманный запрос.

**Умолчания `?? "subject"` в планировщике больше нет.** Если русского запроса нет, берётся
запрос контура ОАЭ — это настоящее имя; если нет ни одного, заявок не строится вовсе. Пустой
план — отсутствие заявок, а не заявка с выдуманной строкой.

### Длинная форма имени не теряет токенов

`permutationsOfName` собирает три строки: полное ФИО, «Имя Отчество Фамилия» и короткое «Имя
Фамилия». Длинная форма собиралась из ровно трёх частей (`parts[1] parts[2] parts[0]`), и у
имени из четырёх частей — «Иванов Иван Иванович Оглы» — второй строкой уходило «Иван Иванович
Иванов»: имя **другого человека**, «Оглы» молча отбрасывалось. Вход редкий, но запрос платный.

Теперь фамилия переносится в конец, а всё остальное идёт своим порядком:
`${parts.slice(1).join(" ")} ${parts[0]}`. Для трёхсловного ФИО это ровно прежняя строка.

Короткая форма «Имя Фамилия» рядом остаётся: это законное сокращение, а не огрызок — так
человек и печатает.
