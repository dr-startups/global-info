# ADR-0001. Сначала чинится приёмочный контур, потом продукт

- **Статус:** принято и выполнено
- **Шаг:** 1 из 9
- **Связано с:** все последующие ADR

## Контекст

Требование к переработке сформулировано так: «весь код должен работать сразу, у
нас нет времени на допущение и исправление ошибок после ручного тестирования».
Это требование нельзя выполнить решением о продукте — только приёмочным
контуром, который ловит дефект до того, как его увидит человек.

> **Поправка к первой редакции.** В ней утверждалось, что `npm run ci:smokes`
> завершается кодом 0, ничего не проверив. Это была ошибка измерения: команда
> запускалась через `| tail`, а код возврата конвейера — это код последней
> команды, то есть `tail`. Проверка без конвейера показывает `exit 1`. Гейт
> падал корректно, и претензия «маскирует провал» снята. Настоящие дефекты
> оказались другими и описаны ниже.

Измерено на `main` (2ffcb3f):

- **Офлайновый контур требует базы.** `scripts/smoke-unified-orion-collection.ts`
  через `scripts/lib/ensure-smoke-case.ts` делал `prisma.case.upsert()`. Без
  Postgres смок падает целиком: `# pass 0, # cancelled 10`.
- **В CI базы нет.** `.github/workflows/ci.yml` не поднимает Postgres и называет
  шаг «Офлайн-смоки». Значит, шаг не мог проходить ни в CI, ни на чистой машине —
  проходил только там, где база осталась от разработчика.
- **Цепочка `&&` скрывает картину.** Смоки шли одной строкой в package.json:
  падение третьего означало, что четвёртый–восьмой не запускались вовсе.
- **Пропуск виден не всегда.** Сводку пропусков `smoke-orion-deck-sections`
  печатал под условием `if (!assetsAvailable)`. Сверка числа страниц
  пропускается по другой причине — нет отрендеренных артефактов — и об этом не
  сообщалось нигде.
- **Смоки не проверялись типами.** `tsconfig.json` исключал `scripts`, и в
  программу попадали лишь четыре файла — те, что импортируют тесты. Ошибка типов
  в самом гейте всплывала бы на запуске.
- **Нулевой код возврата ничего не доказывает.** Смок, у которого все проверки
  пропущены, завершается нулём и выглядит зелёным. Проверено: `it.skip` на всех
  проверках даёт `# pass 0` и `exit 0`.

Все восемь последующих шагов меняют текст отчёта, порядок сборки, состав
провайдеров, вёрстку и поведение UI. Принимать их по гейту, который не запускается
на чистой машине и не отличает пустой прогон от успешного, нельзя.

## Решение

Привести приёмочный контур в состояние, при котором зелёный результат означает
проверенный продукт. Конкретно:

1. **Офлайновый смок не ходит в базу.** Хранилище прогонов переводится в
   файловый режим — он для этого и был оставлен (`UNIFIED_COLLECTION_JOB_STORE`,
   комментарий в `unified-collection-job-store.ts`). Кейс-заглушка в базе
   становится не нужна, `scripts/lib/ensure-smoke-case.ts` удаляется. Сам смок
   проверяет свой режим: вернётся `db` — проверка покраснеет здесь, а не в CI.
2. **Смоки запускает раннер, а не цепочка `&&`** (`scripts/run-smokes.ts`).
   Выполняются все смоки; провалом считается ненулевой код возврата, отменённые
   подтесты, проваленные подтесты и **прогон без единой выполненной проверки**.
   Правила исхода вынесены в чистую функцию и закреплены юнит-тестом: раннер сам
   стал контуром, и его ошибка покрасила бы в зелёный весь проект.
3. **Разделение на две цели.** `npm run ci` — то, что обязано проходить на любой
   машине без сети, без базы и без рендерера. `npm run ci:full` — плюс смоки,
   которым нужны Python-пакеты рендерера и Postgres.
4. **Явный список пропущенного.** Пропуск объявляется строкой `# SKIP <что и
   почему>`; раннер сводит их в один список в конце прогона и понимает штатный
   маркер node, если смок ничего не объявил. Условие
   `if (!assetsAvailable)` в `smoke-orion-deck-sections` снимается.
5. **Гейт проверяет собственный код.** `scripts` возвращается в `tsconfig.json`:
   включение обходится в ноль ошибок, а смоки перестают быть слепой зоной.
6. **Золотой кейс как регрессия текста.** Рядом с числовым эталоном заводится
   `fixtures/golden-case/client-text.baseline.json` — снимок клиентского текста
   собранной деки. Числовой эталон переживает полную переписку формулировок
   незамеченным; текстовый показывает каждое изменённое предложение и сверяется
   на детерминизм наравне со счётчиками.

## Последствия

- Один шаг работы не приносит пользователю ничего видимого. Это цена того, что
  остальные восемь можно принимать по результату проверки, а не по показу с
  экрана.
- Офлайновый смок проверяет оркестрацию поверх файлового хранилища. Путь через
  базу остаётся за юнит-тестами (Prisma там подменён алиасом vitest) и за
  `ci:full`.
- Эталон клиентского текста весит ~105 КБ и будет заметно меняться на шагах
  0002–0004. Это его назначение: правка эталона — часть ревью текста.

## Глобальное тестирование после шага

Выполнено:

- `npm run ci` зелёный **с заведомо недоступной базой**
  (`DATABASE_URL=…:1/none`): 8 смоков, 75 проверок, 0 отменённых.
- Гейт способен краснеть — проверены все три исхода, каждый на временной правке
  с последующим откатом:
  | Сценарий | Итог |
  |---|---|
  | провальная проверка в смоке | `exit 1`, остальные 7 смоков всё равно отработали |
  | смок вернули в режим `db` | `exit 1`, назван виновный смок |
  | все проверки смока пропущены (`exit 0`, `# pass 0`) | `exit 1` — «не выполнено ни одной проверки» |
- Сводка пропусков печатается с причинами: сверка числа страниц — нет
  отрендеренных артефактов; отрисовка шаблонов — не установлен python-pptx.
- Эталон клиентского текста ловит правку одной формулировки и показывает её
  как `было → стало` (проверено на `methodologyNote`).
- Два прогона золотого кейса дают идентичный текст (детерминизм).
- `npm run typecheck` покрывает `scripts` — 0 ошибок; `npm test` — 94 файла.

Не выполнено и вынесено дальше:

- `npm run ci:full` в docker compose: цель заведена, но локально нет
  Python-пакетов рендерера (`pptx`) и поднятой базы. Проверяется там, где
  зависимости есть.
