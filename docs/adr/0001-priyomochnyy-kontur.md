# ADR-0001. Сначала чинится приёмочный контур, потом продукт

- **Статус:** предложено
- **Шаг:** 1 из 9
- **Связано с:** все последующие ADR

## Контекст

Требование к переработке сформулировано так: «весь код должен работать сразу, у
нас нет времени на допущение и исправление ошибок после ручного тестирования».
Это требование нельзя выполнить решением о продукте — только приёмочным
контуром, который ловит дефект до того, как его увидит человек.

Контур сейчас не работает. Измерено на текущем `main`:

- `npm run ci:smokes` завершается **кодом 0**, при этом в отчёте
  `# pass 0, # fail 0, # cancelled 10`. Ни одна проверка не выполнилась.
- Причина — падение на `prisma.case.upsert()` в `scripts/lib/ensure-smoke-case.ts`:
  `The column isFixture does not exist in the current database`. Смоки, заявленные
  как офлайновые, требуют мигрированной базы.
- Node test runner в таком сценарии отдаёт `cancelled`, а не `fail`, и общий код
  выхода остаётся нулевым. Провал маскируется.

То есть из трёх заявленных гейтов (`typecheck`, `test`, `ci:smokes`) реально
работают два. Третий рапортует успех, ничего не проверив. Это худший вид
проверки: она приучает не смотреть на свой результат — ровно тот дефект, который
в этом же репозитории уже описан для смока `rendered artifacts parity`
(`scripts/smoke-orion-deck-sections.ts:565–581`), где отсутствие артефактов
честно помечается как «проверка не выполнялась», а не как успех.

Все восемь последующих шагов меняют текст отчёта, порядок сборки, состав
провайдеров, вёрстку и поведение UI. Проверять их нечем, пока гейт зелёный по
построению.

## Решение

Привести приёмочный контур в состояние, при котором зелёный результат означает
проверенный продукт. Конкретно:

1. **Ненулевой код выхода при `cancelled`.** Обёртка запуска смоков считает
   `cancelled` провалом. Гейт не имеет права рапортовать успех, не выполнив ни
   одной проверки.
2. **Офлайновые смоки не ходят в базу.** `ensure-smoke-case` и всё, что тянет
   Prisma, выносится из офлайнового набора. Смок, которому нужна база,
   переезжает в отдельную цель `npm run smoke:db:*` и в CI поднимается вместе с
   Postgres.
3. **Разделение на две цели.** `npm run ci` — то, что обязано проходить на любой
   машине без сети и без базы. `npm run ci:full` — плюс база и рендерер.
4. **Явный список пропущенного.** Любой смок, пропущенный из-за окружения,
   печатается списком в конце прогона. Молчаливый пропуск запрещён.
5. **Золотой кейс как регрессия текста.** `fixtures/golden-case/` уже даёт
   офлайновый прогон; на нём фиксируется эталон клиентского текста, чтобы шаги
   0002–0004 меняли формулировки осознанно, а не случайно.

## Последствия

- Один шаг работы не приносит пользователю ничего видимого. Это цена того, что
  остальные восемь можно принимать по результату проверки, а не по показу с
  экрана.
- Часть смоков окажется красной сразу после починки — это и есть настоящее
  текущее состояние. Разбор этих падений входит в шаг.
- CI станет дольше: `ci:full` поднимает Postgres и рендерер.

## Глобальное тестирование после шага

- `npm run ci` зелёный на чистой машине без сети и без базы.
- Искусственно сломанный смок (временная правка) делает `npm run ci` красным —
  проверяется, что гейт вообще способен падать.
- `npm run ci:full` зелёный в docker compose.
- В выводе прогона есть раздел «пропущено» с причиной по каждой позиции.
