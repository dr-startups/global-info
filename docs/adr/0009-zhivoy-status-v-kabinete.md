# ADR-0009. Живой статус в кабинете

- **Статус:** предложено
- **Шаг:** 9 из 9
- **Связано с:** [0005](0005-arsenkin-otkaz-ot-vtoroy-stadii.md)

## Контекст

Жалоба: пользователь обязан обновлять страницу, чтобы увидеть актуальный статус.
Дизайн менять не нужно — нужно, чтобы кабинет перестал врать о состоянии.

Что измерено:

- **Из 22 клиентских компонентов опрашивают сервер два.** `AgentsTab.tsx`
  (раз в 3 секунды) и `ArsenkinToolsPanel.tsx`. Остальные двадцать делятся на
  два случая, и оба одинаково слепы к изменениям: одни запрашивают данные
  ровно один раз в `useEffect` при монтировании (`CaseDetailView`,
  `AuditSummaryTab`, `EvidenceQualityTab`, `ComplianceTab`,
  `ReportPreviewPanel`), другие вообще не ходят на сервер и живут на пропсах
  сверху (`SurfacesTab`, `ReportQualityPanel`, `CaseHeader`,
  `DigitalProfileCasesTable`) — то есть зависят от той же единственной
  загрузки.
- **`CaseDetailView` грузит всё разом и целиком.** `loadAll()` вызывается один
  раз (`CaseDetailView.tsx:556–558`) и начинается со
  `setState({ kind: "loading" })`. Даже если сейчас добавить опрос, вся карточка
  будет мигать спиннером на каждом обновлении.
- **Стриминга нет нигде:** ни `EventSource`, ни `text/event-stream`, ни
  `ReadableStream`, ни `WebSocket` во всём `src`.
- **Бэкенд при этом уже умеет отвечать.**
  `GET /api/digital-profile/cases/[id]/unified-collection` возвращает `stage`,
  `status`, `progress`. То есть требование «бекенд может отдавать информацию по
  требованию фронтенда» выполнено — фронтенд просто не спрашивает второй раз.

Отдельно стоит записанное в `ENGINEERING.md:383` правило продукта:
**«Пользователь не должен дожимать прогон руками. Если человеку предлагают
кнопку — значит, мы чего-то не доделали.»** Кнопка F5 — тот же случай.

После [0005](0005-arsenkin-otkaz-ot-vtoroy-stadii.md) появляется состояние «отчёт готов частично и
дополняется» — показывать его без живого статуса невозможно.

## Решение

Дизайн не трогаем. Меняем то, откуда компоненты берут состояние.

1. **Один агрегат состояния кейса.** Появляется эндпоинт, отвечающий одним
   объектом на вопрос «что сейчас с кейсом»: стадия, прогресс, готовность
   отчёта, что собрано, чего ждём, что сломалось. Сейчас этот ответ собирается
   пятью запросами из пяти компонентов — классический случай «один вопрос, три
   ответа», от которого этот проект уже избавлялся.
2. **Дешёвая проверка изменений.** Ответ снабжается версией состояния (ETag или
   `updatedAt`); неизменившееся состояние отдаётся как `304`. Опрос раз в
   несколько секунд не должен стоить как полная выгрузка кейса.
3. **Опрос — в одном месте.** Компоненты перестают ходить за статусом каждый
   сам. Один провайдер держит подписку и раздаёт состояние вниз. Интервал
   адаптивный: чаще, пока прогон идёт, редко — когда терминальное состояние.
   Опрос останавливается на скрытой вкладке (`visibilitychange`) — иначе
   открытая неделю вкладка бьёт по серверу и по бюджету провайдеров.
4. **Обновление без мигания.** `loadAll` разделяется: первичная загрузка
   показывает спиннер, последующие обновления меняют данные на месте. Это
   обязательное условие — иначе живой статус будет раздражать сильнее, чем F5.
5. **Опрос, а не стриминг.** SSE рассматривался и отклонён: инфраструктуры нет,
   воркер живёт внутри приложения, а поверх Railway долгоживущие соединения
   дают отдельный класс проблем. Опрос с `304` решает задачу при несопоставимо
   меньшем риске. Решение пересматривается, если частота опроса станет узким
   местом.
6. **Показывать ожидание честно.** Пока идёт медленный источник, интерфейс
   называет, чего именно ждём и что уже готово, — вместо неподвижного
   «выполняется». Данные для этого в агрегате уже есть.

## Последствия

- Нагрузка на API вырастет: активная вкладка = запрос раз в несколько секунд.
  Снимается `304` и остановкой на скрытой вкладке.
- Агрегат становится зависимостью почти всех вкладок: его поломка заметна
  везде. Он должен деградировать частями, а не отказывать целиком.
- Два существующих опроса (`AgentsTab`, `ArsenkinToolsPanel`) переводятся на
  общий механизм, чтобы не осталось трёх разных способов узнать одно и то же.

## Глобальное тестирование после шага

- `npm run ci` зелёный.
- Сценарий без единого F5: запуск прогона → кабинет сам показывает смену
  стадий → появление готового отчёта.
- Неизменившееся состояние отдаёт `304`; тело не пересылается.
- Скрытая вкладка не шлёт запросов; возврат на вкладку немедленно обновляет.
- Обновление статуса не сбрасывает открытую вкладку, скролл и введённые данные.
- Частичный отчёт из [0005](0005-arsenkin-otkaz-ot-vtoroy-stadii.md) отображается как «готово частично» с
  перечнем того, чего ждём.
