# Шаг 0012. Выключенный инструмент не выдаётся за пустую поверхность (AL, находка H6)

## Задача и границы

Страница «Россия — AI-ответы поисковых систем» живого прогона 76 (PDF стр. 32) печатает:
«Ответы ИИ-поиска (AI Overview, нейро-ответы) по запросам о субъекте **проверены**: материалов
нет — это результат проверки». При этом инструменты `ai-serp` и `check-h`/`indexation` в состав
прогона не входили: агенты `ARSENKIN_AI_SEARCH_REAL` и `ARSENKIN_URL_AUDIT_REAL` получили
`disabled-by-tools`, ни одной задачи не создали, а Яндекс на запрос о субъекте отдаёт развёрнутый
быстрый ответ Алисы со санкционной строкой (скриншот владельца). Нейро-ответы никто не спрашивал —
отчёт утверждает, что проверил.

**В границах:**

1. Развести исходы у источника: выключенный инструмент получает собственный терминальный исход,
   не `EMPTY_VALID`, и этот факт доезжает по всей трассе коллектор → покрытие → пустое состояние
   страницы → клиентский текст.
2. Клиентский текст всех состояний AI-поверхности, по образцу комплаенс-страниц шага F:
   «не проверялось + причина», «проверено, пусто», «ответы есть» — плюс честное частичное
   состояние, когда по одному движку проверено, а по другому нет (реальный случай прогона 76).
3. Аудит остальных поверхностей Arsenkin: где ещё сегодня печатается «проверено» при
   невыполненной проверке (результат аудита — в «Контексте», правки — только по AI-поверхности
   и счётчикам покрытия).
4. Ответ на вопрос владельца: можно ли получить ответ Алисы легально — фактами, с источниками
   (см. «Контекст», раздел «Легальные пути»; включение любого из путей — **отдельный шаг** по
   решению владельца, в AL не входит).

**Вне границ (по одной строке, почему):**

- Включение сбора AI-ответов (Arsenkin `ai-serp`, генеративный ответ Yandex Search API) — трата
  денег и отдельный красный тест; только по решению владельца, отдельным шагом.
- Заголовок UAE-слота «панель знаний и AI Overview» (`p31_uae_knowledge`), показывающего только
  панель знаний, — мелкая неточность заголовка слота, не ложное утверждение о проверке.
- Строка executive-резюме «Смотрели: …, ИИ-ответы» — строится по существующим единицам
  поверхности (`executive.ts:259-265`); на прогоне 76 её питает панель знаний UAE. Пограничная
  формулировка, не утверждение «проверено, пусто».
- Несоответствие единиц в `progressRatio` покрытия (агенты против 12 поверхностей,
  `unified-orion-collection-orchestrator.ts:1243-1251`) — существовавший до шага перекос; здесь
  меняется только бакет для выключенных, не арифметика.
- Пункт M бэклога (`ARSENKIN_TOOLS`/`DIGITAL_PROFILE_LINK_READING` как флаги в окружении) — не
  трогаем; состав прогона по-прежнему решает `arsenkinTools()`.
- `regional-summary.ts`, `run-deck-build.ts`, `slides.py` — не трогаем: их правят параллельные
  шаги AJ/AD, а для AL они не нужны (см. «Риски»).

## Контекст

Всё ниже измерено по коду репозитория и артефактам: живой бандл прогона 76 —
`/tmp/claude-0/-root-projects-global-info/51393af0-b406-4aa4-8016-0d186f952598/scratchpad/live-run/`
(далее «бандл»), эталон — `baselines/report-72/artifacts/`.

### Дефект на источнике

`arsenkin-enrichment-tick.ts:950-967`: агент без задач, без исполнения и не входящий в состав
(`isArsenkinAgentEnabled` → `arsenkinTools(env)`, по умолчанию `["check-top","suggest","paa"]`,
`providers/arsenkin/flags.ts:32` — вторая стадия отключена решением ADR-0005) получает:

```ts
const disabledByTools = agentTasks.length === 0 && !exec && !isArsenkinAgentEnabled(agentName);
if ((input.offlineEmptyValid && ...) || disabledByTools) {
  ...
  agents.push({ ..., terminal: true, terminalKind: "EMPTY_VALID", ingested: true, ... });
```

Тот же `EMPTY_VALID` означает настоящую пустоту после настоящей проверки
(`progressFromTasks`, строка 175-176: задачи DONE, клиентских наблюдений ноль). Один статус —
два смысла; ровно тот класс, из-за которого замерзал прогон (`ENGINEERING.md`, «Состояние — это
данные, а не название»).

В бандле (`arsenkin-enrichment-state.json`): оба агента `terminalKind: "EMPTY_VALID"`,
`ingested: true`, `doneTaskCount: 0`, `observationCount: 0`, **`enrichmentRunId: null`** — у
настоящих проверок ран и задачи есть (три первых агента: SUCCESS, 200/36/14 наблюдений).
Предупреждения джобы (`job.json.warnings`) честные:
`arsenkin-agent-disabled-by-tools:ARSENKIN_AI_SEARCH_REAL` и `...URL_AUDIT_REAL` — но никто ниже
по конвейеру их не читает.

### Потребители лжи

1. **Покрытие джобы.** `unified-orion-collection-orchestrator.ts:1248` считает
   `EMPTY_VALID`/`NO_RESULTS` в бакет `noResults` («спрошено, пусто»). В бандле
   `provider-surface-coverage.json`: `measured: 5, noResults: 2` — две «пустоты» по не заданным
   вопросам.
2. **Сводка качества.** `report-quality-summary.ts:398` перекладывает `terminalKind` как есть:
   в бандле `report-quality-summary.json.arsenkin.agents` — два `EMPTY_VALID`.
3. **Дека.** Трасса до слайда — самое важное, и она **не** проходит через состояние агентов:
   - `canonical-report-prepare.ts:808-820` строит `coverageRows` **только** из существующих
     наблюдений, все со статусом `OK`. Про не собиравшиеся поверхности пайплайн аналитики не
     узнаёт ничего.
   - Поэтому `analytics/composite-serp-provenance.json` бандла: `nonOkCoverageCells: []`
     (у эталона report-72, где вторая стадия реально отработала, — 15 ячеек, среди них
     `{region: RU, engine: YANDEX, surface: ai_answer, status: NO_RESULTS, provider: arsenkin}`
     и ещё две ai-ячейки; см. также удалённый план ADR-0005 в истории git, коммит `5846a75^`).
   - `load-deck-inputs.ts:206-235` (`googleAnswerProbeHints`) **выводит** для `ai_answers`
     подсказку `status: "NO_RESULTS"` по региону, где есть органика Google: раз ответ serper
     разобран, отсутствие готового ответа — измеренный факт. Для прогона 76 это дало подсказки
     по RU и UAE.
   - `scoped-input.ts:396-425` (`resolveEmptySurfaceCollection`) считает `NO_RESULTS` и
     `EMPTY_VALID` измеренным сбором → `MEASURED_EMPTY`.
   - `shared.ts:1754-1761` (`COVERAGE_EMPTY_COPY["no-ai-answers"]`) печатает: «Ответы ИИ-поиска
     (AI Overview, нейро-ответы) … проверены: материалов нет — это результат проверки».
   - Итог в бандле: `deck/section-packs/ru/ai.json`, слайд `p19_ru_knowledge_2`,
     `emptyStateReason: "no-ai-answers"`, дословно этот текст; PDF стр. 32, зелёная карточка
     «Статус сбора».

То есть у лжи два соучастника: тик присваивает выключенному `EMPTY_VALID` (ложь в состоянии и
счётчиках), а дека даже не спрашивает состояние — она обобщает измеренный факт про **Google**
(разобран ответ serper, `answerBox` пуст) на **все** «нейро-ответы», включая Яндекс, которого
никто не спрашивал.

### Что при этом правда

- Утверждение `googleAnswerProbeHints` само по себе честно, но только про Google и только про
  готовый ответ: `serper-surfaces.ts:109-135, 235-241` разбирает поле `answerBox` ответа serper
  (добавлено ровно потому, что раньше страница говорила «не собиралось» при ответе, лежавшем в
  выдаче). Поле Google **AI Overview** наш адаптер не читает; сторонние обзоры упоминают у
  serper поле `aiOverview`, собственной документацией serper это не подтверждено — в формулировках
  не утверждать.
- Единственный запланированный источник `ru_yandex_ai` — арсенкинский `ai-serp`
  (`ARSENKIN_AGENT_TOOLS`, `real-arsenkin-agents.ts:135-141`; слоты —
  `workflow-contract.ts:23-36`: `ru-yandex-ai`, `ru-google-ai`, `uae-google-ai` для `ai-serp`,
  `url-audit` для `check-h`). Базовый Яндекс-провайдер (`yandex-v2.ts`, официальный Search API
  v2 `/v2/web/search`) нейро-ответов не отдаёт.
- UAE-страница AI (`p31_uae_knowledge`) на прогоне 76 не пустая: анализатор
  (`surface-analyzers.ts:178-184`) относит `knowledge_block` к `ai_answers`, и единственная
  панель знаний Google (serper `knowledgeGraph` о субъекте) дала единицу поверхности — ветка
  «данные есть», лжи нет.

### Образец: как это уже решено на комплаенс-страницах (шаг F)

`fragment-builders/compliance.ts:316-385`: ветвь выбирают **данные** — есть строка рана
скрининга → «проверка выполнена…», ран с ошибкой → «не выполнена: причина», нет строки →
«проверка по официальному API не выполнялась: доступ подключается по договору». Инфраструктура
пустых состояний поверхности тоже уже трёхветочная: `EmptySurfaceCollectionKind =
MEASURED_EMPTY | NOT_COLLECTED | COLLECTION_FAILED` (`scoped-input.ts:224-233`), и
`coverageContent` (`shared.ts:1817-1894`) умеет все три. Задача шага — не третий способ отвечать,
а довести правдивые данные до уже существующего выбора ветви и добавить одну недостающую ветвь —
частичную (по одному движку проверено, по другому нет).

### Легальные пути к ответу Алисы (пункт 4 задания — установлено фактами)

- **Arsenkin `ai-serp`** — инструмент существует и документирован: «API сбора ИИ ответов Яндекс
  Алисы на поиске и Google AI Overview» (`help.arsenkin.ru/api/api-ai-serp`; сам сайт из этой
  среды недоступен — соединение отклонено, факты из поисковой выдачи по его документации). API
  доступен на тарифах STANDARD и CORPORATE. На эталоне report-72 инструмент **принимал задачи**
  и вернул `NO_RESULTS` по всем трём ai-ячейкам (артефакт provenance) — то есть тогда тариф его
  пускал; формулировка бэклога «недоступны на тарифе аккаунта» из данных прогона 76 **не
  выводится** (там только состав `disabled-by-tools`) и отсюда не перепроверяется. Формат ответа
  `ai-serp` в доступных цитатах документации не показан — фикстуры по документации не выдумывать
  (эти грабли уже стоили формата, которого у провайдера нет): включение требует снятия реального
  ответа.
- **Официальный Yandex Search API v2 — генеративный ответ.** Тот же сервис, которым мы уже
  собираем органику (`yandex-v2.ts`, ключ `YANDEX_SEARCH_API_KEY` + `YANDEX_SEARCH_FOLDER_ID`).
  Документация AI Studio: «Генеративный ответ при текстовом запросе к Yandex Search API»
  (aistudio.yandex.ru/docs/ru/search-api/concepts/generative-response.html; страница из этой
  среды за капчей, состав ответа подтверждён публичным сгенерированным кодом yandex-cloud:
  `GenSearchResponse` = `message` (текст ответа), `sources[]` (`url`, `title`, `used`),
  `search_queries`, `fixed_misspell_query`, `is_answer_rejected`, `is_bullet_answer`). Языки —
  ru/kk/uz. Цена — порядка единиц рублей за запрос (в казахстанской версии тарифов виднелась
  цифра 25 400 KZT за 1000 генеративных запросов; точную цену перепроверить на pricing при
  включении). Это легальный ответ той же нейро-технологии, что «Быстрый ответ Алисы», **но не
  дословный блок из выдачи** — в отчёте подаётся как «ответ генеративного поиска Яндекса,
  получен официальным API», с его источниками.
- **Запрещённые пути** (названы, чтобы не всплывали): скрейпинг выдачи ya.ru — прямой запрет
  правил; генерация «похожей справки» своей моделью — выдуманный факт в отчёте банку. Ответ
  чужой модели, полученный её официальным API, — не наша генерация: это наблюдение поверхности,
  как заголовок выдачи, и цитируется с атрибуцией.

## Решение

Принцип: **вопрос «спрашивали ли поверхность в этом прогоне» получает один ответ — в данных
прогона**, и все потребители (счётчики, сводка качества, дека) читают его, а не выводят каждый
свой.

1. **Новый терминальный исход `DISABLED`.** В `ArsenkinAgentTerminalKind` добавляется
   `"DISABLED"`; ветка `disabledByTools` тика пишет его вместо `EMPTY_VALID`. Поля
   `scheduled/terminal/ingested: true` **сохраняются**: на них держатся гейты завершения
   (`assertEnrichmentReadyForComposite` требует пятерых в `scheduledAgents`/`ingestedAgents`,
   `state.ts:321-336`; `completedAgents` принимает любой исход кроме FAILED/SUBMIT_UNKNOWN,
   `state.ts:266-274`) — менять их значило бы заново открыть «прогон ждёт отключённых вечно»,
   от которого этот код и лечили (комментарий в тике это объяснит). Ветка `offlineEmptyValid`
   не задевается: оффлайн-синтетика (`offlineSyntheticCompleteTick`) остаётся `EMPTY_VALID` —
   там раны зарегистрированы (`offline-arsenkin-*`), это «оффлайн-контур считает пустоту
   валидной», отдельный смысл с отдельным словом.
   Почему не «чинить» булевы поля вместо слова: слово и было единственным местом, где смысл
   потерялся; данные (`enrichmentRunId: null`, `doneTaskCount: 0`) правду хранят и так.

2. **Предикат «не спрашивали» — одна функция.** Рядом с типом состояния заводится
   `agentWasDisabled(agent, state): boolean` = `agent.terminalKind === "DISABLED"` **или**
   легаси-форма: `agent.terminalKind === "EMPTY_VALID" && agent.enrichmentRunId == null &&
   agent.doneTaskCount === 0` **и при этом прогон вообще говорил с провайдером** — в том же
   состоянии есть хотя бы один агент с непустым `enrichmentRunId`. Второе условие обязательно:
   в оффлайн-режиме отправка пропускается целиком (`arsenkin-enrichment-tick.ts:732` —
   `!input.offlineEmptyValid`), и **все** агенты, включая включённых, завершаются веткой 952 с
   `runId: null` и `EMPTY_VALID`; без второго условия оффлайн-состояние читалось бы как «всё
   выключено». На живом прогоне 76 условие выполняется: три агента несут реальные раны.
   Легаси-форма нужна одному потребителю — пересборке уже записанных прогонов (76-й заморожен со
   старым словом); комментарий у функции объясняет обе оговорки и назначает ей срок жизни «пока
   живы прогоны до v88».

3. **Счётчики покрытия.** `unified-orion-collection-orchestrator.ts:1244-1252`: агенты с
   `DISABLED` уходят в существующий бакет `notSupported` («в этом прогоне не поддержано
   составом»), не в `noResults`. Схема `SurfaceCoverageBreakdown` не меняется.

4. **Транспорт в деку — через существующий канал ячеек покрытия.**
   В `canonical-report-prepare.ts` (рядом со сборкой `coverageRows`, строки 808-820): читается
   `arsenkin-enrichment-state.json` из `input.artifactsDir` (файла нет — фикстуры и голден —
   ничего не добавляется); для каждого агента с `agentWasDisabled` его слоты из
   `FIRST36_FULL_SURFACE_SLOTS` × `ARSENKIN_AGENT_TOOLS` дают ячейки
   `{region, engine, surface, status: "NOT_COLLECTED", provider: "arsenkin",
   errorCode: "DISABLED_BY_TOOLS"}`. `composite-dataset-builder.ts:97,271-273`: статус
   `NOT_COLLECTED` добавляется в множество записываемых в `nonOkCoverageCells` (сейчас
   `DESTRUCTIVE_STATUSES` его отбросил бы). Дальше ячейки едут уже существующей трассой:
   provenance → `load-deck-inputs.ts:395-403` → подсказки.
   Почему не читать состояние агентов прямо в `load-deck-inputs`: тот работает от analytics-дира
   и не знает джобы; provenance — уже существующий канал «что с покрытием», второй канал был бы
   вторым ответом.

5. **Движок в подсказках.** `SurfaceCollectionHint` получает `engine?: string`;
   `load-deck-inputs` прокидывает его из ячеек provenance (у report-72 ячейки его уже несут),
   `googleAnswerProbeHints` ставит `engine: "GOOGLE"`. Подавление выведенной подсказки
   (`alreadyKnown`) уточняется: probe-подсказка не добавляется, только если по региону уже есть
   **измеренная или сбойная** подсказка `ai_answers` (NOT_COLLECTED-ячейка Яндекса не должна
   глушить измеренный факт по Google — иначе честность по одному движку купится потерей факта
   по другому).

6. **Резолвер пустого состояния.** `resolveEmptySurfaceCollection`:
   - статусы `NOT_COLLECTED`/`DISABLED` — третий класс: не «измерено» и не «сбой» (сейчас любой
     небелый статус падает в `COLLECTION_FAILED`, `scoped-input.ts:396-409`);
   - группировка подсказок по `engine` (подсказки без движка — одна общая группа, поведение всех
     прочих страниц не меняется);
   - все группы измерены → `MEASURED_EMPTY` (как сейчас); все не собраны/пусто →
     `NOT_COLLECTED`; смесь → новый kind `"MEASURED_PARTIAL"` с полями
     `measuredEngines: string[]` и `notCollectedEngines: string[]` (клиентские имена движков —
     «Google», «Яндекс»; словарь имён уже есть в `regional-summary.ts:325-330`, для деки завести
     один общий хелпер в `shared.ts`, не второй словарь);
   - сбой одного движка при измеренном другом — тоже `MEASURED_PARTIAL`, несобранное называется
     с причиной сбоя.

7. **Клиентский текст.** `coverageContent` (`shared.ts`) получает ветвь `MEASURED_PARTIAL`;
   словарная ветвь `MEASURED_EMPTY` **не меняется** (для report-72, где ai-serp реально
   спрашивал и Яндекс, и Google, фраза «проверены: материалов нет» — правда и остаётся
   дословно). Тексты новой ветви для AI-страницы (черновик — точные слова закрепит текстовый
   эталон и ревью диффа):
   - narrative: «Готовый ответ в разобранной выдаче Google по запросам о субъекте отсутствует.
     Нейро-ответы Яндекса в этом прогоне не проверялись: инструмент сбора ИИ-ответов не входил
     в состав прогона.»
   - bullets: существующее «почему важно» из словаря + «Непроверенная поверхность — не результат
     „материалов нет“: ответ может показываться пользователям поисковой системы.»
   - whatToCheck: «Подключить сбор ИИ-ответов (инструмент провайдера или официальный API
     поисковой системы) и повторить проверку.»
   Ветвь `NOT_COLLECTED` (не проверялось нигде) использует уже существующую формулировку
   `shared.ts:1842-1857` с причиной «инструмент сбора не входил в состав прогона» вместо
   generic-текста. Причину «недоступен на тарифе» **не печатать**: из данных прогона она не
   прослеживается (в данных — только состав). Внутренние коды (`DISABLED_BY_TOOLS`,
   `EMPTY_VALID`) в клиентский текст не попадают — как и сейчас.
   Рендерер не меняется: шаблон `orion_golden_no_data_compact` («Статус сбора», зелёная карточка
   accent) уже обслуживает комплаенс-ветви «не выполнялась» шага F тем же тоном.

Итог для прогона 76 после пересборки: RU-страница AI — `MEASURED_PARTIAL` («Google — готового
ответа нет; Яндекс — не проверялся, причина»); UAE-страница — без изменений (данные есть);
report-72 — без изменений (`MEASURED_EMPTY`, инструмент спрашивал); голден — без изменений
(ветвь «ответы есть»; его analytics-фикстуры не содержат `arsenkin-enrichment-state.json`, и
подсказки не появляются).

Что из обоснований обязано пережить этот файл: смысл `DISABLED` против `EMPTY_VALID` и легаси-
предикат — комментарии у кода; правило «не спрашивали ≠ пусто» и трасса ячеек NOT_COLLECTED —
`ENGINEERING.md` (см. последний раздел).

## Риски и что может сломаться молча

- **Второй ответ на «что было в составе прогона».** Если prepare начнёт спрашивать
  `arsenkinTools(env)` вместо записанного состояния, пересборка старого прогона на машине с
  другим окружением «переиграет» историю. Решение читает только данные прогона; предикат — одна
  функция. Ревьюеру: искать обращения к `arsenkinTools`/`isArsenkinAgentEnabled` в новых
  фрагментах prepare/деки — их там быть не должно.
- **Кэш секций.** Правки словаря и резолвера без подъёма `DECK_CONTENT_VERSION` молча не доедут
  до документа — пункт 7 плана обязателен, отпечаток построителей это ловит.
- **Заслон измеренного факта.** Неправильный порядок в п. 5 «Решения» (NOT_COLLECTED глушит
  probe-hint) сделает страницу «не проверялось вовсе» — ложь в обратную сторону. Тест 8.
- **Легаси-предикат и оффлайн-состояния.** Найденный при планировании угол: в оффлайн-режиме
  включённые агенты тоже завершаются `EMPTY_VALID` с `runId: null` (ветка 952 при пропущенной
  отправке, строка 732) — предикат без условия «в состоянии есть хоть один реальный ран» ловил бы
  их как выключенных, и страницы оффлайн-смоков сменили бы формулировки. Условие входит в
  предикат (Решение, п. 2) и закреплено тестом 5; ревьюеру стоит перепроверить по
  `progressFromTasks` и ветке 952, что других источников `EMPTY_VALID` без рана нет.
- **`MEASURED_PARTIAL` у чужих страниц.** Резолвер общий; подсказки без `engine` обязаны давать
  старое поведение (тест 3в), иначе пустые страницы подсказок/картинок тихо сменят формулировки
  и голден-сверка покраснеет — что и будет сигналом.
- **Пересборка прогона 76 не обновит его джобу.** `provider-surface-coverage.json` и
  `arsenkin-enrichment-state.json` в замороженном джобе останутся со старыми словами
  (`noResults: 2`, `EMPTY_VALID`); честной станет дека (через легаси-предикат) и новые прогоны.
  Это принятая цена — миграция замороженных артефактов не делается.
- **Параллельные шаги.** AL задевает `fragment-builders/shared.ts` — его же может задеть AK
  (пометки «о другом лице» живут рядом: `claimText`, панельные строки); `content-version.ts`
  поднимают все. С AD (`identity.ts`, `run-deck-build.ts`, `common.py`) и AJ
  (`llm-slide-copy.ts`, `run-deck-build.ts`, `slides.py`, `regional-summary.ts`) пересечения по
  файлам нет — AL сознательно не трогает ни `run-deck-build.ts`, ни рендерер. Порядок мержа с AK
  решает оркестратор; конфликт в `shared.ts` содержательный, не механический.
- **GPT-стадия 2 поверх пустых состояний.** `gptCopy` на прогоне 76 применился к 1 слайду пака
  AI; если копирайт перепишет частичную формулировку обратно в «проверено», ложь вернётся. У
  шага AJ ровно эта тема (защита носителей честности от переписки); тест 1 гоняется на
  детерминированном тексте без GPT, а связку с AJ проверит живой прогон. Назвать в отчёте
  инженера, если увидит переписку этих полей в путях стадии 2.
- **Скрытые enum-потребители.** `terminalKind` читают также `unified-enrichment-sibling-remap`
  (только FAILED, инертно) и `report-quality-summary` (z.string — пропустит). Если где-то
  найдётся строгий enum по старому списку — типы упадут на `npm run typecheck`, это ожидаемый
  ловец.
