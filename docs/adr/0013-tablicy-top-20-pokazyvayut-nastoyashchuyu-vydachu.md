# Шаг 0013. Таблицы ТОП-20 показывают настоящую выдачу

## Задача и границы

Закрыть блокеры B1 и B2 разбора живого прогона 76 (`docs/adr/0000-etalon-gap-backlog.md`,
раздел «Разбор живого прогона 76»): таблица «ОАЭ — Google, ТОП-20» наполовину заполнена
позициями Арсенкина и противоречит соседнему снимку выдачи; таблица «Россия — Google» —
шесть строк с дырами. В рамках шага:

1. Глубина сбора Serper: запрошенные 20 позиций доходят до провайдера.
2. Дедупликация при записи выдачи: движок — часть идентичности строки; Яндекс не
   вычёркивает выдачу Google.
3. `rankSource` едет через весь тракт до деки, и таблица движка печатает только позиции
   своего движка.
4. Сравнение запросов — регистронезависимое, в одном месте.
5. Ингестия примеров «прочих материалов» перестаёт стирать данные строк выдачи в
   `evidenceIndex`.
6. Фолбэк «наборов без запросов» перестаёт печатать чужие ранги на современных данных.
7. Ворота: печатная таблица сверяется с артефактом наблюдений независимым инструментом.
8. Эталоны и `DECK_CONTENT_VERSION` — обновляются; дифф — материал ревью.

**Вне рамок** (замечено, не чинится здесь):

- Дублирование сборщиков: `REAL_GOOGLE_SEARCH`/`REAL_YANDEX_SEARCH` собирают ту же органику,
  что ORION-профиль, но не записывают запрос (`real-search-agent-base.ts` не кладёт
  `query` в rawMetadata, строки без `queryId`) — их безымянные строки и дали фантомный

- `GOOGLE_SEARCH_RESULTS_PER_QUERY` — не-секрет в переменной окружения
  (`providers/config.ts:148`); нарушает правило «в env только секреты», но существует до
  шага и не мешает ему.
- Объединение `NOT_FOUND_PATTERNS` (serp.ts) с `isEmptyMarker` анализатора — уже помечено
  в `ENGINEERING.md` §8 как отдельная работа.
- Печать доли прочитанного (шаг AJ), классификатор принадлежности (AK), Арсенкин-тик (AL),
  «почему выделено» (AG).

## Контекст

Всё ниже перемерено по живому бандлу прогона 76 (scratchpad `live-run/`) и по коду рабочей
копии (ветка `feature/kostyannew`, после `5e4aa0f`). Разбор из бэклога в основном
подтверждён; **одно утверждение опровергнуто, один механизм разбором не был найден** —
оба помечены.

Тракт данных выдачи (важно, потому что дефекты сидят на стыках):

```
сбор (агенты + ORION-профиль) → search_results (Prisma, unique [caseId, dedupHash])
  → mergeCompositeSerp (services/composite-serp-merge.ts)
      → верхнеуровневый composite-serp-observations.json  ← 919 строк, ЕСТЬ ranksByProvider/rankSource
  → compositeObservationsToInventory (canonical-report-prepare.ts:283)
      → инвентарь: rawMetadata несёт rank, НЕ несёт rankSource        ← обрыв
  → buildAnalyticsCompositeDataset (analytics/composite-dataset-builder.ts)
      → analytics/composite-serp-observations.json ← 881 строка, поля rankSource НЕТ в контракте
  → loadDeckInputsFromAnalyticsDir (deck-sections/load-deck-inputs.ts) → evidenceIndex
  → buildSerpFragment (fragment-builders/serp.ts) → таблица
```

Дека читает **только** `analytics/`-вариант (`load-deck-inputs.ts:353-357`); верхнеуровневый
файл с `rankSource` в деку не попадает никогда.

**М1. Serper не просили о 20 — адаптер режет просьбу до настройки.**
`serperSearch` (`providers/serper-search-provider.ts:84-87`):

```ts
const limit = Math.min(
  request.limit ?? providerConfig.google.resultsPerQuery,
  providerConfig.google.resultsPerQuery
);
```

`resultsPerQuery` по умолчанию 10 (`providers/config.ts:148`), значит просьба сбора
(`runRegionOrganic` передаёт `limit = max(…, SERP_AUDIT_DEPTH) = 20`,
`orion-search-profile-service.ts:259-263`) срезается до 10 **до сетевого вызова**: в сеть
уходит `num: 10`. Это ровно тот паттерн, который коммит `6e66ef8` («глубина выдачи —
просьба вызывающего, а не потолок настройки») вычистил из `google-search-provider.ts` и
`yandex-search-provider.ts`, создав `providers/search-depth.ts`, — но третий адаптер с тем
же паттерном пропустил. Живой путь Google идёт именно через него
(`external-google-serp-provider.ts:90`). Замер по бандлу: из 601 serper-строки ни одной с
рангом > 10 (RU max 10, UAE max 10); Яндекс — через починенный адаптер — дал до 20.
Ответ на вопрос «не просит / просит, но не получает / получает и теряет»: **не просит**.

**М2. Дедуп при записи вычёркивает выдачу Google — в двух трактах по-разному.**

- ORION-профиль: `dedupHash = sha256(normUrl|query|region)` — движка в хеше нет
  (`orion-search-profile-service.ts:222`). В цикле по запросу Яндекс пишется раньше Google
  (строки 287-317), обе записи идут `createMany({skipDuplicates})`, и Google-строка того же
  URL по тому же запросу молча выбрасывается.
- Агентский тракт: `dedupHash = sha256(normUrl)` — на весь кейс
  (`real-search-agent-base.ts:115`); `REAL_YANDEX_SEARCH` завершился раньше
  `REAL_GOOGLE_SEARCH` (порядок в `unified-collection-summary.json`).

Замер: по запросу «Рашников Виктор Филиппович» (RU, GOOGLE) в analytics есть ровно шесть
строк — ранги 4, 6, 7 (tadviser), 8, 9, 10. Ранги 1, 2, 3, 5 держат в Яндексе по тому же
запросу ru.wikipedia.org, ru.ruwiki.ru, forbes.ru, p.warheroes.ru — URL, которые Google
почти наверняка тоже отдал первыми, но их строки не были записаны. Дыры 1, 2, 3, 5 в
печати — это они. Формулировка бэклога «`dedupHash` по нормализованному URL на весь кейс»
верна только для агентского тракта; для дыр таблицы решающим был ORION-тракт с хешем без
движка.

**М3. `rankSource` умирает на переходе в инвентарь и не существует в analytics-контракте.**
`compositeObservationsToInventory` копирует в `rawMetadata` только `rank`
(`canonical-report-prepare.ts:318-334`); `CompositeObservationRowSchema` поля `rankSource`
не имеет (`orion-golden/contracts/composite-dataset.ts:6-33`); `toRow` его не пишет
(`composite-dataset-builder.ts:159-185`). Замер: в analytics-файле бандла `rankSource`
отсутствует у **всех 881** строк. Поэтому фильтр `rankFromOwnEngine`
(`fragment-builders/serp.ts:320-325`) с его «`!src || src === "unknown" → true`» на живом
пути **истинен вакуумно — он не отфильтровал ни одной строки ни в одном живом прогоне**:
защита `d41c95d` («Arsenkin в списках не участвует») построена на поле, которое до деки не
доезжает. Юнит-тесты кормили `evidenceIndex` с проставленным `rankSource` вручную — и были
зелёными. Так арсенкинские ранги вошли в таблицу ОАЭ: 12 строк из 19 печатных (4 —
metalinfo.ru, 10 — ko.ru, 11–20 целиком) несут нумерацию Арсенкина.
Примечание: у analytics-строки есть поле `provider` ('serper'/'arsenkin'/'yandex'), и на
сегодняшнем построении оно совпадает с источником ранга, но дека его не читает, а
совпадение — свойство текущего кода, не контракт.

**М4. Серперные строки 3, 4, 10 выбиты из таблицы ОАЭ перезаписью «прочих материалов» —
механизм, которого в разборе не было.** Ингестия `uncategorized-materials.json`
(`load-deck-inputs.ts:700-710`, появилась в `939a6ac`) перезаписывает запись
`evidenceIndex[ref]` **целиком**: `{title, domain, kind: "uncategorized", region}` — без
rank, query, engine. Соседний цикл `topExamples` (строки 712-724) делает то же самое под
охраной `if (!evidenceIndex[ref])` — задуманная семантика видна, охраны нет только в
цикле byRegion. Замер: восемь UAE-примеров «прочих материалов» включают ровно
`obs-8e0aa21765b2b67e` (opensanctions.org, serper rank 3, query 'viktor rashnikov'),
`obs-a3efa0d9f3689b44` (bloomberg.com, rank 4) и `obs-c1c6ba53c7d42a45` (wikidata.org,
rank 10). После перезаписи у их материалов не остаётся ни одного ref с запросом таблицы →
`rankInQuery` возвращает MAX_SAFE → материалы выпадают; дыру на 3 никто не занял, 4 и 10
заняли арсенкинские metalinfo.ru и ko.ru. **Проверено исполнением**: реплей текущего
`loadDeckInputsFromAnalyticsDir` + `buildSerpFragment` над analytics-каталогом бандла
воспроизводит обе печатные таблицы дословно (и «4 metalinfo», и дыру 3, и RU
«4,6,7,8,9,10»); в RU-примерах перезаписаны только агентские twin-строки Яндекса, у чьих
материалов остались живые ORION-refs — потому Яндекс-таблица не пострадала.

**М5. Регистрозависимое сравнение запросов решило судьбу двух таблиц в разные стороны —
подтверждено.** Запросы Арсенкина — сплошь нижний регистр (все 232 строки обогащения);
запросы ORION RU — смешанный («Рашников Виктор Филиппович», «рашников виктор филиппович
состояние»); UAE — нижний латиницей. Сравнения в деке строковые: `queriesOfGroup` — ключ
Map (serp.ts:277-283), `groupInQuery` — `queries.has(query)` (:290-294), `rankInQuery` —
`=== query` (:348), `pickSerpTableQuery` — ключ stats (:158-176), `subjectQueriesLine` —
ключ Map (`shared.ts:1627-1647`). В UAE выбранный запрос 'viktor rashnikov' совпал со
строкой Арсенкина посимвольно → его ранги вошли; в RU «Рашников Виктор Филиппович» ≠
«рашников виктор филиппович» → не вошли. Ключи наблюдений при этом уже
регистронезависимы (`norm()` в `services/composite-serp-merge.ts:229-234`,
`compositeObservationKey` в `composite-dataset-builder.ts:127-129` — оба lowercase);
регистр сохраняется только в **поле** `query`, которым и сравнивает дека. Вне деки
запросы сравниваются строками ещё в `arsenkin-tool-adapters.ts:214` и
`collect-pilot-surfaces.ts:673` — оба раза внутри данных одного провайдера, где регистр
однороден; не трогать.

**М6. Свёртка `load-deck-inputs.ts:461-479` на прогоне 76 не сработала — утверждение
бэклога в этой части опровергнуто.** Свёртка реальна: `rank` — минимум по всем
наблюдениям ref, `rankSource` едет за минимумом, `query` — первый попавшийся. Но замер
показал: ни один ref не встречается в двух analytics-наблюдениях (0 из 881; провенанс —
872 записи 1:1 и 9 записей с 2–10 refs, это дубли одного ключа). Каждая analytics-строка
и так несёт пару «запрос × движок × URL» со своим личным ref — упрощать хранение не
нужно, нужно перестать терять `rankSource` (М3) и перестать затирать записи (М4). Свёртка
остаётся миной на случай будущего шаринга refs; лечится не переделкой индекса, а
правилом М8 (ранг берётся только у наблюдения своего движка) и тестом тракта.

**М7. Фолбэк «наборов без запросов» печатает чужой ранг на современных данных.**
`rankInQuery`: если ни у одного ref группы нет запроса — берётся лучший ранг группы
(serp.ts:355-357; задумано для прогонов, собранных до записи запросов). Агентские строки
без запроса образуют такие группы сейчас: печатный «7 lenta.ru» в RU-Google — ранг
наблюдения без запроса (агентский тракт), а настоящий №7 выбранного запроса
(tadviser.ru) выброшен `dropDuplicateRanks` как дубль. Номер строки соврал о запросе.

**М8. Материал, найденный обоими движками, попадает только в одну таблицу.** Группы
материалов собираются по domain|title через все юниты региона (serp.ts:226-259), а
`byEngine` раскладывает **группу целиком** по движку первого ref (:368-374). Сегодня это
маскируется дедупом М2 (общих URL почти нет); почини мы только сбор — forbes.ru с
позициями в обоих движках уехал бы в таблицу Яндекса и оставил в Google новую дыру.
Правка деки обязана идти в паре с правкой сбора.

**Снимок против таблицы (читателю виден разворот).** Стр. 45 PDF: «выделены 5 результатов
повышенного внимания: opensanctions.org, data.europa.eu, sanctionssearch.ofac.treas.gov,
sanctions.lursoft.lv…». Стр. 42–43: в таблице ОАЭ opensanctions.org нет. При этом
буквальная сверка «домены снимка ⊆ строки таблицы» неверна как проверка:
sanctionssearch.ofac.treas.gov в выдаче по запросу таблицы не стоит вовсе (его ранги — по
пробе 'viktor filippovich rashnikov sanctions', №1), то есть и у полностью починенной
таблицы буквальная сверка осталась бы красной. Противоречие ловится сверкой печати с
артефактом, а не двух страниц между собой — см. Решение, Р8.

**Стоимость глубины.** По сторонним разборам тарифов Serper (coldiq.com/blog/serper-pricing,
apiserpent.com/blog/serper-pricing-credits-explained; собственная страница тарифов без
логина отдаёт 404), запрос с `num` 11–100 стоит 2 кредита вместо 1. Починка М1 удваивает
цену каждого органического запроса Serper (в прогоне 76 их порядка шестидесяти).
Поверхностные вызовы (`serper-surfaces.ts`) уже просят 20 и, если правило действует, уже
платят по двойному тарифу. Это данные сторонних источников, не документации провайдера —
пометить при сверке первым живым прогоном.

## Решение

**Р1. Глубина — правилом, которое уже записано.** `serperSearch` считает глубину через
`resolveSearchDepth({requested: request.limit, fallback: cfg.resultsPerQuery, max: 100})`
— тем же модулем `providers/search-depth.ts`, что и два других адаптера. Потолок 100 — это
существующий предел API, уже зашитый в `buildSerperSearchBody` (:43). Альтернатива
«поднять умолчание `resultsPerQuery` до 20» отвергнута: настройка — не обещание аудита, и
правило «настройка — глубина по умолчанию, потолок задаёт API» уже принято `6e66ef8`;
третий ответ на тот же вопрос не нужен.

**Р2. Движок — часть идентичности строки выдачи.** «Страница на месте N у Яндекса» и «на
месте M у Google» — два разных факта, оба нужны отчёту.
`persistOrganicResults`: `dedupHash = sha256(engine|normUrl|query|region)`;
`RealSearchAgentBase.saveEvidence`: `dedupHash = sha256(engine|normUrl)` (движок у агента
свой на подкласс, идемпотентность повторного запуска сохраняется: тот же агент → тот же
хеш → skip). Миграции не нужны: меняется значение поля, не схема
(`@@unique([caseId, dedupHash])` остаётся). Альтернатива «дедупить после записи, в
merge» отвергнута: merge и так дедупит по ключу с движком; терять факт до первой записи —
значит не иметь его нигде. Комментарий-почему обязателен в обоих местах: хеш без движка
выглядит «упрощением», которое кто-нибудь вернёт.

**Р3. `rankSource` — данные, а не свойство слоя.** Источник ранга вычислен один раз
(`rankInOneScale` в верхнеуровневом merge) — дальше это данные, и они едут не теряясь:
`compositeObservationsToInventory` кладёт `rankSource` в rawMetadata; `toRow` пишет его в
строку; `CompositeObservationRowSchema` получает optional-поле `rankSource`;
`load-deck-inputs` уже читает `obs.rankSource` (:470-474) — заработает без правки.
Альтернатива «вывести источник из поля `provider` строки» отвергнута: их совпадение —
случайность текущего построения (base добавляется раньше enrichment), а не контракт;
полагаться на него — второй ответ на вопрос «чей это ранг». Старые артефакты без поля
работают как раньше (см. Р4).

**Р4. Таблица движка собирается из наблюдений движка.** В `buildSerpFragment`:

- партиция по движкам идёт не по группе целиком, а по refs: таблица движка E строится из
  групп, у которых есть ref с `engine == E`; одна группа может дать строку в обеих
  таблицах (М8);
- `rankInQuery(group, query, E)` берёт ранги только у refs, чьи `engine == E` **и**
  `rankSource` принадлежит E (`ENGINE_RANK_SOURCE`);
- политика `unknown`/отсутствующего `rankSource` становится **датасетной**, а не
  построчной: если ни один ref таблицы не несёт `rankSource` — набор старый, всё
  допускается (эталоны report-72/golden-case не теряют таблиц); если хотя бы один несёт —
  строки без `rankSource` в позиционную таблицу не допускаются. Построчное «!src → true»
  — та самая лазейка, через которую жил М3: смешанный набор проходил целиком.

**Р5. Сравнение запросов — одна функция.** Нормализация `trim + toLowerCase +
схлопывание пробелов` (ровно как `norm()` в merge — тот же ответ, что уже дан на уровне
ключей) — в одной экспортированной функции serp.ts; ею пользуются `queriesOfGroup`,
`groupInQuery`, `rankInQuery`, `pickSerpTableQuery` и `subjectQueriesLine` (shared.ts).
Печатная форма запроса — исходная строка самого частого варианта написания; при равенстве
— детерминированно (алфавит), чтобы отчёт был воспроизводим. Генерацию запросов
(`orion-query-plan.ts`) не трогать: поисковику регистр безразличен, а нормализация при
генерации была бы вторым местом того же решения.

**Р6. Ингестии дополняют индекс, не перезаписывают.** Цикл byRegion-примеров получает ту
же охрану, что и topExamples: писать только refs, которых в индексе нет. Региональные
резюме не пострадают: их примеры идут из `extras.uncategorizedMaterials`
(`regional-summary.ts:45-63`), а в скоуп такие refs попадают через юниты поверхностей
(`scoped-input.ts:476-481`); ветка `kind === "uncategorized"` в `buildScopedInput` нужна
только refs, не достижимым иначе, — ровно те, кому охрана разрешит записаться.

**Р7. Фолбэк «без запросов» — свойство набора, не группы.** Ранг у группы без запросов
берётся только когда **во всей таблице движка** нет ни одного наблюдения с запросом. На
старых наборах поведение прежнее; на современных — безымянные строки не получают
выдуманных мест (М7: lenta.ru «7»).

**Р8. Ворота: печать сверяется с артефактом, а не с самой собой.** Новая проверка в
`assembly-validation.ts` (работает и на живом пути — отчёт `assembly-validation-report.json`
есть в бандле, и в приёмке через `gates.assemblyValidation`):

- пак позиционной таблицы записывает свой движок и выбранный запрос **данными**
  (`content.table` или metrics пака) — печатный факт, который можно проверить;
- проверка читает `composite-serp-observations.json` (analytics) напрямую — не
  `evidenceIndex`, которым собрана таблица: мерить инструментом, создающим дефект,
  бессмысленно (этой фразой уже оплачен растровый контур);
- в обе стороны: (а) каждый печатный номер строки подтверждён наблюдением этого движка,
  этого запроса (регистронезависимо), с `rankSource` движка; (б) каждое наблюдение движка
  по запросу таблицы с своим `rankSource` и рангом ≤ `SERP_TABLE_TOP_N` напечатано — кроме
  поимённо допустимых потерь (дубль ранга — напечатан один из дублей; маркер
  `NOT_FOUND_PATTERNS`). Наборы без `rankSource` вовсе (старые) — проверка объявляет
  пропуск, а не молчит.

На реплее бандла 76 проверка обязана быть красной в обе стороны (арсенкинские 11–20 не
подтверждаются, серперные 3/4/10 не напечатаны). Буквальную сверку «снимок ↔ таблица» не
строим — измеренный контрпример sanctionssearch.ofac.treas.gov показывает, что она красна
и у честного отчёта (выделение пришло из другого запроса той же выдачи); противоречие
разворота — симптом, причина ловится сверкой с артефактом. Это ответ на вопрос 6 задания.

**Р9. Неполная позиционная таблица говорит о себе словами** *(зависит от открытого
вопроса №1; вариант по умолчанию — рекомендованный)*. Когда собранные позиции движка не
достигают `SERP_TABLE_TOP_N`, заголовок называет фактический диапазон («…Google,
ТОП-20: позиции 1–10»), а под таблицей печатается строка причины: отсутствующие номера —
потеря при сборе, не пустые места выдачи. Пересборка прогона 76 после починки даст ОАЭ
полные 1–10 без арсенкинских 11–20 и Россию с дырами 1, 2, 3, 5 — эти данные потеряны при
записи навсегда, и честная подпись — единственное, что тут можно сделать («пустое
состояние честнее выдуманного»). Полные двадцать появятся только у следующего живого
прогона.

Что из обоснований обязано пережить этот файл: правило «позиция — свойство пары
наблюдение × движок × запрос» и датасетная политика `unknown` — в `ENGINEERING.md` §8;
«движок в dedupHash» и «границы 100 у Serper + двойной кредит при num>10» — туда же;
причины у охраны ингестии и у хеша — комментариями в коде.

   подтверждает разные хеши одного URL у разных движков и одинаковые — у повторного

7. **Ворота печати против артефакта.** `orion-golden/deck-sections/assembly-validation.ts`

8. **Эталоны.** Пересборка приёмки report-72 (`npx tsx scripts/run-orion-deck-sections-report72.ts`)

## Риски и что может сломаться молча

- **Деньги.** `num: 20` у Serper — 2 кредита за запрос вместо 1 (по сторонним данным);
  органика дорожает вдвое. Это трата, которая начинается без чьего-либо клика — потому
  вопрос №2 вынесен владельцу до реализации, а не после счёта.
- **Обрыв `rankSource` где-то ещё** вернёт вакуумный фильтр — датасетная политика Р4
  переводит этот отказ из «молча пропустили всё» в «строки без поля не вошли», что видно
  воротами Р8 (сторона «наблюдение не напечатано»). Тест 5 держит сам тракт.
- **Смена dedupHash на живом кейсе со старыми строками**: после деплоя повторный сбор
  того же кейса запишет строки со старым и новым хешем — дубли в `search_results`.
  Composite-merge дедупит по ключу с движком, до отчёта дубль не доходит; но счётчики
  «вставлено строк» у агентов могут подрасти. Приемлемо; в комментарии к хешу назвать.
- **Регистронезависимость меняет эталоны**: выбранный запрос таблицы и состав строк на
  report-72/golden-case могут сдвинуться — это не побочный шум, а материал ревью; команда
  `--update-baseline` сделает зелёным любой текст, смысл проверки — в чтении диффа.
- **Кэш секций**: без подъёма `DECK_CONTENT_VERSION` пересборка возьмёт паки из кэша и
  всё сделанное молча не доедет (пункт 5 помечен; тест-отпечаток напомнит).
- **Ворота, меряющие инструментом дефекта**: проверка Р8 обязана читать артефакт
  наблюдений, не `evidenceIndex`, и брать запрос из пака (печатный факт), не пересчитывать
  `pickSerpTableQuery` — иначе сломанный пикер согласится сам с собой.
- **Пропуск, похожий на пасс**: у наборов без `rankSource` проверка Р8 пропускается —
  пропуск обязан быть строкой в отчёте проверки; тихий пропуск на живом прогоне будет
  выглядеть как зелёное.
- **Параллельные шаги**: одновременная правка `serp.ts` (AK), `shared.ts` (AJ/AK),
  `content-version.ts` (AD/AJ/AK) — конфликты слияния; оркестратор разводит по времени.
- **Замороженные прогоны не станут полными**: дыры RU 1/2/3/5 — данные, которых нет;
  пересборка 76 их не вернёт. Не считать это провалом починки — считать провалом их
  молчаливую печать без подписи (Р9).

## Что переедет в ENGINEERING.md

В §8 «Решения, которые стоит помнить», при закрытии шага:

- **«Позиция выдачи — свойство пары „наблюдение × движок × запрос“».** Ранг существует
  только внутри нумерации одного поисковика по одному запросу; `rankSource` вычисляется
  один раз (`rankInOneScale`) и едет данными через инвентарь и analytics-контракт до
  деки; таблица движка собирается из наблюдений своего движка, и одна страница может
  стоять в обеих таблицах со своими номерами. Датасетная политика `unknown`: старые
  наборы без поля работают целиком, в смешанном наборе безымянный ранг не печатается.
  Упомянуть прогон 76: 12 из 19 строк таблицы ОАЭ были арсенкинскими, потому что поле
  умирало на переходе в инвентарь, а фильтр «!src → true» был истинен вакуумно.
- **«Движок — часть идентичности строки выдачи»** (dedupHash с движком): пока движка в
  хеше не было, Яндекс, отработав первым, вычёркивал верх выдачи Google — дыры 1, 2, 3, 5
  в «Россия — Google» прогона 76 — это невwritten строки, невосстановимые пересборкой.
- **Дополнить правило глубины** (сейчас живёт только в `search-depth.ts`): адаптеров три —
  google, yandex, serper; `6e66ef8` починил два, третий нашёлся по прогону 76 (serper
  нигде не выше 10 при яндексе до 20). Потолок Serper — 100; `num` > 10 стоит 2 кредита
  за запрос (по сторонним разборам тарифа; подтвердить счётом первого живого прогона).
- **«Ингестия дополняет индекс доказательств, не перезаписывает»**: перезапись примеров
  «прочих материалов» стёрла rank/query у serper-строк, и №3 выдачи (opensanctions.org)
  исчез из таблицы при зелёных воротах; охрана `if (!evidenceIndex[ref])` — единственный
  режим записи для вторичных ингестий.
- **«Запросы сравниваются регистронезависимо, в одном месте»**: регистр — свойство
  написания, не запроса; на прогоне 76 регистрозависимое `===` впустило арсенкинские
  ранги в UAE и не впустило в RU — один дефект, два противоположных исхода.
- В раздел про ворота/приёмку — строка о проверке «печать против артефакта наблюдений»
  и её объявленном пропуске на наборах без `rankSource`.

Бэклог `0000`: вычеркнуть AM; пункт «Списки ТОП-20 — только из родного поисковика» из
«Что уже сделано» пометить как довершённый этим шагом (д41c95d защищал слой, которого
дека не читала).
