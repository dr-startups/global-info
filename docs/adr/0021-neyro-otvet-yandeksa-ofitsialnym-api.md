# Шаг 0021. Нейро-ответ Яндекса — официальным Yandex Search API v2 (пункт AO)

## Задача и границы

Собирать генеративный («нейро») ответ Яндекса по субъекту легально — методом `GenSearch` того же
официального Yandex Search API v2, которым уже собирается органика, тем же ключом и каталогом, — и
доводить его до страницы «Россия — AI-ответы поисковых систем» с честной подписью, полным текстом и
списком источников, которые Яндекс назвал сам. Все исходы различимы словами на странице: ответ есть /
спросили — ответа нет / модель отказалась / сбор сорвался / провайдер не настроен.

**В границах:**

- один вызов `POST /v2/gen/search` на прогон, контур RU, запрос — первый subject-запрос RU-плана;
- персистенция ответа и источников как базовых наблюдений (`dp_search_surface_items`, новый тип
  `AI_ANSWER`) и запись исхода попытки в `base-collection-manifest.json`;
- печать ответа на слайде: полный текст, подпись «получен официальным API», источники;
- согласование сводки с этой страницей: `dataLimitations` перестаёт объявлять «ответы ИИ-поиска (RU)
  не собраны», когда на слайде напечатан собранный ответ (сегодняшнее противоречие измерено ниже);
- офлайн-закрепление: фикстуры золотого кейса, эталоны текста, тесты без сети и без базы.

**Вне границ (явно):**

- **Google AI Overview** — его даёт арсенкинский `ai-serp`, выключенный решением ADR-0005; состав
  `ARSENKIN_TOOLS`, `DEFAULT_TOOLS` в `providers/arsenkin/flags.ts` и сетка
  `FIRST36_FULL_SURFACE_SLOTS` не трогаются. Ячейка «RU/Google AI не спрашивали» остаётся честной
  правдой и остаётся на странице.
- Пункты T (тональности) и AH (разбор Википедии) — следующие шаги.
- Многострочная вёрстка текста в SVG-панели `buildKnowledgePanelSvg` (см. Контекст, п. 8): панель
  остаётся иллюстрацией, полный текст несёт страница. Одна строка о том, что панель обрезает длинный
  текст до одной строки, — известное ограничение, чинится отдельно, если владелец захочет.
- Пофразовое «в Google проверено, в Яндексе есть ответ» на **непустой** странице — сегодня непустая
  страница не потребляет ячейки покрытия, и учить её этому здесь не будем; страница показывает
  данные, пустые состояния остаются пофразовыми.
- Вызов gen-ответа по дополнительным запросам плана (риск-пробам и т.п.) — один субъектный запрос,
  см. Решение, п. Р1.

## Решение

Нейро-ответ Яндекса — **базовая поверхность базового сбора**, а не шестой арсенкинский агент: тот же
провайдер, тот же ключ, синхронный HTTP-вызов в секунды (не minutes-scale задача с опросом, поэтому
бюджеты `maxAttempts`/`maxWaitMs` арсенкинского типа не нужны — вызов живёт внутри уже существующего
шага BASE_COLLECTION с его лизом и ретраями). Данные — наблюдения; не-данные — запись о попытке.

- **Р1. Один вызов на прогон, RU, субъектный запрос.** `messages=[{role: ROLE_USER, content:
  <первый subject-запрос RU-плана>}]`, `searchType: SEARCH_TYPE_RU`, `folderId` из конфигурации; без
  `site/host/url` (спрашиваем весь индекс — продуктовый вопрос «что поисковик отвечает о субъекте»);
  `fixMisspell` не включаем (proto3-умолчание false): «исправленное» ФИО — это другой субъект;
  `enableNrfmDocs`, `enableRichStructuredAnswer`, `getPartialResults` не включаем. Отвергнуто:
  вызов по каждому запросу плана (кратный расход, дубли одного и того же ответа) и вызов для контура
  ОАЭ (аудитория ОАЭ не пользуется Яндексом; AO явно оставляет Google AI Overview за рамками).
  Запрос выводится тем же построителем, что у плана (`buildSubjectQuerySet`, без
  автодополнения — оно сетевое и на первый запрос не влияет); равенство с
  `queriesForRegionPurpose(plan, "RU", ["subject_lookup"])[0]` закрепляется тестом. Читать запрос из
  `dp_search_queries` отвергнуто: `createMany` не гарантирует порядок выборки.

- **Р2. Терпимый парсер + сырой ответ в данных.** Чистый модуль разбирает: единый JSON-объект;
  поток JSON Lines (берётся последний полный объект — по документации каждый следующий содержит
  предыдущий текст); обёртку `{"result": {...}}`; оба регистра полей (`isAnswerRejected` /
  `is_answer_rejected`, `sources` / `links`+`titles` старой формы). Последний разобранный объект
  сохраняется в `rawMetadata` строки-тела (evidence-first, клиенту не рендерится). **После первого
  живого прогона** форма снимается с этого rawMetadata и фикстуры пере-закрепляются — правило
  проекта про арсенкинские фикстуры, применённое заранее. Причина, которая должна пережить план
  (комментарием в модуле): «формат REST-стрима не подтверждён живым ответом; парсер терпим намеренно,
  сузить можно только по сохранённому сырому ответу».

- **Р3. Данные — строками наблюдений, по арсенкинскому образцу.** Успех: строка-тело (тип
  `AI_ANSWER`, синтетический URL `yandex-gen://answer/<hash>`, title
  «Нейро-ответ Яндекса (официальный API): <запрос>», snippet — полный текст) плюс по строке на
  каждый источник из `sources[]` (настоящий URL, title; `used` — в rawMetadata). Измеренная пустота:
  строка-маркер «Нейро-ответ Яндекса: не найден». Отказ модели (`is_answer_rejected`) — тоже
  измеренный факт, печатается словами: маркер «Нейро-ответ Яндекса: ответ не предоставлен — модель
  Яндекса отказалась отвечать на запрос (этические ограничения)»; `NOT_FOUND_PATTERNS` дополняется
  альтернативой `ответ не предоставлен`, чтобы отказ считался измеренной пустотой, а не находкой.
  Новое значение enum `SearchSurfaceType.AI_ANSWER` вместо переиспользования `KNOWLEDGE_BLOCK` —
  осознанно: knowledge_block утащил бы генеративный ответ на страницу «панель знаний» (фолбэк
  `ruKnowledge` в `canonical-visual-assets.ts:747-760`) и подписал бы его чужим именем; цена —
  аддитивная миграция и обход `Record<SearchSurfaceType, …>`-карт (компилятор их сам укажет).

- **Р4. Не-данные — записью о попытке в манифесте, и OK из неё не читается.** Исход вызова
  (`SUCCESS | NO_RESULTS | REJECTED | FAILED | NOT_CONFIGURED`, с `errorCode` и текстом запроса)
  пишется полем `yandexGenAnswerProbe` в `base-collection-manifest.json`. На подготовке отчёта
  в `coverageRows` добавляется ячейка `{region: RU, engine: YANDEX, surface: ai_answer}` **только
  для не-SUCCESS исходов**: измеренный успех доказывают сами строки (и существующие ворота
  `baseCount`/traceability ловят их потерю), поэтому второй ответ «собрано» в манифесте не
  появляется. NO_RESULTS/REJECTED дают измеренную ячейку (страховка от потери маркера), FAILED —
  ячейку сбоя с причиной, NOT_CONFIGURED — «не собиралась» с причиной «провайдер не настроен».
  Старые прогоны без поля ведут себя как раньше — история не переписывается. Это причина, которая
  должна пережить план (комментарий у чтения поля): «OK из манифеста не читается — иначе манифест и
  строки становятся двумя ответами на один вопрос».

- **Р5. Печать: полный текст, честная подпись, источники.** В `ScopedEvidenceIndex` добавляется
  `snippet` (заполняется для `kind === "ai_answer"`), и `buildKnowledgeAiFragment` печатает:
  тело ответа — полным текстом (переносы страниц — существующими continuations), с подписью
  «Ответ генеративного поиска Яндекса, получен официальным Yandex Search API; это не дословный блок
  „Алисы" на странице выдачи» и с запросом; источники — строками «title — domain» (их URL уже в
  evidenceRefs и приложении); маркеры — титулом, как на report-72. Правило продукта держится
  данными: текст ответа — наблюдение с источниками, а не утверждение отчёта; интерпретация — только
  в существующих блоках рамки. Строка-тело распознаётся по данным: kind `ai_answer` + непубличный
  URL + титул не под `NOT_FOUND_PATTERNS` (у источников URL публичные, у маркеров — паттерн).
  Визуальная панель предпочитает строку-тело как summary; её однострочная обрезка остаётся
  (вне границ), полноту несёт текст страницы.

- **Р6. Сводка перестаёт спорить со слайдами.** Пробел покрытия по NOT_COLLECTED-ячейке не
  печатается, если у той же пары «регион + поверхность-группа» есть измеренная ячейка; группировка —
  той же функцией `normalizeCoverageSurface`, которая дополняется приведением `knowledge_block` →
  `ai_answers` (ровно так группирует анализатор поверхности — два грейдера начинают мерить одной
  линейкой). `googleAnswerProbeHints` начинает считать «отвеченность» региона по-движково (ответ
  Яндекса не гасит факт «Google спрошен, ответа нет»).

- **Р7. Разрешение — ключ.** Никаких новых флагов и переменных: без `YANDEX_SEARCH_API_KEY` /
  `YANDEX_SEARCH_FOLDER_ID` вызов не делается, probe получает `NOT_CONFIGURED` с причиной из
  `configKeyDefects`. Вызов происходит только внутри живого базового сбора, который запускает
  владелец; офлайн-контур (`fixtureBaseRows`, отсутствие prisma) пробу пропускает так же, как
  пропускает остальной сбор.

## Что должно быть протестировано

Все пункты — офлайн (без сети, без базы: это условие `npm run ci`), уровень — vitest в
`tests/unit/`, если не сказано иное. Красными первыми пишутся 1–4 и 8–10.

1. **Парсер терпим к формам ответа**: единый JSON; JSON Lines из трёх нарастающих чанков (берётся
   последний); `{"result": {...}}`-обёртка; snake_case-поля старой формы (`is_answer_rejected`,
   `links`+`titles` → источники без потери URL). Неверный ответ (не-JSON, пустой, сверх лимита
   размера) — типизированная ошибка, не исключение сквозь стек. Ошибкой было бы: взять первый чанк
   (обрезанный текст) или уронить разбор на camelCase.
2. **Тело запроса**: messages ровно один, ROLE_USER, текст — дословно запрос; folderId и searchType
   присутствуют; `site/host/url`, `fixMisspell`, `enableNrfmDocs` отсутствуют. Ошибкой было бы:
   любое «полезное» поле сверх контракта — оно меняет вопрос, который мы задаём.
3. **Разрешение — ключ**: без ключа/каталога — `NOT_CONFIGURED` с причиной, **fetch не вызывался**
   (шпион); с ключом-заглушкой (`<<<FILL>>>`) — то же через `configKeyDefects`.
4. **Строки по исходам** (`collectYandexGenAnswer`): успех → тело (тип AI_ANSWER, непубличный URL
   схемы `yandex-gen://`, полный текст в snippet, честный титул с запросом) + по строке на источник
   с настоящим URL и титулом; `is_answer_rejected` → один маркер «ответ не предоставлен…», ноль
   источников; пустой текст без отказа → маркер «не найден»; FAILED → ноль строк, probe FAILED с

   строка-«сбой» в наблюдениях (сбой — не измерение).

6. **Слияние**: базовая строка типа AI_ANSWER получает `surface: "ai_answer"`, engine YANDEX,
   provider yandex; тело и источники не схлопываются с органикой того же URL.

   второй ответ на «собрано ли».
8. **Страница с ответом**: полный текст напечатан дословно и без обрезки (вход длиннее 300 символов

## Риски и что может сломаться молча

- **Формат живого ответа отличается от документации** — главный риск. Парсер терпим, но если REST
  отдаёт что-то третье (например, SSE с префиксом `data:`), проба уйдёт в FAILED. Это не молчание:
  страница скажет «сбор сорвался», probe сохранит код, rawMetadata тела не будет. Снятие формата с
  первого живого прогона — обязательный след шага, записан в «Глобальное тестирование».
- **Доступ к gen-поиску на аккаунте не подтверждён**: старая документация требовала роль
  `search-api.executor` и Preview-доступ по форме. Возможный первый исход — 403, честно видимый как
  сбой с причиной. Действие владельца названо в приёмке.
- **Два ответа на «собрано ли»** — закрыто правилом «OK из манифеста не читается»; тест 7 держит.
- **Кэш секций** — исправление построителей молча не доедет без подъёма `DECK_CONTENT_VERSION`;
  тест отпечатка ловит, пункт плана 7 напоминает.
- **Отказ модели, прочитанный как пустота выдачи** — слова маркера различают («ответ не
  предоставлен — модель отказалась» vs «не найден»), паттерн расширен осознанно; тест 9.
- **Расширение `NOT_FOUND_PATTERNS`** задевает `assembly-validation` (строки-маркеры не считаются
  данными). Направление честное — отказ и есть не-данные, — но проверить тестом 9, что страница с
  одним отказом не превращается в `coverage-empty-state` с потерей слов отказа.
- **Ответ Яндекса пересказан GPT-стадиями как факт о субъекте** — существующий контур (текст —
  наблюдение; статусные строки и «почему выделено» GPT не трогает), но новый длинный текст в
  claims/units увеличивает соблазн; подпись и рамочные блоки — из детерминированного билдера,
  закреплены эталоном текста. Отдельной защиты не добавляем; риск назван.
- **Потеря строк на пути к деке** — строки едут в манифесте, существующие ворота
  `compositeBaseCount ≥ baseCount` и traceability ловят потерю как и для прочих базовых строк.
- **Синтетический URL утёк клиенту как источник** — `publicDomainOf` уже отбрасывает не-http схемы;
  тест 8 проверяет, что тело не значится в «Источниках».
- **Повторный сбор кейса**: дедуп по `dedupHash` (тип|источник|url|запрос|титул) устойчив — hash
  синтетического URL детерминирован от запроса; пропущенные дубликаты доезжают через
  `caseCorpusSurfaceItemIds`. Но **изменение титула** строки-тела в будущем породит вторую строку на
  том же кейсе — причина держать титул стабильным, записана комментарием у формирования титула.
- **Цена**: один запрос ≈ единицы рублей за прогон; спенд не начинается сам — вызов живёт только в
  живом базовом сборе, который запускает владелец.

Команды, которые обязаны быть зелёными на чистой машине:

```bash
npm run ci

npx tsx scripts/run-orion-deck-sections-report72.ts
python3 renderer/smoke_deck_raster_layout.py
```

Наблюдаемые исходы сверх команд:

- диф `fixtures/golden-case/client-text.baseline.json` прочитан на ревью и содержит ровно: полный
  текст нейро-ответа с подписью про официальный API, строки источников, отсутствие «ответы ИИ-поиска
  (RU/UAE)» в ограничениях там, где поверхность измерена;
- `npm run db:migrate` создал одну аддитивную миграцию; `npm run db:audit` на локальной базе чист.

**Что нельзя проверить без платного прогона (увидим только завтра):**

1. фактическую форму REST-ответа `/v2/gen/search` (JSON Lines / обёртка / регистр полей) — после
   прогона снять из rawMetadata строки-тела и пере-закрепить фикстуры парсера;
2. доступность gen-поиска на нашем сервисном аккаунте (роль `search-api.executor` / статус Preview)
   — при 403 действие владельца: выдать роль в консоли Yandex Cloud;
3. фактическую цену запроса (сверить со страницей тарифов аккаунта);
4. сам ответ по субъекту, его длину, вёрстку страницы с продолжениями и вид SVG-панели;
5. поведение `is_answer_rejected` на реальном лице.

Сводка для владельца: клиентский текст — **меняется** (эталоны обновляются, диф — материал ревью);
число страниц — может вырасти на продолжения при длинном ответе; `DECK_CONTENT_VERSION` —
**поднимается**; схема БД — **меняется** (одно значение enum, аддитивная миграция); переменные
окружения — **не меняются**.
