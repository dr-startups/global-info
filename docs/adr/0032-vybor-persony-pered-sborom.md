# Шаг 0032. Выбор персоны перед сбором: панель различимых тёзок из собственных источников

## Что увидит владелец

Оператор вводит данные субъекта как обычно — ФИО и дату рождения, — но кнопка запуска сбора
теперь ведёт сначала в выбор персоны. Система за несколько секунд опрашивает уже подключённые
источники (Википедию на двух языках, панель знаний Google, санкционные и PEP-списки) и
показывает карточки различимых людей с таким именем: у карточки из Википедии — заголовок
статьи (русская Википедия сама разводит тёзок уточнением в скобках: «Петров, Иван
(предприниматель)» против «(футболист)») и первая строка статьи, которая у персон почти
всегда несёт полную дату рождения; у карточки из панели знаний — название, описание и фото;
у карточки из санкционных списков — имя записи, дата рождения и темы (санкции, PEP) с
процентом совпадения. Введённая оператором дата рождения напечатана над карточками — сверить
её с датой на карточке можно одним взглядом. Оператор либо отмечает «это он» на одной
карточке, либо явно отвечает «различимой персоны нет — продолжить»: например, субъект — не
публичная фигура и в этих источниках не представлен. После любого из двух ответов запуск
открывается; до того система запуск не принимает и объясняет почему. Если оператор потом
правит ФИО или дату рождения, подтверждение снимается и выбор запрашивается заново. Отказ
любого источника панель называет словами, и оператор всё равно может продолжить — его
решение и причина записываются.

Whitebridge в продукт не входит (решение владельца 25.08.2026): он не принимает дату
рождения ни на одном входе, не даёт меры уверенности ни на одном поле, а его платный отчёт
($13–19 за отчёт по месячным тарифам) заказывается по уже выбранному кандидату — то есть не
помогает выбрать. Панель собирается из источников, которые уже оплачены и подключены; одна
проверка стоит порядка цента (два запроса Serper; Википедия бесплатна; OpenSanctions — в
рамках имеющегося ключа). Новых ключей и настроек не появляется.

## Задача и границы

Постановка владельца (25.08.2026, дословно): «я создаю новый кейс, пишу Петров Иван
Иванович, дату рождения (рассчитываю, что мне попадется определенное публичное лицо). Но,
т.к. оказалось много совпадений по ФИО, предполагаемое мной публичное лицо не попало в
отчет, а попал рандомный человек». Задача — различение однофамильцев **до первой траты**:
показать оператору две-три различимые персоны с приметами и получить явный выбор.

В объёме:

- панель различимых персон из трёх уже написанных источников: Википедия (ru/en, кандидаты с
  лидами), Serper (Knowledge Graph + органика), OpenSanctions (`/match` с датой рождения);
- серверные ворота: новый платный прогон не создаётся, пока решения нет; решение привязано
  к содержимому данных субъекта (ФИО, алиасы, дата рождения), а не к факту нажатия;
- запись снимка панели и решения в базу и в аудит-лог;
- снимок выбранной персоны с машиночитаемыми якорями — для второй половины.

Явно вне объёма:

- **Whitebridge целиком** — не «отложен», а не входит (решение владельца 25.08). Причины —
  в «Контексте»; они записываются в ENGINEERING, чтобы инструмент не переоткрыли;
- **влияние выбранной персоны на последующий сбор** — вторая половина задачи, отдельный
  шаг со своим планом. Обязательство перед ней здесь одно: шаг сохраняет в базе снимок
  выбранной карточки с якорями (см. «Решение»), чтобы вторая половина пользовалась ими,
  не пересобирая панель и не переделывая первую;
- машинная склейка сущностей **между** источниками (статья ↔ KG ↔ запись OpenSanctions) и
  мультивыбор нескольких карточек как «это всё он» — v1 обходится без обоих (причины в
  «Решении»);
- парсер дат рождения из прозаического текста;
- Яндекс в составе среза: панель различает энциклопедическими сущностями, а не выдачей;
  вторая органика удвоила бы шум вспомогательного блока, не добавив ни одной сущности.
  Добавить его позже дёшево, если покрытия Serper не хватит;
- поиск по email/телефону субъекта — как и в прежней редакции, отдельным решением.

## Контекст

### Почему не Whitebridge — факты, на которых принято решение

Проверено по документации 25.08.2026 (живых вызовов не было; ключа нет):

- **Дата рождения — сильнейший различитель, который владелец уже вводит, — не принимается
  нигде.** `GET /search`: вход — `query` («name, email, phone, or social media URL») плюс
  обязательная соцплощадка `type`; кандидат ответа — `candidateId`, `avatarUrl`, `fullName`,
  `fragments` — даты нет (`docs.whitebridge.ai/search-candidates.html`). `POST /lookups`,
  объект `candidate` — только `fullName`, `avatarUrl`, `email`, `sources`, `fragments`;
  полей даты рождения, возраста, места нет (`create-lookup.html`, проверено целевым
  запросом). Год рождения существует только **в ответе** платного отчёта — узнать его можно,
  лишь купив отчёт о каждом тёзке.
- **Меры уверенности нет ни на одном поле** ни в поиске, ни в отчёте (`get-lookup.html`).
- **Платный отчёт заказывается по уже выбранному кандидату** — выбор тёзки стоит до него и
  им не решается.
- **Цена** (`whitebridge.ai/pricing`, снято 25.08.2026): единица — кредит, один полный
  lookup списывает кредит («deducts credit», `create-lookup.html`); месячные планы —
  $19/мес за 1 кредит/мес, $35/мес за 2, $65/мес за 5 (то есть $13–19 за отчёт); годовые —
  $9–12 за отчёт. Бесплатного объёма нет. Тарификация `GET /search` не публикуется.
  Вилка «$8–17» из первой редакции плана ни одной страницей не подтверждена.

### Репозиторий — что подтверждено кодом (HEAD `ef8bdb6`)

Всё, из чего строится панель, уже написано:

- **Википедия** — `providers/wikipedia-provider.ts`: публичный `wikipediaProvider.lookup(...)`
  (используется `agents/real/real-wikipedia-agent.ts:96`); внутри `lookupLanguage`
  (строки ~318–380): один поиск `list=search&srlimit=5` даёт до пяти кандидатов
  (`candidates: WikipediaCandidate[]` — title, pageId, snippet — **уже возвращаются
  наружу** в `WikipediaLanguageResult`), `pickWikipediaCandidate` выбирает одного, для него
  тянутся REST-сводка и полный плейнтекст `articleText`. Склейка ru↔en —
  `resolveByLanglink`: межъязыковая ссылка — утверждение самой Википедии о том, что это
  одна сущность, не наша догадка (комментарий в коде, наблюдение Мордашова: en-поиск дал
  дизамбигуацию, langlink дал статью). **Измеренный факт из комментария к `articleText`

  исчезла дата рождения.** Лид для карточки обязан браться из `articleText`.
  Транслитерация имени уже есть (`hasCyrillic`, `transliterateRuToEn` из

- **Serper** — `providers/serper-surfaces.ts`: `serperOrganicWithExtras` (строка 137) за

  title, description/type, imageUrl (строки 198–218).
- **OpenSanctions** — `compliance-providers/open-sanctions-provider.ts:75`:
  `POST /match/{dataset}`; тело строит `buildOpenSanctionsMatchBody`
  (`open-sanctions-mapping.ts`): **`birthDate` уже уходит в запрос** (строки 51–52,
  `normalizeBirthDate` — `YYYY-MM-DD` или `YYYY`), все формы имени — многозначным `name`;
  ответ несёт `score` и `topics`, пороги — `confidenceFromScore` (128–130: ≥0.9 HIGH,
  ≥0.8 MEDIUM), русские ярлыки тем — `RISK_TYPE_LABEL_RU`.
  **`runComplianceScreening` (`compliance-providers/service.ts:119`) панели не подходит**:
  он рождает комплаенс-находки (`COMPLIANCE_FINDING_OWNER = "compliance-layer-v1"`), а

  напрямую и находок не создаёт.
- **Субъект**: `Subject.dateOfBirth` — `DateTime?` (`prisma/schema.prisma`, модель
  `Subject`); также `fullName`, `aliases[]`.
- **Старт сбора**: `POST /api/digital-profile/cases/[id]/unified-collection`
  (`route.ts:60–77`, guards `agents.run`/`agents.runReal`/`requireCaseAccess`) →
  `startUnifiedOrionCollection`
  (`services/unified-orion-collection-orchestrator.ts:548`): ветки resume/recover
  (~557–599), затем `findOrCreateUnifiedCollectionJob` (~602) — **новый платный прогон
  рождается ровно здесь**, других мест нет. Кнопки: `client/CaseDetailView.tsx:265` и
  `:290` (`confirmPaidRecollection`) через `client/api.ts:1429`.
- **Правило, с которым граничит задача**, дословно (ENGINEERING.md:1013–1014, проверено на
  HEAD): «**Пользователь не должен дожимать прогон руками.** Система ждёт сама и сама
  повторяет. Если человеку предлагают кнопку — значит, мы чего-то не доделали».
- **Родственный принцип** (ENGINEERING §1): «Совпадение по комплаенсу не подтверждается

- `Case.isFixture` (schema.prisma:225) — смоковые кейсы офлайн-контура.
- `buildSubjectFingerprint` (`evidence-quality/subject-fingerprint.ts`) отвечает на другой

### Цена одной проверки

2 запроса Serper (доли цента; тарифы Serper на лендинге не публикуются, порядок — доллар за
тысячу) + до ~12 бесплатных вызовов Википедии (2 поиска + лиды кандидатов + langlinks) +
1 `POST /match` OpenSanctions в рамках уже оплачиваемого ключа. Итого — порядка цента.
Всё — по кнопке оператора; автоматических запусков нет.

## Решение

### Ворота до прогона, а не шаг конвейера

Выбор персоны — **состояние кейса до первой траты**, а не строка `dp_workflow_steps`:

- пока решения нет, прогона не существует — нечему жечь `maxAttempts`, нечему держать лизу,
  нечему «выглядеть зависшим», деплой ничего не прерывает: состояние — строка в таблице;
- оператор не решает сутки/неделю/никогда — не тратится ничего; кейс виден в админке со
  статусом «ожидает выбора персоны»;
- правило «расписание — в базе» относится к исполняемой работе; здесь работы нет — есть
  ожидание человека, закодированное данными (строка решения), а не таймером.

Отвергнутая альтернатива — шаг `SUBJECT_VERIFICATION` в конвейере: потребовал бы бессрочного
`maxWaitMs` (ломает смысл бюджета ожидания) и показывал бы «идущий» прогон, который ничего
не делает. Причина, которую надо сохранить при переносе в ENGINEERING: **ворота до первой
траты — часть постановки задачи, а не кнопка посреди оплаченной работы**; правило 1013
говорит о начатом прогоне. Уточнение правила — готовым текстом в последнем разделе.

### Панель различимых персон: карточка — сущность источника, а не наша склейка

Главный принцип: **панель группирует по людям, но группировку даёт источник, чьи записи —
люди; мы не изобретаем свою.** Одна статья Википедии — один человек (дизамбигуация —
работа самой Википедии, включая уточнение в скобках в заголовке); одна запись OpenSanctions —
один человек; панель знаний Google — одна сущность на запрос. Карточки:

- **Википедия** (основная секция): заголовок статьи, **полная первая строка лида из
  `articleText`** (у персон она почти всегда несёт дату рождения и род занятий; REST-сводка
  не годится — она срезала дату Мордашова), ссылка на статью, язык. Русская и английская
  статьи объединяются в одну карточку **только по langlink** — это утверждение источника о
  тождестве, механизм уже написан. Лиды тянутся для первых трёх кандидатов каждого языка;
  хвост (4-й, 5-й) показывается заголовком и сниппетом поиска, лид дотягивается кликом
  (один бесплатный вызов).
- **Панель знаний Google** (по одной на каждую из ≤2 форм имени): название, описание/тип,
  фото по `imageUrl` (URL строкой, файл не сохраняется).
- **OpenSanctions**: имя записи, **структурная дата рождения записи**, русские ярлыки тем
  (санкции, PEP, розыск), процент совпадения (`score`), порядок — по score.
- **Вспомогательный блок «Выдача»** (не карточки): топ органики Serper с доменами и
  заголовками — контекст для случая, когда тёзка публичен «в среднем» и в энциклопедические
  источники не попал.

Введённая владельцем дата рождения печатается над панелью. **Подсветка «дата совпала» есть
только у карточек со структурной датой (OpenSanctions).** Даты из прозы (лид Википедии) не
парсятся и не подсвечиваются — сравнивает человек. Причина, которую надо сохранить:
эвристика над прозой ошибается молча, и неверно распарсенная дата с зелёной подсветкой —
тихая ложь, хуже отсутствия подсветки; полная строка лида честнее.

Отвергнутые альтернативы (обе — до измеренной нужды, не навсегда):

- **автосклейка карточек между источниками** (статья ↔ KG ↔ запись) — любая эвристика
  тождества здесь и есть второй ответ на вопрос принадлежности, главный сорт дефектов
  проекта; склейку делает глазами оператор, источники стоят рядом;
- **мультивыбор** («эта статья и эта запись — один мой человек») — усложняет решение,
  снимок и вторую половину; полный сбор всё равно прогонит OpenSanctions по ФИО+ДР, так
  что санкционный якорь не теряется. Если одной карточки окажется мало — отдельное
  расширение.

Состояния панели: **одна карточка** — всё равно ждёт клика, никакого автовыбора (тот же
класс, что PENDING по комплаенсу); **ноль карточек** — словами «различимых персон не
найдено», причина по каждому источнику (не настроен / не нашёл / отказ), явное «продолжить
без выбора»; **много (6+)** — секции по источникам в порядке источника, хвост Википедии
свёрнут. Пустая панель — валидный результат, не ошибка.

**Выбор карточки OpenSanctions — не подтверждение комплаенс-совпадения.** Панель отвечает
«про кого собирать», скрининг 04.3 в прогоне идёт своим чередом и рождает находки `PENDING`
аналитику, как сегодня. Чтобы вопросы не смешались и находки не задвоились, срез зовёт
`openSanctionsProvider.screenPerson` напрямую, минуя `runComplianceScreening`.

### Ворота применяются всегда: режима NOT_CONFIGURED больше нет

Отличие от прежней редакции: там разрешением был ключ Whitebridge, и без ключа шага не
существовало. Срез не требует нового внешнего контракта — Википедия работает без ключа
вовсе, Serper и OpenSanctions уже ключи сбора. Поэтому на реальном кейсе ворота применяются
**всегда**; несконфигурированность или отказ отдельных источников деградирует панель
словами (правило «разрешение — ключ» продолжает действовать на уровне каждого источника),
а путь «продолжить без выбора» существует всегда. Режимы предиката: `CONFIRMED | PENDING |
STALE | FIXTURE_BYPASS`. Следствие, которое надо объявить владельцу: **существующие кейсы
после миграции потребуют решения при следующем новом прогоне** (включая платный перезапуск
`confirmPaidRecollection`) — это не регрессия, а ровно сценарий постановки: перезапуск по
неподтверждённой персоне и есть то, от чего ворота защищают. Ветки resume/recover идущей
джобы ворот не проходят.

### Приятное следствие: юридическая граница исчезла вместе с инструментом

Срез строится провайдерами, чьи данные и так попадают в отчёт с URL и доменом. Вопрос
«как не дать данным панели утечь в отчёт банку» больше не существует — не потому что решён,
а потому что исчез вместе с Whitebridge: у панели нет ни одного источника, которого нет у
отчёта. Снимок панели (`personasJson`) при этом в отчёт не читается — он вход только
админ-панели и предиката ворот, — но это отсутствие пути данных, а не правило продукта со
сторожем. Растяжка в `internal-code-scan.ts` не заводится, **построители деки не меняются
вообще, `DECK_CONTENT_VERSION` не двигается, диффа эталонов у шага нет** — появление диффа
означает ошибку.

### Данные — новая таблица `dp_subject_persona_checks`

Одна строка = одна сборка панели (снимок карточек) плюс, возможно, решение по ней:

- `id`, `caseId` (FK Case, onDelete Cascade), `subjectId`;
- `subjectInputHash` — SHA-256 нормализованных `fullName` + отсортированных `aliases` +
  **`dateOfBirth`** (нормализация имён: trim, нижний регистр, схлопывание пробелов, `ё→е`;
  дата — ISO `YYYY-MM-DD` или пустая строка). Дата рождения вошла в хеш, потому что стала
  различителем: правка ФИО **или даты рождения** снимает подтверждение;
- `requestJson` — формы имени, языки, регион;
- `personasJson` — снимок панели: карточки по источникам (Википедия: заголовки, URL,
  первая строка лида, langlink-пары; KG: название, описание, `imageUrl` строкой;
  OpenSanctions: id записи, имя, дата рождения, темы, score; выдача: топ доменов и
  заголовков) и статус каждого источника (`SUCCESS | NOT_CONFIGURED | FAILED` + код);
- `fetchStatus` — `SUCCESS` (хотя бы один источник ответил) | `FAILED` (ни один),
  `errorCode`;
- `searchedBy`, `searchedAt`;
- решение (nullable, пока его нет): `decision` — `PERSONA_SELECTED |
  APPROVED_WITHOUT_PERSONA`, `selectedPersonaJson` — **снимок выбранной карточки с
  якорями**, `decidedBy`, `decidedAt`;
- `@@index([caseId, searchedAt])`, `@@map("dp_subject_persona_checks")`.

**Якоря в `selectedPersonaJson` — обязательство перед второй половиной**: `source`
(`wikipedia | knowledge_graph | opensanctions`), для Википедии — заголовки и URL статей по
языкам (обе, если склеены langlink), для OpenSanctions — id сущности, для KG — название,
описание и `imageUrl`; плюс полный снимок карточки, как её видел оператор. Вторая половина
берёт якоря отсюда и не пересобирает панель.

**Предикат ворот выводится из данных**: «подтверждено» ⇔ существует строка с
`decision != null` и `subjectInputHash`, равным хешу текущих данных субъекта. Оператор
поменял ФИО или дату рождения — хеш разошёлся, ворота снова закрыты. Статуса «отклонено»
нет: не тот человек → оператор правит данные и ищет заново; терминальна только явная форма
согласия. Решение по строке неизменяемо — новое решение только новой сборкой панели.
Ошибка в сторону строгости намеренная: любое редактирование субъекта снимает решение, даже
косметическое; цена — лишний клик, альтернатива — прогон по данным, которых оператор на
панели не видел.

### Поток

1. Оператор жмёт «Выбрать персону» (или «Начать сбор» без решения — UI ведёт в выбор).
   `POST /cases/[id]/identity-check` собирает панель **синхронно** (худший случай ограничен
   таймаутами провайдеров; фонового исполнителя не заводим — прогона нет, нечему держать
   шаг, кнопка повторяема): ≤2 форм имени × Serper, Википедия ru+en с лидами трёх
   кандидатов на язык, один `POST /match` с ФИО+алиасами+датой рождения. Пишет строку со
   снимком. Пустая панель — валидный результат.
2. Панель в `CaseDetailView` — секции и состояния из «Решения». Две операции: «Это он» (по
   одной карточке) и «Различимой персоны нет — продолжить» (явное решение без карточки).
3. `POST /cases/[id]/identity-check/decision` записывает решение (guards как у старта:
   `agents.run` + `agents.runReal` на реальном контуре) и строку в `AuditLog`.
4. `startUnifiedOrionCollection` перед `findOrCreateUnifiedCollectionJob` (только на пути
   создания **нового** джоба) спрашивает предикат `identityGateState`:
   - `case.isFixture` → `FIXTURE_BYPASS`, старт (офлайн- и смоковые прогоны не требуют
     человека);
   - решения нет → `PENDING` → `ConflictError` с кодом `IDENTITY_NOT_CONFIRMED` и
     человеческим текстом; job не создаётся;
   - решение есть, хеш разошёлся → `STALE` → тот же отказ;
   - решение есть, хеш совпал → `CONFIRMED`, старт.
   Проверка живёт в **одном** месте — в сервисе; маршрут только транслирует 409. UI-запрет
   ничего не гарантирует.
5. Отказ источников (`fetchStatus: FAILED`, сеть, 429): панель показывает причины и даёт то
   же явное «продолжить без выбора» с фиксацией автора — отказ внешних сервисов не
   парализует продукт (тот же принцип, что `COMPLETED_PARTIAL`). Решение фиксируется со
   ссылкой на строку исходной попытки.

### Чего срез не различит — честные границы

- Тёзки, **оба** отсутствующие в Википедии, панели знаний и санкционных списках, — панель
  почти пуста, различать нечем; остаётся блок выдачи (домены, сниппеты) и решение человека.
- Фотографии нет нигде, кроме панели знаний: у персоны без KG карточка текстовая.
- Персона со статьёй только на третьем языке (не ru/en) не найдётся — расширение языков
  отдельным решением, если случится на практике.
- Свежая публичность: статья ещё не написана, KG не собран.
- Панель не проверяет, что выбранная карточка — действительно тот, кого имел в виду
  владелец кейса: она даёт приметы для различения, решает и ошибается человек.

## План реализации

1. **Схема**: модель `SubjectPersonaCheck` в `prisma/schema.prisma` (поля из «Решения»),
   связь из `Case`. ⚠️ Меняет `prisma/schema.prisma` — следом новая миграция. Готово, когда
   `npm run db:*`-контур видит таблицу, а `ci:full`-сверка схемы зелёная.
2. **Расширение WikipediaProvider** (`providers/wikipedia-provider.ts`): публичный метод,
   возвращающий для языка кандидатов поиска с лидами первых N из `articleText` (сегодня
   `lookupLanguage` тянет лид только для одного выбранного `pickWikipediaCandidate`).
   Поведение существующего `lookup(...)` для сбора не меняется. Готово: юнит на моках
   fetch — лид карточки взят из `articleText`, не из REST-сводки; ни одного сетевого
   вызова в офлайн-контуре.
3. **Сервис**: `services/subject-persona-check.ts` — формы имени (транслитерация из
   `orion-query-plan`), вызовы: Википедия (п. 2), `serperOrganicWithExtras` (≤2 запросов),
   `openSanctionsProvider.screenPerson` напрямую (не `runComplianceScreening` — панель не
   рождает находок); сборка `personasJson` с статусами источников; `subjectInputHash` с
   датой рождения; предикат `identityGateState(caseId)` → `{ mode: "CONFIRMED" | "PENDING"
   | "STALE" | "FIXTURE_BYPASS", … }` — **единственный ответ** на вопрос ворот.
4. **Ворота**: `services/unified-orion-collection-orchestrator.ts` — вызов предиката перед
   `findOrCreateUnifiedCollectionJob`, `ConflictError("IDENTITY_NOT_CONFIRMED…")`. Ветки
   resume/recover не проходят через ворота (проверить тестом).
5. **Маршруты**: `src/app/api/digital-profile/cases/[id]/identity-check/route.ts`
   (POST — сборка панели, GET — состояние и снимок) и `identity-check/decision/route.ts`
   (POST — решение). Guards зеркалят маршрут старта; решение — в `AuditLog`
   (паттерн `services/search-surface-service.ts`).
6. **Клиент**: функции в `client/api.ts`; панель персон в `client/CaseDetailView.tsx`
   (секции, состояния «одна/ноль/много», причины отказов словами, введённая дата рождения
   над карточками); кнопка старта показывает причину блокировки из ответа 409.
7. **ENGINEERING.md** — по разделу «Что переедет» (тем же коммитом закрытия шага).

Шаг **не трогает**: построители деки и `deck-sections/` (отпечаток не двигается,
`DECK_CONTENT_VERSION` на месте, диффа эталонов нет), `config/defaults.ts` (ни одной новой
настройки), `config/env-validation.ts` и `.env.example` (ни одного нового ключа).

## Что должно быть протестировано

Офлайн (vitest, `tests/unit/`, мок Prisma, ни сети, ни базы — условие `npm run ci`):

- **Предикат ворот**: (а) решения нет → `PENDING`, старт отвергнут 409
  `IDENTITY_NOT_CONFIRMED`, job в базе не появился; (б) решение есть, хеш совпал →
  `CONFIRMED`, старт; (в) после решения отредактировано ФИО **или дата рождения** →
  `STALE`, старт снова отвергнут; (г) `case.isFixture` → старт при любом состоянии;
  (д) существующая джоба в `WAITING`/восстановимая — те же ответы, что до шага, ворота не
  спрашиваются. Неверный ответ выглядит как «изменённый субъект стартует по старому
  решению». Мутационная точка для ревьюера: снять сравнение `subjectInputHash` — краснеет
  (в).
- **Хеш**: перестановка алиасов, регистр, двойные пробелы, `ё/е` — стабилен; смена фамилии —
  другой; смена даты рождения — другой; дата `null` и дата заполненная — разные.
- **Сборка панели**: моки трёх источников → карточки строго по сущностям источников;
  ru+en статьи склеены в одну карточку только при langlink, без langlink — две; KG —
  отдельной карточкой; OpenSanctions отсортирован по score и несёт структурную дату и
  русские ярлыки тем; отказ одного источника → панель собрана из остальных,
  отказ назван словами с кодом у источника; отказ всех → `fetchStatus: FAILED`, пустая
  панель с причинами — валидное состояние, не исключение.
- **Лид карточки Википедии — из `articleText`**: фикстура, где REST-сводка без даты в
  скобках, а `articleText` с датой → карточка несёт полную строку с датой. Мутационная
  точка: подменить источник лида на сводку — тест краснеет. (Это прямая защита от
  возвращения бага Мордашова.)
- **Даты из прозы не парсятся**: признак «дата совпала» есть только у карточек со
  структурной датой (OpenSanctions); у карточек Википедии его нет ни при каком тексте лида.
- **Панель не рождает комплаенс-находок**: после сборки среза в моке Prisma ноль новых
  находок. Мутационная точка: заменить вызов на `runComplianceScreening` — тест краснеет.
- **Никакого автовыбора**: одна карточка в снимке — состояние всё ещё `PENDING`.
- **Решения**: выбор карточки пишет `selectedPersonaJson` со всеми якорями (для
  Википедии — URL и заголовки обоих языков склеенной карточки; для OpenSanctions — id
  сущности) и автора; «продолжить без выбора» пишет решение без карточки и принимается
  также по строке с `fetchStatus: FAILED`; повторное решение по той же строке отвергается
  (решение неизменяемо); guards ролей на обоих маршрутах.
- **Провайдеры в офлайне**: ни одного сетевого вызова (мок-счётчик fetch); ключи не
  встречаются ни в одном сохраняемом JSON.

Смок (офлайн-tier в `scripts/run-smokes.ts`): кейс → сборка панели (мок-источники) →
решение → старт прогона проходит; без решения — старт отбит 409. Кейс смока создаётся
**без** `isFixture`, иначе обход по фикстуре сделает проверку пустой — пропуском, который
выглядит как pass.

## Риски и что может сломаться молча

- **Второй ответ на вопрос ворот.** Проверка и в route.ts, и в сервисе разойдётся при
  первом рефакторинге. Ответ один — `identityGateState`; маршрут транслирует 409.
- **Автосклейку «дочинят».** Карточки одного человека из разных источников выглядят как
  дубль, и будущая «оптимизация UX» склеит их эвристикой — вторым ответом на вопрос
  принадлежности. Причина запрета — комментарием в сервисе и строкой в ENGINEERING.
- **Парсер дат вернут.** «Подсветим совпадение и у Википедии» — неверно распарсенная дата
  с зелёной подсветкой это тихая ложь. Причина — там же.
- **Выбор санкционной карточки прочитают как подтверждённый комплаенс-хит.** Разделение
  вопросов записано в ENGINEERING §1; скрининг 04.3 рождает PENDING как раньше; панель
  находок не создаёт (закреплено тестом).
- **Лид из REST-сводки.** Упрощение «сводки хватит» молча вернёт исчезнувшие даты рождения
  (прецедент Мордашова измерен). Закреплено тестом с мутационной точкой.
- **Fixture-щель.** Ворота обходятся по `isFixture`; живой кейс, ошибочно созданный
  фикстурным, проскочит без выбора. Проверить, что операторская форма флаг не выставляет.
- **Тихая трата.** Serper платный (доли цента, но платный): срез только по кнопке
  оператора, ни на какие автоматические события не вешается.
- **Старые кейсы.** После миграции следующий новый прогон любого существующего кейса
  потребует решения. Не регрессия, а сценарий постановки — объявить владельцу при закрытии
  шага, чтобы первый же 409 не выглядел поломкой.
- **Пустая панель у непубличного субъекта.** Для не-медийных людей панель будет часто
  пуста, и гейт выродится в клик «продолжить без выбора». Это честное состояние (пустота
  названа словами и решение записано), но если так пойдут почти все кейсы — ценность фичи
  падает; выяснится практикой, лечится расширением источников, а не ослаблением ворот.

## Глобальное тестирование после шага

- `npm run ci` и `npm run build` зелёные (офлайн).
- `npm run ci:full` — миграция накатывается, сверка схемы зелёная.
- Диффа эталонов (`golden-case`, `report-72`) **нет вообще**; ворота деки и растр не
  запускаются — шаг не касается отчёта. Появление диффа — сигнал ошибки.
- **Первый живой прогон панели — отдельное разрешение владельца** (трата — порядка цента,
  но правило про живые вызовы то же). Шаг закрывается на моках, и это объявляется в ревью
  как место, где проверка слабее обычного. Пункты приёмки живого сеанса:
  1. Кейс с кириллическим ФИО известного тёзки: панель показывает ≥2 различимые карточки
     Википедии, первая строка лида несёт дату рождения.
  2. KG-карточка на латинской форме имени с фото.
  3. OpenSanctions-карточка с датой рождения и score при введённой дате.
  4. Выбор карточки → старт открывается; правка даты рождения → старт снова закрыт (STALE).
  5. Пустой случай: вымышленное редкое ФИО → панель словами называет «не найдено» по
     каждому источнику, «продолжить без выбора» работает.
