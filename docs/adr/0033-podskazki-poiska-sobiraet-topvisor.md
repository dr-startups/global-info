# Шаг 0033. Поисковые подсказки собирает Топвизор

## Задача и границы

Владелец, дословно: «я хотел бы, чтобы подсказки гугл/яндекс формировал топвизор, и всё».

В объёме:

- новый провайдер `topvisor` (официальный API v2) и новый шаг конвейера
  `SUGGESTIONS_COLLECTION`, который собирает те же три поверхности подсказок, что сегодня:
  RU Яндекс, RU Google, ОАЭ Google;
- **замена, а не соседство**: инструмент `suggest` уходит из Arsenkin-слоя целиком, вызов
  autocomplete у Serper в базовом сборе прекращается (второй источник подсказок — главная
  форма дефектов проекта; владельцем сказано «и всё»);
- статус и причина пустоты подсказок в кабинете и в деке выводятся из нового шага.

Явно вне объёма:

- прочие инструменты Топвизора (позиции, частота, кластеризация, AI-трекер) — не просили;
- расширение состава подсказок (генераторы перебора, глубина >1) — по умолчанию паритет с
  сегодняшним объёмом; включение генераторов — открытый вопрос владельцу №2, но не условие
  шага;
- прочие Arsenkin-агенты (`check-top`, `paa`) не трогаются.

## Контекст

### Чем подсказки собираются сегодня — по коду

Два канала, и оба существуют одновременно:

1. **Arsenkin, инструмент `suggest`** — выделенный агент `ARSENKIN_SUGGESTIONS_REAL`

### Топвизор — что подтверждено и чем

Источники: **(С)** — официальная OpenAPI-схема `github.com/topvisor/topvisor-openapi`
(`src/json/Topvisor.json`, 162 метода, машинный контракт), **(Д)** — страницы документации
`topvisor.com/ru/api/*` и справки, **(П)** — предположение. Живых ответов API у нас нет.

- **(С)** Подсказки в API есть — как режим «Подбора слов»: в определителе задачи
  `searcher_key` имеет enum `0,1,5,100,101,104,105` с именами
  `Yandex, Google, Bing, Yandex_hint, Google_hint, YouTube_hint, Bing_hint`; описание 100 —
  «Подбор подсказок, суррогатный ключ поисковика»
  (`Keywords_2/Types/Collect/SearcherKey.json`). Нужные нам: **100 (подсказки Яндекса)** и
  **101 (подсказки Google)**. В самой схеме слов «suggest/подсказ» в путях нет — API называет
  их «hint», из-за чего беглый поиск по докам отвечает «подсказок в API нет»; это ложный
  след, снятый схемой.
- **(С)** Задача без проекта: `POST /add/projects_2/tasks/keywords/collect/` с телом
  `{keywords: [...], qualifiers: [{region_key, searcher_key, region_lang?, depth?,
  hint_depth?, hint_generators?}]}`; обязательны `keywords`+`qualifiers`; ответ — целое,
  id задачи (`Projects_2/Methods/Tasks/Keywords/Collect/Add.json`,
  `Keywords_2/Types/Collect/Qualifier.json`). Генераторы перебора — enum
  `letter, letter_ru, number, space` (`…/HintGenerator.json`).
- **(Д)** Статус: `POST /get/projects_2/tasks/` — поля `id`, `task_method_name`,
  `task_status` со значениями **`ongoing` | `completed`**, и `task_time_delete` — «секунд до
  удаления задачи» (`topvisor.com/ru/api/tasks/get-tasks/`). Результаты: те же
  `get/keywords_2/keywords`, где **вместо `project_id` передаётся id задачи**
  (`topvisor.com/ru/api/tasks/volumes/get-results/`; для «Подбора слов» документация
  описывает тот же порядок).
- **(Д)** Вызов и аутентификация: `POST https://api.topvisor.com/v2/json/{operator}/{service}/{method}`,
  заголовки `User-Id: <id>` и `Authorization: bearer <ключ>`
  (`topvisor.com/ru/api/v2/first-call/`, пример процитирован дословно).
- **(Д)** Ограничения API: не более **5 одновременных запросов с одного IP** и **5 на один
  User-Id**, до 10 000 результатов на запрос, превышение — `429`
  (`topvisor.com/ru/api/v2/intro/`). Пер-минутных лимитов документация не называет.
- **(Д)** Цена: базовый тариф — **0,1 ₽ за фразу-обращение × ПС × регион**; без генераторов
  отправляется 1 фраза (справка `topvisor.com/support/suggestions/`). Наш паритетный объём —
  3 обращения на прогон, то есть копейки. Точная цена перед запуском доступна методом
  `get/projects_2/tasks/keywords/collect/price` (С).
- **(Д)** Каталог регионов: `POST /get/system_2/common/regions/` — вход `searcher_key` +
  `search`, выход `{id, countryCode, name, domain, …}`
  (`System_2/Methods/Common/Regions/Get.json`).
- **(П)** Числовые `region_key` для «Москва/Россия» у `searcher_key=100` и «ОАЭ» у
  `searcher_key=101` не наблюдены; разрешаются одноразовым вызовом каталога при реализации.
  **(П)** Длительность hint-задачи глубины 1 — предположительно минуты; документация
  молчит. **(П)** Возвращает ли выдача результатов привязку «фраза → породивший её ключ» —
  не установлено; дизайн ниже делает привязку ненужной (одна задача = одна поверхность =
  одна исходная фраза).

## Решение

### Новый шаг конвейера, а не новый агент внутри Arsenkin-стадии

`SUGGESTIONS_COLLECTION` — позиция 2 (после `BASE_COLLECTION`, перед
`ARSENKIN_ENRICHMENT`), бюджеты **раздельные**: `maxAttempts: 10` (отказы),
`maxWaitMs: 15 * 60_000` (ожидание задач Топвизора; первый живой прогон сверяет запас с
фактом). Отвергнутые альтернативы: врастить Топвизор в стадию `ARSENKIN_ENRICHMENT` — вся её
машинерия (state, ledger, лимитер аккаунта, классификация задач) арсенкин-типизирована, а имя
стадии стало бы враньём; врастить в `BASE_COLLECTION` — базовый сбор синхронный, задачная
асинхронщина смешала бы модели. Цена выбранного: последовательный конвейер удлиняется на
время hint-задачи (минуты при часовом бюджете обогащения). Параллельные шаги отвергнуты —
`nextRunnableStep` намеренно строго последователен.

Шаг работает так: один тик — отправка трёх задач (по одной на поверхность, идемпотентно
через `ProviderTask` `provider="topvisor"` и `@@unique([reportRunId, provider,
requestHash])`), дальше тики опроса `get/projects_2/tasks/` с бэкоффом 5с→30с (паттерн
`stepBackoffMs`); `completed` → **в том же тике** чтение результатов
`get/keywords_2/keywords` (задачу удалят по `task_time_delete` — откладывать чтение нельзя),
маппинг в наблюдения, артефакт, ячейки покрытия, шаг done.

**Одна задача = одна поверхность = одна фраза.** Три задачи: Яндекс-RU (searcher 100, регион
Москвы, кириллическая каноника), Google-RU (searcher 101, регион RU, латинская форма),
Google-UAE (searcher 101, регион ОАЭ, латинская форма). Паритет с сегодняшним: `hint_depth`
не задаётся/1, `hint_generators` не задаются (одна фраза без перебора). Атрибуция
«подсказка → движок/регион/запрос» следует из принадлежности задаче — неустановленный вопрос
(П) о привязке в выдаче становится неважным.

**Выбор фразы — тем же кодом, что сегодня.** `selectCanonicalSuggestQuery` и
`buildArsenkinSubjectQueryPlan` переиспользуются; выбор фразы переезжает из
`providers/arsenkin/adapters/suggest.ts` в нейтральный модуль механическим переносом —
копия была бы вторым ответом на вопрос «какую фразу спрашиваем у подсказок». Это
единственный сопутствующий перенос, и он условие задачи, а не рефакторинг по случаю.

### Отказ источника не валит конвейер

Исход провайдера — содержимое ячеек покрытия, а не состояние шага: нет ключа →
`NOT_CONFIGURED`; задача не завершилась в `maxWaitMs` или API отвечает ошибками после
бюджета попыток → `ERROR` с кодом; пусто → `NO_RESULTS`/валидная пустота. Во всех этих
случаях шаг завершается **done**, конвейер идёт дальше, полнота прогона считается как
сегодня (`COMPLETED_PARTIAL` называет дыру). `FAILED` шага остаётся системным сбоям
(джоба исчезла и т. п.) — потому что `nextRunnableStep` останавливает конвейер на `FAILED`,
а «Топвизор упал» не должен отменять оплаченные базу и Arsenkin. Причина решения обязана
пережить план — переносится в ENGINEERING (см. последний раздел).

Знаменатель покрытия прогона не меняется: 12 поверхностей, три подсказочные ячейки теперь
наполняет новый шаг. Формулировка причины пустоты на слайдах перестаёт упоминать состав
Arsenkin и называет Топвизор («источник подсказок не настроен: нет TOPVISOR_API_KEY» /
«источник подсказок не ответил») — текст фиксируется эталоном.

### Замена, а не соседство

- `suggest` удаляется из `ArsenkinToolName`, `DEFAULT_TOOLS`, `ALL_ARSENKIN_TOOLS` и
  allowed-набора `parseTools` (`providers/arsenkin/flags.ts:8-63`): оставить его «выключенным,
  но включаемым через `ARSENKIN_TOOLS`» значило бы держать второй источник под переменной
  окружения — ровно класс дефекта №1. Агентов становится четыре
  (`ARSENKIN_AGENT_TOOLS`, `ARSENKIN_REAL_AGENT_NAMES`), знаменатели прогресса выводятся из
  состава и пересчитаются сами (`real-arsenkin-agents.ts:207-227`).
- Канареечный workflow `suggest-canary` умирает вместе с инструментом
  (`workflow-contract.ts`, ветки в `full-audit-job-store.ts`,
  `report-evidence-provenance.ts:252`): создающие пути удаляются, чтение старых записей с
  этим словом не ломается.
- Serper-autocomplete: из батча базового сбора уходит четвёртый платный вызов
  (`orion-search-profile-service.ts:393` — цикл сокращается до
  `organic/images/videos`; ветка `autocomplete` и `ENDPOINTS.autocomplete` в
  `serper-surfaces.ts` удаляются). Экономия — один платный вызов Serper на каждый запрос
  плана; измеренный вклад в эталонную деку — ноль строк. Исторические строки `SUGGESTION` в
  базе остаются читаемыми.
- Подсказочная gap/retry-машинерия Arsenkin (`unified-suggestions-gap.ts`,
  suggest-ветки `unified-enrichment-targeted-retry.ts`, `unified-suggestions-retry-ui.ts`,
  сборка gap в `GET unified-collection`) заменяется статусом нового шага: «почему подсказок
  нет» отвечают его ячейки покрытия, «повторить» — общий ручной ретрай шага
  (`stepIsRetryable`). Отдельного платного «ретрая подсказок» больше нет — он был ответом на
  арсенкинскую специфику отправки.

### Провайдер и адреса

`providers/topvisor/client.ts`: секреты — `TOPVISOR_API_KEY` (bearer) и `TOPVISOR_USER_ID`
(заголовок; прецедент идентификатора рядом с ключом — `YANDEX_SEARCH_FOLDER_ID`); без любой
из двух — `NOT_CONFIGURED` с названной переменной и ни одного вызова; `429`/ошибки — коды.
Новых значений в `config/defaults.ts` нет (включатель не заводится, разрешение — ключ).
Отдельный лимитер в базе не заводится: документированный предел — 5 одновременных
запросов, а наш поток последователен (отправка и опрос по расписанию `ProviderTask`);
поймали `429` — это retryable-ожидание. Записать это решение, чтобы лимитер «на всякий
случай» не приехал позже.

Синтетический адрес наблюдения — `topvisor://suggest/<hash>` (по образцу
`adapters/suggest.ts:380`). Белые списки `https?://` пропускают его как служебный
автоматически; `isArsenkinItem` переименовывается в `isEnrichmentItem` со списком служебных
схем (`arsenkin://`, `topvisor://`) — иначе аналитика посчитает топвизорные строки базовыми
(`run-analytics-pipeline.ts:415-416`), и provenance соврёт.

Наблюдения шага пишутся в собственный `OrionReportRun` (FK для `ProviderTask` и
`SerpObservation`), артефакт `suggestions-observations.json` кладётся рядом с арсенкинским,
и merge-стадия читает **оба** (`unified-orion-collection-orchestrator.ts:1362-1411` — второй
вход в `arsenkinObservations`-массив либо параллельный параметр, форма наблюдения та же).

`region_key`: числовые коды Москвы (searcher 100) и ОАЭ (searcher 101) инженер получает
одноразовым вызовом `get/system_2/common/regions/` и фиксирует константами с комментарием,
каким вызовом получены. Выдумывать их по аналогии с Яндексом (213) нельзя — контракт не
наблюдён.

## План реализации

Порядок — снизу вверх по конвейеру; шаг большой, коммит один.

1. **Провайдер**: `providers/topvisor/client.ts`, `providers/topvisor/adapters.ts` —
   построение задачи (фраза+qualifier), разбор статуса (`ongoing|completed` — всё прочее
   «спросить снова» с логом неузнанной формы, как у Arsenkin `/check`), маппинг результатов в
   наблюдения (`kind: "suggestion"`, surface `autocomplete`, engine/region из задачи,
   `topvisor://suggest/<hash>`). Готово: юниты на фикстурах, собранных по схеме, с пометкой в
   коде, что живым ответом форма не подтверждена и разбор намеренно терпим.
2. **Перенос выбора фразы**: `selectCanonicalSuggestQuery`+нормализация — в нейтральный
   модуль (например `services/suggest-query-selection.ts`), Arsenkin-адаптер (до его
   удаления в п.6) и Топвизор импортируют одно. Механический перенос, поведение закреплено
   существующими тестами адаптера.
3. **Шаг**: `SUGGESTIONS_COLLECTION` в `workflow/step-plan.ts` (позиция 2, сдвиг позиций
   ниже), стадия в типах джобы (`unified-collection-types.ts`), обработчик стадии в
   оркестраторе (отправка/опрос/ингест/артефакт/ячейки покрытия), регистрация в
   `unified-step-handlers.ts` (`jobStagePosition` — не забыть `CLIENT_CONTENT`), выведение
   стадии/прогресса. ⚠️ Изменение реестра шагов — см. риск деплой-окна.
4. **Merge**: чтение второго артефакта наблюдений в composite-стадии
   (`unified-orion-collection-orchestrator.ts:1362-1411`).
5. **Покрытие и текст пустоты**: три ячейки поверхностей наполняет шаг; формулировки причин
   в построителе фрагментов подсказок; ⚠️ построители деки меняются →
   **`DECK_CONTENT_VERSION` поднимается**.
6. **Ампутация Arsenkin-suggest**: `flags.ts`, `real-arsenkin-agents.ts` (5→4),
   `plan-arsenkin-exact-tasks.ts`, `collect-pilot-surfaces.ts`, `arsenkin-tool-adapters.ts`
   (ветка SUGGESTIONS), каталог поверхностей (`workflow-contract.ts:27-29` — слоты переходят
   к новому шагу или удаляются из арсенкинского каталога), canary, gap/retry-машинерия и её

## Что должно быть протестировано

Офлайн (vitest; всё на моках — условие `npm run ci`):

- **Построение задач**: для субъекта с кириллическим ФИО и латинским алиасом собираются
  ровно три задачи с верными парами (searcher 100 + кириллица; 101 + латиница ×2 региона);
  субъект без латинской формы → Google-задачи не создаются, ячейки честно объясняют почему
  (сегодняшнее поведение `plan-arsenkin-exact-tasks.ts:134-135` — Google-suggest без латиницы
  не отправляется — сохраняется).
- **Идемпотентность отправки**: повторный тик после отправки не создаёт вторые задачи
  (requestHash), после деплоя посреди опроса шаг продолжает опрашивать те же внешние id —
  ничего не отправляя заново. Неверный ответ — двойная оплата, как в
  `provider-task-store.ts:53` уже случалось у Arsenkin.
- **Опрос**: `ongoing` → waiting с ростом паузы; «неузнанная форма ответа» → waiting плюс
  событие в лог, не сбой; `completed` → результаты читаются в том же тике.
- **Ожидание — не попытка**: серия `ongoing` не расходует `maxAttempts`; истечение
  `maxWaitMs` завершает шаг **done** с ячейками `ERROR`, конвейер доходит до merge и
  полнота — partial. Неверный ответ выглядит как «Топвизор молчит — весь прогон FAILED».
- **NOT_CONFIGURED**: без ключа/User-Id — ноль сетевых вызовов (мок-счётчик), шаг done,
  три ячейки `NOT_CONFIGURED` с названной переменной, слайды подсказок печатают причину
  словами; дека собирается.
- **Маппинг результатов**: фразы задачи → наблюдения с верными engine/region/query,
  `topvisor://suggest/<hash>` стабилен (два прогона — один хеш), пустая выдача — валидная
  пустота, а не сбой.
- **Merge**: артефакт шага попадает в композит; `isEnrichmentItem` относит topvisor-строки к
  обогащению (мутационная точка: вернуть литерал `arsenkin://` — тест краснеет).
- **Замена без остатка**: состав агентов Arsenkin — четыре; `ARSENKIN_TOOLS=suggest` в env
  не включает ничего; базовый сбор не зовёт ручку autocomplete (мок Serper фиксирует набор
  вызванных endpoint'ов).
- **Отпечаток построителей**: тест `DECK_CONTENT_VERSION` требует подъёма — существующий
  механизм, проверить красным до правки версии.

Смоки/ворота (офлайн): смок п.9 — конвейер из пяти шагов проходит с мок-Топвизором и с его
отказом (обе ветки); `run-orion-deck-sections-report72` и
`renderer/smoke_deck_raster_layout.py` — после пересборки эталона.

## Риски и что может сломаться молча

- **Контракт выдуман по схеме.** Формат ответов (`result`-обёртка, регистры полей) не
  наблюдён живым вызовом — та самая история с фикстурами Arsenkin. Мера: терпимый разбор,
  «неузнанное = ещё не готово + событие в лог», фикстуры помечены как неподтверждённые,
  контракт дописывается по первому живому прогону.
- **`region_key` для hint-searcher'ов.** Если регионы у searcher 100/101 имеют собственное
  пространство id, «подставить 213» молча соберёт подсказки не того региона. Мера: коды —
  только из каталога регионов, константы с провенансом.
- **`task_time_delete`.** Задача удаляется провайдером; опрос с большим бэкоффом может
  прийти к удалённой задаче — это должно читаться как ERROR с кодом, а не как вечное
  `ongoing`.
- **Ретро-добавление шага в реестр.** У прогонов, идущих в момент деплоя, строк шага
  `SUGGESTIONS_COLLECTION` нет; повторный `ensurePipelineSteps` (recover) создаст строку
  задним числом. Общий обработчик закрывает это («джоба переросла шаг → done»,
  `unified-step-handlers.ts`), но поведение обязано быть покрыто тестом: прогон в
  `ARSENKIN_ENRICHMENT` с ретро-строкой не запускает сбор подсказок. Плюс предупредить
  владельца об окне деплоя: прогоны, начатые до выката, подсказки получат по-старому или
  не получат вовсе.
- **Кэш секций.** Правка построителей без подъёма `DECK_CONTENT_VERSION` молча оставит в
  деках старые тексты причин — механизм отпечатка это ловит, но только если версия
  действительно поднята.
- **Скрытая ценность Serper-autocomplete.** Измеренный вклад в эталон — ноль, но эталон —
  один прогон одного субъекта. Если на других субъектах Serper давал подсказки, объём
  слайдов может просесть до «только канонические фразы Топвизора». Открытый вопрос №1
  фиксирует это решение за владельцем.
- **Двойная правка одного файла с шагом 0031.** Шаг 0031 трогает построители страницы выдачи
  и эталоны; 0033 трогает эталоны тоже. Исполнять после закрытия 0031 и пересобирать эталон
  поверх его состояния, иначе дифф эталона смешает два шага.
