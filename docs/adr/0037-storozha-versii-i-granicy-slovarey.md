# Шаг 0037. Сторожа версии и позиции, и границы двух словарей

## Задача и границы

Первая партия описи бэклога: пять дешёвых пунктов, каждый — отдельный коммит. Два первых чинят
**сторожей** (без них любая последующая правка может молча не доехать до документа), три
остальных — **границы**: два ответа на один вопрос и два словаря, ловящих лишнее.

В объёме ровно эти пять пунктов. Явно вне объёма:

- всё остальное из раздела «Опись известного и непочиненного» бэклога — берётся отдельными
  решениями;
- Топвизор (`SUGGESTIONS_COLLECTION`) — отложен владельцем, материал сохранён в бэклоге;
- пополнение и переписывание словарей сверх снятия ложных срабатываний, названных ниже;
- пересборка отчётов и любой платный прогон.

## Контекст

Всё помечено: **измерено** — файл и строка на `e7071aa`; **гипотеза** — если не проверено.
Четыре из пяти пунктов подтвердились как записаны; **два описаны неточно, и это меняет план** —
поправки названы отдельным подразделом.

### 1. Сторож версии деки проверяет формат, а не движение номера — измерено

`tests/unit/deck-content-version.test.ts` держит четыре утверждения:

- `:190-193` — записанный отпечаток совпадает с посчитанным по исходникам;
- `:195-208` — подсказка о расхождении называет правило и исключение;
- `:213-244` — правка реестра шаблонов и правка каждого построителя двигают отпечаток;
- `:245-247` — **номер версии назван так, как его ждёт кэш**: `expect(DECK_CONTENT_VERSION).toMatch(/^deck-sections-v\d+$/u)`.

Последнее — единственное утверждение о номере, и это утверждение о **форме строки**. Ни одно
утверждение не связывает номер с отпечатком. Значит сценарий забывчивости проходит зелёным:
правишь построитель → падает `:190` → обновляешь `DECK_BUILDER_FINGERPRINT`
(`deck-sections/content-version.ts:391`) → тест зелен, а `DECK_CONTENT_VERSION`
(`content-version.ts:16`, сейчас `deck-sections-v144`) остался прежним, и готовые паки приедут
из кэша без правки.

**Исключение существует и оплачено деньгами.** Доктекст `content-version.ts` объявляет узкую
ветку: правка, которая заведомо не может изменить ни одну **собранную** деку, двигает только
отпечаток, потому что подъём номера обесценивает готовые паки и заставляет платить за стадии GPT
заново — в том числе прогону, который идёт прямо сейчас. Любое решение обязано эту ветку
сохранить.

### 2. Позиция стадии записана числом — измерено

`workflow/unified-step-handlers.ts:93-98`:

```ts
function jobStagePosition(stage: string): number {
  const byStage = UNIFIED_PIPELINE.find((d) => d.stage === stage);
  if (byStage) return byStage.position;
  if (stage === "CLIENT_CONTENT") return 4;
  return 0;
}
```

Соседний комментарий (`:88-91`) объясняет, откуда четвёрка: «`CLIENT_CONTENT` делит позицию с
`ORION_PREPARE`: это движение внутри одного шага подготовки отчёта». То есть величина **выводима**
— это позиция шага, чья стадия `ORION_PREPARE`, — но записана литералом.

В реестре (`workflow/step-plan.ts`) сейчас: `BASE_COLLECTION` — 1 (`:41-43`),
`ARSENKIN_ENRICHMENT` — 2 (`:48-50`), `COMPOSITE_MERGE` — 3 (`:59-61`), `REPORT_PREPARE` — 4 со
стадией `ORION_PREPARE` (`:66-68`). Четвёрка совпадает **сегодня** и только сегодня.

Обе величины пары читаются из реестра: `:143` (`stepDefinition(step.name)?.position` — по имени)
против `:144` (`jobStagePosition(after.stage)` — по стадии), и то же на `:231`. Пока обе выводимы,
вставка шага сдвигает их вместе. Литерал из этой пары выпадает.

**Отказ будет тихим.** Вставь шаг вторым — `REPORT_PREPARE` станет пятым, `CLIENT_CONTENT`
останется четвёркой, сравнение `4 > 5` ложно, шаг **никогда не признаётся сделанным** и ждёт до
исчерпания `maxWaitMs`. Комментарий на `:140-142` описывает ровно этот отказ как случившийся на
первом живом прогоне: «шаг ждал бы вечно и сжёг бы бюджет попыток, остановив конвейер».

Сохранённые в базе позиции при этом безопасны: они сравниваются только между собой внутри одной
джобы (`workflow/step-store.ts:157`, `:208-209`), абсолютной арифметики против реестра там нет.

### 3. «Тема обвиняет по умолчанию» задано дважды — измерено

`config/finding-themes.ts:52` — `accusing: z.boolean().default(true)` в схеме каталога;
`:659-661` — `isAccusingTheme(theme) { return theme?.accusing ?? true; }`.

Второй `?? true` покрывает **два разных случая сразу**, и только один из них законен:

- **темы нет вовсе** (метка не нашлась в каталоге) — доктекст `:655-658` объявляет это намеренно:
  «считаем обвиняющей: защита строже». Это правило остаётся;
- **поле не задано у существующей темы** — а этого не бывает: схема уже подставила `true`, и
  `ThemeDef.accusing` объявлен обязательным `boolean` (`:33`).

То есть умолчание поля записано в двух местах, и мутация, снимающая любое из них, не краснит ни
один тест.

### 4. Корень `суд` ловит больше, чем судебное, — измерено, и шире, чем записано

Выражение `суд(?!острое|ьб)` стоит **в двух местах**, а не в одном:

- `config/finding-themes.ts:239` — ключевые слова темы `criminal_legal`;
- `config/finding-themes.ts:359` — `adversePatterns`, словарь негатива.

Прогнал корень по словам (левая граница ставится `withWordStart`, правой у словаря нет):

| судебный, суд отказал | да | да |
| судостроение, судьба | нет | да, исключения работают |
| **судмедэксперт** | **да** | **нет** |

### 5. Мягкие площадки читают подстроку и весь адрес — измерено, и шире, чем записано

`serp-observation/resolve-observation-highlights.ts:35-36`:

```
/forbes\.|klerk\.|tadviser\.|wikipedia\.|ruwiki\.|wikiwand\.|linkedin\.|rusprofile\.|
 audit-it\.|zachestnyibiznes\.|labyrinth\.|instagram\.|facebook\.|x\.com|twitter\.|youtube\.|imslp\./i
```

Ни у одного элемента нет левой границы. Прогнал: `netflix.com`, `linux.com`, `forex.com`,
`fintechx.com` — **все мягкие** из-за `x\.com`; `notinstagram.com` мягкий из-за `instagram\.`;
`myforbes.ru` — из-за `forbes\.`.

**И это применяется не только к домену.** `:261-263`:

```ts
const dictionary =
  SOFT_PROFILE_DOMAIN_RE.test(url) || SOFT_PROFILE_DOMAIN_RE.test(domain)
    ? getStrongAdversePatterns()
    : getAdversePatterns();
```

Проверяется **весь адрес**, поэтому мягким становится и обычное издание, у которого в пути или в
параметрах встретилось `x.com` (например трекинг-метка). Для соседнего списка негативных площадок
чтение всего адреса выбрано намеренно (агрегатор компромата виден перепечаткой, `:15-19`), но
здесь вопрос другой: «мягкая площадка» — свойство **издателя**, а не адреса.

**Последствие для клиента — потеря сигнала, а не ложная метка.** С такого домена строка судится
только сильным подмножеством словаря, поэтому «Обыск в офисе компании» на нём рамки не получит.

### Оба правимых файла входят в отпечаток построителей — измерено

`tests/unit/deck-content-version.test.ts`, список `EXTRA_SOURCES`: `:121` —
`../../serp-observation/resolve-observation-highlights.ts`, `:134` —
`../../config/finding-themes.ts`. То есть работы 3, 4 и 5 **двигают отпечаток**, и по правилу,
которое вводит работа 1, обязаны двигать и номер версии — либо объявить исключение.

Это меняет три строки моего же плана и делает партию связной: работа 1 не просто стоит первой, а
**даёт механизм, которым пользуются работы 3–5**. Первым его законным потребителем становится
работа 3 (см. ниже), и это лучшая проверка механизма, чем любой синтетический тест.

### Поправки к постановке

1. **Пункт 4 шире, чем записан:** корень стоит в **двух** местах (`:239` и `:359`). Починка
   только словаря негатива оставила бы тему `criminal_legal` ловить «судмедэксперта».
2. **Пункты 4 и 5 эталоны не двигают.** Проверил оба корпуса (98 доменов и весь клиентский текст
   `report-72` + золотого кейса):
   - ни один домен не меняет классификацию при постановке границ — расхождений между нынешней и
     строгой формой **ноль**;
   - слова с корнем `суд` в эталонах — только «судебные», «судебными», «судов», причём «судов»
     встречается **в нашей же статичной рекомендации** («по картотекам судов»), а не в материале.
   Значит дифф эталонов у обоих пунктов ожидается **пустым**, и держат правку только юниты. На
   живых данных разница видна — именно поэтому тесты обязаны нести настоящие примеры.
3. **Строка пункта 3 в описи указана неточно:** `z.boolean().default(true)` стоит на `:52`, а
   `?? true` — на `:660` (в описи значились `:38` и `:605`; файл с тех пор вырос).

## Решение

### 1. Отпечаток и номер двигаются вместе, а исключение остаётся объявляемым

Рядом с отпечатком записывается **версия, при которой он снят**:

```ts
export const DECK_BUILDER_FINGERPRINT = "…";
/** Номер версии на момент снятия отпечатка. */
export const FINGERPRINT_TAKEN_AT_VERSION = "deck-sections-v144";
```

Тест требует `FINGERPRINT_TAKEN_AT_VERSION === DECK_CONTENT_VERSION`. Цепочка забывчивости
рвётся: правка построителя роняет сверку отпечатка → разработчик обновляет отпечаток → обязан
обновить и «версию снятия» → она обязана совпасть с номером, значит номер тоже поднимается.

**Исключение сохраняется и становится объявляемым, а не подразумеваемым:** отдельная константа с
причиной («правка не может изменить ни одну собранную деку — …»), при которой равенство не
требуется. Сегодня исключение живёт только в доктексте и в дисциплине ревью; после правки оно
живёт в коде и попадает в дифф — то есть его видно.

Почему не «вшить отпечаток в номер версии» (`deck-sections-v144-5644923781c30f81`): это выглядит
красивее и закрывает класс целиком, но **уничтожает исключение**, а оно оплачено деньгами —
подъём номера обесценивает готовые паки и заставляет платить за стадии GPT заново, в том числе
идущему прогону. Отказ от узкой ветки ради изящества здесь стоит реальных денег.

Почему не «сравнивать с предыдущим коммитом через git»: `npm run ci` обязан проходить на чистой
машине; тест, зависящий от истории VCS, — это новое условие контура ради одной проверки.

### 2. Позиция выводится из реестра

`jobStagePosition` перестаёт знать число. `CLIENT_CONTENT` — вторая стадия шага подготовки
отчёта, поэтому её позиция берётся у того шага, чья стадия `ORION_PREPARE`. Связь «стадия →
владеющий шаг» объявляется данными рядом с реестром, а не выражением в функции: спрятанное в
функции условие — это тот же литерал, только длиннее.

Признак верности выбран так, чтобы он не зависел от нынешних чисел: **сдвиг реестра не должен
требовать правки второго места**. Тест это и проверяет — реестром со сдвинутыми позициями.

### 3. Умолчание поля — одно, правило «темы нет» — своё

`isAccusingTheme` перестаёт совмещать два вопроса:

```ts
export function isAccusingTheme(theme: ThemeDef | undefined): boolean {
  return theme === undefined ? true : theme.accusing;
}
```

Правило «темы нет вовсе — считаем обвиняющей» остаётся и становится видимым; умолчание **поля**
живёт только в схеме каталога, где ему и место. Поведение сегодня не меняется — обе величины
`true`; меняется то, что мутация любой из них теперь краснеет.

### 4. Корень `суд` ограничен там, где он стоит, — в обоих местах

Вместо списка исключений, который приходится дополнять новым словом при каждой находке, корень
ограничивается тем, что он на самом деле означает: судебная процедура, а не всё, что начинается
на «суд». Форма — за разработчиком; требование — чтобы **список исключений перестал расти**, то
есть чтобы «судмедэксперт», «судоходство» и «судоверфь» не совпадали **не будучи перечисленными
поимённо**.

Правка применяется **в обоих местах** (`:239` и `:359`) одним коммитом: два места отвечают на
разные вопросы (тема и негатив), но ловят одно и то же семейство слов, и починка одного оставила
бы дефект в другом на глазах у того же читателя.

**Цена ошибки здесь симметрична, и это записано требованием к тестам:** ложная метка на
нейтральном материале вредит клиенту так же, как пропущенный негатив, — ему предлагают убирать
то, что его не порочит. Поэтому проверка держит обе стороны: «судмедэксперт» метки не получает,
«судебный процесс» получает.

### 5. Мягкая площадка — свойство издателя, и список читает хост

Две правки, обе узкие:

1. **Границы.** Каждый элемент списка получает левую границу — совпадение только с начала имени
   хоста или после точки. `netflix.com`, `linux.com`, `forex.com`, `notinstagram.com` перестают
   быть мягкими; `x.com`, `instagram.com`, `forbes.ru` остаются.
2. **Хост, а не весь адрес.** Список сверяется с доменом, а не с полным URL. Почему это не
   симметрично соседнему списку негативных площадок, который весь адрес читает намеренно
   (`:15-19`): там вопрос «перепечатал ли это агрегатор компромата», и перепечатка видна в пути;
   здесь вопрос «кто издатель», и путь на него не отвечает. Разные вопросы — разные входы, и это
   надо записать рядом, иначе через месяц их «согласуют».

Что **не** делается в этом коммите: `forbes.` и `klerk.` остаются в списке мягких, хотя это
издания, а не хостинги биографий. Это отдельный пункт описи (**EJ**) со своей ценой — он меняет
разметку живых материалов, а не снимает ложное срабатывание.

### Порядок и обоснование

```
1 → 2 → 3 → 4 → 5
```

- **1 первым, и это не формальность.** Работы 3, 4 и 5 **двигают отпечаток** — оба правимых
  файла входят в `EXTRA_SOURCES` (`:121`, `:134`). Значит без работы 1 каждая из них проходит по
  старому правилу: обнови отпечаток, а про номер вспомнят или не вспомнят. С работой 1 они обязаны
  либо поднять номер (4 и 5), либо **объявить исключение с причиной** (3). Партия сама становится
  первой проверкой механизма.
- **2 вторым.** Второй сторож; ни от чего не зависит, ничего не двигает, и его удобно закрыть до
  правок разметки.
- **3 третьим.** Чисто структурная правка без изменения поведения — она дешевле всех и
  освобождает голову перед двумя правками словарей.
- **4 и 5 — независимы, и порядок между ними свободен.** Зависимости по эталону между ними
  **нет**: измерено, что ни один из двух не двигает ни `report-72`, ни золотой кейс. Обе поднимают
  номер версии — каждая свой, последовательно; сливать их в один коммит нельзя, иначе дифф
  разметки будет отвечать сразу на два вопроса. Они трогают
  разные файлы (`config/finding-themes.ts` против `serp-observation/resolve-observation-highlights.ts`)
  и разные предикаты. Поставлены в этом порядке только потому, что 4 трогает два места и потому
  тяжелее.

## План реализации

Пять работ, пять коммитов. Каждая начинается красной фазой: тесты пишутся первыми, их падение
сохраняется файлом **до первой строки продакшн-кода**, любая последующая правка теста называется
отдельной строкой отчёта.

---

### Работа 1. Отпечаток сдвинулся — сдвинулся и номер

**Файлы.** `orion-golden/deck-sections/content-version.ts` — константа «версия на момент снятия
отпечатка» и объявляемое исключение с причиной; `tests/unit/deck-content-version.test.ts` —
утверждение о паре и о том, что исключение объявлено, а не подразумевается; подсказка о
расхождении (`:176-186`) называет **обе** константы.

**Чем закрывается.** Забытый подъём номера перестаёт проходить зелёным.

**Признак.** Сценарий: правим построитель, обновляем отпечаток, **не** трогаем номер — тест
красный и в подсказке названо, что именно обновить. Обратный сценарий: объявлено исключение —
тест зелёный, и в диффе видно, кто и почему его объявил.

**Эталоны.** Не двигаются. `DECK_CONTENT_VERSION` **не поднимается**: построители не тронуты.

**`ENGINEERING.md`.** Раздел об эталонах и версии деки: правило «отпечаток сдвинулся ⇒ номер
сдвинулся, либо исключение объявлено» переезжает из дисциплины ревью в код, и исключение теперь
видно в диффе.

---

### Работа 2. Позиция стадии выводится, а не пишется числом

**Файлы.** `workflow/unified-step-handlers.ts:93-98` — литерал уходит; связь «стадия → владеющий
шаг» объявляется данными рядом с `UNIFIED_PIPELINE` (`workflow/step-plan.ts`).

**Чем закрывается.** Вставка шага перестаёт готовить тихое зависание `REPORT_PREPARE`.

**Признак.** Тест подставляет реестр со сдвинутыми позициями и требует, чтобы `CLIENT_CONTENT`
получил позицию шага `ORION_PREPARE` **без правки второго места**. Неверный ответ — четвёрка.

**Эталоны.** Не двигаются, версия не поднимается.

**`ENGINEERING.md`.** Раздел о конвейере: обе величины сравнения «джоба переросла шаг» выводятся
из реестра; ни одна позиция не записана числом, потому что расхождение даёт не отказ, а зависание

### Работа 3. Умолчание «тема обвиняет» — в одном месте

**Файлы.** `config/finding-themes.ts:659-661` — `isAccusingTheme` разводит «темы нет» и «поле не
задано»; умолчание поля остаётся только в схеме (`:52`).

**Признак.** Тема без метки в каталоге считается обвиняющей; тема с `accusing: false` — нет;

**Эталоны.** Не двигаются. Отпечаток **двигается** (`finding-themes.ts` входит в
`EXTRA_SOURCES`, `:134`), но правка заведомо не может изменить ни одну собранную деку: обе

узкий случай, ради которого исключение существует, — **работа 3 объявляет его механизмом работы 1

поля и правило „темы нет“ разведены; ответ предиката не изменился ни на одном входе».

**`ENGINEERING.md`.** Строка в разделе о темах: умолчание поля — в схеме, правило «темы нет —
обвиняет» — в предикате, и это разные вопросы.

### Работа 4. Корень `суд` означает суд

**Файлы.** `config/finding-themes.ts:239` (ключевые слова `criminal_legal`) и `:359`
(`adversePatterns`) — **оба**.

**Чем закрывается.** Ложная метка на нейтральном материале — обратная сторона замечания №4
аудита.

**Признак.** «Судмедэксперт установил причину смерти», «судоходство», «судоверфь» метки и темы не
получают; «суд отказал в иске», «судебный процесс», «уголовное дело» — получают. Список
исключений при этом **не растёт**: проверка держит слова, которых в нём нет.

**Эталоны.** **Измерено: не двигаются** — в обоих корпусах слова с этим корнем только «судебные»,
«судебными» и «судов», причём последнее стоит в нашей же статичной рекомендации, а не в
материале. Значит правку держат **только юниты**, и это надо сказать вслух в отчёте: зелёный
эталон здесь ничего не доказывает.

**`DECK_CONTENT_VERSION` поднимается.** `config/finding-themes.ts` входит в отпечаток
(`EXTRA_SOURCES`, `:134`), и на исключение эта правка **не претендует**: на живых данных она
меняет разметку — то есть изменить собранную деку она может, просто не на наших двух корпусах.
Пустой дифф эталона основанием для исключения не является, и это надо сказать вслух: исключение
даётся ветке, которой на деке нет вовсе, а не правке, которую эталон не покрывает.

**`ENGINEERING.md`.** Раздел «Цена единого словаря»: корень ограничен смыслом, а не перечнем
исключений, и правка сделана в обоих местах, где он стоит.

## Риски и что может сломаться молча

- **Сторож, написанный после правки, не ловит ничего (работа 1).** Проверка 1.1 обязана быть
  красной **до** продакшн-правки, и красный лог обязан лежать файлом. Сторож версии, впервые
  запущенный на исправленном коде, доказывает только то, что он компилируется.
- **Исключение без причины (работа 1).** Если объявляемое исключение окажется голым флагом, оно
  станет самым дешёвым путём к зелёному, и сторож выродится. Причина обязана быть непустой и
  попадать в дифф.
- **Зелёный эталон ничего не доказывает (работы 4 и 5).** Измерено: ни одна правка разметки в
  этой партии не двигает ни `report-72`, ни золотой кейс. Значит единственный сторож —
  юнит-тесты, и отчёт обязан это назвать, а не предъявлять зелёные ворота как подтверждение.
- **Симметрия ошибки (работа 4).** Сужение корня снимает ложные метки, но может снять и верные,
  если сузить слишком. Обе стороны держатся проверками 4.1 и 4.2; отчёт называет, какие слова
  перестали совпадать, поимённо.
- **Два списка, которые «согласуют» (работа 5).** Мягкий читает хост, негативный — весь адрес.
  Без проверки 5.4 следующий читатель приведёт их к одному виду и вернёт потерю сигнала на
  перепечатках компромата.
- **Правка одного из двух мест (работа 4).** Корень стоит дважды; починка словаря без темы
  оставит «судмедэксперта» в криминальной теме — на той же странице, у того же читателя.
- **Позиция, выведенная наполовину (работа 2).** Если связь «стадия → шаг» окажется выражением
  внутри функции, а не данными, литерал вернётся при следующей вставке шага. Признак — 2.1 на
  сдвинутом реестре, а не на нынешнем.
