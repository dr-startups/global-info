## 2. Данные о субъекте

Миграции базы нет: якоря живут в case-owned `subject-identity-profile.json` (`services/subject-profile-admin.ts:52-54`), решение — в JSON-колонках `dp_subject_persona_checks`.

Новый блок типа (`orion-golden/identity/subject-identity-profile.ts`):

```
anchors: { birthDate: string|null; phrases: {kind: 'employer'|'position'|'birthPlace'|'education'|'fact', text: string, strong: boolean}[];
           inn: string[]; domains: string[]; source: 'operator'; updatedAt }
discovered: { inn: {inn, regionCode, urls[]}[]; namesakeCandidates: {label, words[], urls[], reason}[] }
```

- `anchors.birthDate` — копия `dp_subjects.dateOfBirth`, только чтение в панели; бутстрап переносит её всегда (сливает в существующий файл, ручные поля не трогает — закрывает дыру «файл есть → discovered пуст»). Поле формы кейса становится `required` (`validation/case-schemas.ts:59`, `client/CreateCaseForm.tsx:104-112`) — сегодня `optionalDate`.
- `anchors.phrases` — фразы со слов клиента (он же заказчик): работодатель, должность, место рождения, вуз, факт. Многословная фраза сильная по умолчанию; однословная — только с явной галочкой «сильный» и предупреждением. Регион — не якорь (гребец «Динамо», депутат, «Опора» — все Краснодар).
- `anchors.inn` — только введённый оператором, с контрольной суммой; подсказка поля: «ИНН из поисковой выдачи не вводить — только от клиента или из его документов».
- `discovered.inn` — заменяет автоподъём: builder возвращает `{inn, regionCode, urls}`, `knownIdentifiers.inn` и `queryVariants «ИНН …»` (builder:258-262) из добытого не строятся. **Легаси-файлы** (0049): при загрузке `knownIdentifiers.inn` без `anchors` переезжает в `discovered.inn` — три чужих ИНН становятся предложениями, не идентификаторами.
- `contextIdentifiers` и `knownIdentifiers.birthDate/locations/wrongBirthDates` удаляются как второй ответ (`discoverLocations` builder:196-212 мёртв для кириллицы из-за `\b`). `namesakeProfiles`, `unrelatedKnownPersons`, `wrongPatronymics` остаются.
- Ввод — в форме внутри панели персон (`client/SubjectPersonaPanel.tsx`), а не в свёрнутой панели ниже (`CaseDetailView.tsx:728-740`); PUT `/subject-profile` (`route.ts:55-80`) принимает блок `anchors`. Права записи — `case.update` как у профиля; кнопка решения персоны требует их же.

Расхождение документа: `nationality/country/identifiers` нигде не вводятся, ENGINEERING.md:1528-1530 обещает гражданство в теле `/match` — назвать в §8, не трогать.

## 4. Разрешение субъекта

Режим — данные: `SubjectIdentity.anchors` непуст ⇒ «по якорям»; пуст (фикстуры, легаси) ⇒ прежняя лестница (458-543) + оговорка в отчёте. Слово-флага нет.

**Якорь-фраза.** Токены — split по не-буквам без `\b` (грабля `patronymic-conflict.ts:27-29`). Слова ≤3 букв отбрасываются («ст.», «суд»). Стем — слово без падежного окончания из явного списка (только если остаток ≥4 букв); совпадение — токен = стем + окончание из того же списка. Закрепляется примерами: «судья» ↔ судьи/судьей ✓, судьба/судей/судейская ✗; «Краснодарского края» ↔ «Краснодарский край» ✓, «Красноармейская» ✗; «Арбитражный суд Краснодарского края» ↔ «председатель Арбитражного суда Краснодарского края» ✓. Совпадение фразы — все стемы. Идеальной морфологии нет; оператор вводит варианты («АС Краснодарского края»). Стемы печатаются в `matchedIdentifiers`.

**Дата рождения.** Формы `DD.MM.YYYY`, «D месяц YYYY», ISO → `birth_date`; «родил*/born/г.р. … YYYY» → `birth_year` (0.8). Конфликт `foreign_birth_date`: другая дата (год 2 или 4 цифры) в 40 знаках от сигнала родил*/рожден*/born/г.р./«дата рождения» — регэксп сигнала без `\b` (рецензия: «15.06.54 г.р.» пропускался). Дата без сигнала конфликтом не является («ИП с 23.11.2000»). Действует **во всех режимах** — депутат (10.08.1983, 14 строк), боксёр, кандидат уходят в OTHER без ручного ввода.

**ИНН.** Только `anchors.inn` → `strong_identifier_match` 0.98. Извлечение из текста: 12 цифр с контрольной суммой, в 30 знаках от «ИНН»/ОГРНИП или на реестровом домене; дробные хвосты не считаются. При известном своём ИНН: свой на странице → SUBJECT_MATCH независимо от чужих (карточка компании с соучредителями); своего нет, чужой есть → `foreign_inn`. При неизвестном — страница с чужим ИНН не выше `registry_inn_unverified` (AMBIGUOUS), если нет сильного якоря.

**Лестница в режиме «по якорям»** (после `hasSurname && hasGivenName`, вместо 503-510; ветки без полного имени не меняются):
1. конфликт (foreign_birth_date | foreign_inn | тёзка с жёстким признаком или ≥2 словами | patronymic/given_name) и нет сильного якоря → OTHER_SUBJECT 0.9;
2. конфликт и сильный якорь → AMBIGUOUS `mixed_identity_signals` 0.5 (Нейро-ответ Яндекса о двух людях);
3. сильный якорь → SUBJECT_MATCH `full_name_with_anchor:<kind>` 0.92 (ИНН 0.98);
4. чужой ИНН без своего известного → AMBIGUOUS `registry_inn_unverified`;
5. иначе AMBIGUOUS `full_name_no_anchor` 0.5.
Одно слово тёзки → как сегодня AMBIGUOUS (ENGINEERING.md:2140-2143). Порядок записан явно, чтобы реализация не выбрала любой из двух.

**Пост-проходы.** `inheritByUrl`: бесконфликтная строка того же нормализованного адреса (схема, `www`, хвост `/`, utm, регистр хоста) наследует SUBJECT_MATCH заякоренной (`url_inherited`). `promoteLikelyBySharedDomain` (560-595) в режиме «по якорям» выключен: домен, подтверждённый ИНН судьи, поднимал бы чужих ИП rusprofile.

**Майнер контекста** (`subject-context-miner.ts:150-198`): в режиме «по якорям» не выполняется (`minedContext: []`, `skippedReason` в `derived-subject-context.json`); в прежнем режиме — по решению №4. Его код переназначается: `discovered.namesakeCandidates` после прогона — строки с чужой датой/ИНН и частотные слова их доменов (DF≥2) как подсказка оператору с адресами, никогда не автоприменение.
