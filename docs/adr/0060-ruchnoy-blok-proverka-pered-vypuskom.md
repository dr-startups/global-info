# 0060 — Ручной блок: проверка перед выпуском отчёта

**Статус:** план программы, ждёт решений владельца. Кода нет. Каждый шаг ниже получит свой ADR и
свой красный лог, когда владелец утвердит порядок.

## Что просили

После сборки отчёта аналитик должен (1) подтвердить или снять спорные факты — прежде всего то, что
напечатано с пометкой «Требует подтверждения», (2) убрать из отчёта то, чего в нём быть не должно,
(3) в блок LexisNexis положить скриншот настоящего отчёта LexisNexis и описать его руками, и только
после этого отдать документ в рендер. Владелец назвал два возможных устройства: править готовый PDF
руками либо проходить пункты проверки до сборки.

## Два устройства, и почему второе

**А. Править готовый PDF (или PPTX) руками.** Отвергается как основной путь по четырём причинам,
каждая из которых бьёт по правилам продукта (`ENGINEERING.md` §1):

1. Правка не становится данными: следующая пересборка её теряет, а пересборки случаются — правка
   якоря, новая версия деки, починка дефекта.
2. Ни одни ворота её не видят: сторож внутренних кодов, бюджеты текста, проверка «каждое поле
   оставило след», растровая проверка — всё судит документ **до** правки.
3. Утверждение, вписанное в PDF, ни к какому наблюдению не прослеживается. Правило «LLM не источник
   правды» существует не ради модели, а ради читателя: он должен видеть, откуда взялась каждая
   фраза. У фразы, вписанной руками, происхождение — «аналитик такой-то тогда-то», и это должно быть
   напечатано, а не подразумеваться.
4. PPTX собран рендерером под меру: правка текста руками ломает вёрстку, которую мера уже
   проверила, и телеметрию, по которой ворота выпуска отказывают.

Оставить PDF-правку можно только как **аварийный выход** с записью — см. решение 5.

**Б. Проверка — это данные.** Отчёт собирается всегда как **черновик**. Аналитик проходит лист
проверки, построенный по черновику, и принимает решения — по строкам, по темам, по записям
комплаенса, — которые сохраняются как данные. Кнопка «Выпустить» пересобирает отчёт из данных с
учётом решений, рендерит его и помечает **выпуском**: кто, когда, какие решения вошли, какой хеш у
документа. Клиент получает только выпуск.

Это закрывает оба варианта владельца сразу: проверка происходит «до сборки» той версии, которую
получит клиент, но по уже нарисованным страницам — потому что список спорных пунктов нельзя
составить, пока неизвестно, что именно попало на страницы.

## Устройство

### 1. Черновик и выпуск — состояние джобы

К `payloadJson` унифицированной джобы добавляется блок:

```
release: {
  state: "draft" | "released",
  round: number,                 // номер круга проверки: сколько раз пересобирали по решениям
  releasedAt, releasedBy,        // пусто у черновика
  decisionsDigest,               // хеш набора решений, вошедших в эту сборку
  documentSha256,                // хеш выпущенного PDF
  openItems: number              // сколько пунктов листа оставались нерешёнными на момент выпуска
}
```

- Любая сборка (первая, пересборка, повторный рендер) ставит `state = "draft"`: документ изменился,
  выпуск устарел по построению.
- «Выпустить» = пересборка по решениям + рендер + `state = "released"` одной операцией. Отдельной
  кнопки «пометить как выпуск без пересборки» нет: иначе выпуском станет документ, собранный до
  последних решений.
- Черновик отличим на самом листе: на обложке под названием строка «Черновик для проверки аналитиком
  — не для передачи клиенту», в подвале каждой страницы то же слово. Это **текст в нагрузке**, а не
  новая графика рендерера: старый рендерер напечатает его как обычный подзаголовок, окна деплоя нет.
- Скачивание: аналитик и выше видят обе ссылки (черновик, выпуск); `CLIENT_VIEWER` — только выпуск
  (решение 3).

### 2. Лист проверки — что предъявляется аналитику

После каждой сборки конвейер пишет артефакт `analytics/review-sheet.json`: список пунктов, у каждого —
устойчивый ключ, вид, что напечатано, на каких страницах, текущее решение аналитика (если было) и
доступные действия. Строится детерминированно из уже существующих артефактов: `subject-resolution`,
`verified-finding-bundle`, `ambiguous-findings`, `link-usage-trace`, `compliance-inventory`.

**Пункты вида «материал»** (`kind: "evidence"`, ключ `inventory:obs-…` — он и сегодня один на
наблюдение и переживает пересборку, потому что выводится из ключа наблюдения):

- все материалы с решением `LIKELY_SUBJECT` и `AMBIGUOUS`, дошедшие до страниц; и все `SUBJECT_MATCH`,
  напечатанные негативными (их можно снять);
- показывается: заголовок, адрес, сниппет, решение и код причины словами («фамилия при запросе о
  субъекте, признака рядом нет»), страницы, где напечатан, и цитата, которой напечатан;
- действия: **подтвердить принадлежность** (→ `SUBJECT_MATCH`, причина `analyst_confirmed`),
  **это другой человек** (→ `OTHER_SUBJECT`, существующий `WRONG_SUBJECT`), **не негатив** /
  **негатив** (существующая классификация строки), **убрать из отчёта** (существующий `EXCLUDED`:
  материал не печатается нигде, кроме служебного приложения с пометкой «снято аналитиком»).

**Пункты вида «тема»** (`kind: "finding"`, ключ `theme:<themeId>|<subjectMatch>` — идентификатор
находки хешируется от состава улик и меняется вместе с ним, поэтому ключом служит тема с корзиной):

- все находки матрицы рисков со статусом «Требует подтверждения» (`LIKELY_SUBJECT`) и все
  подтверждённые темы повышенного внимания;
- действия: **подтвердить тему** (все её улики `LIKELY` → `SUBJECT_MATCH`, тема уходит из «Требует
  подтверждения» в подтверждённые, в блоке печатается «подтверждено аналитиком <дата>»), **снять тему**
  (находка исключается с причиной, в приложении — «снято аналитиком: <причина>»), **примечание
  аналитика** — одно предложение, печатается в блоке темы последней строкой «Примечание аналитика:
  …» (см. решение 2).

**Пункты вида «комплаенс»** (`kind: "compliance"`, ключ — `dp_database_profiles.id`):

- каждая запись `PENDING` / `NEEDS_REVIEW`; действия — существующие `MATCH_CONFIRMED` /
  `FALSE_POSITIVE` (`reviewComplianceHit`);
- отдельный пункт **«снимок отчёта LexisNexis»** (и такой же для Dow Jones): загрузить одну или
  несколько страниц-изображений, указать дату отчёта, написать описание в трёх полях, которые лист
  и так печатает в сайдбаре («Что показывает экран», «Почему это важно», «Что сделать»); статус
  пункта — «нет снимка» / «загружен, не одобрен» / «одобрен к печати». Механика одобрения
  (`complianceVisual.approved`) уже есть у Dow Jones / World-Check — LexisNexis добавляется как
  третий вид `lexisnexis_report`, а не новый механизм.

Каждый пункт несёт `pages: number[]` из трассы ссылок и ссылку на PNG страницы — аналитик решает,
глядя на то, что увидит клиент.

### 3. Где хранятся решения

Одна таблица `dp_review_decisions` (план R10.8b, обобщённый на три вида пунктов):

```
id, caseId, itemKind (evidence|finding|compliance|compliance_visual), itemKey,
status, note, caveatText, reviewedBy, reviewedAt,
decisionVersion, previousDecisionId, isActive, source (ui|import|fixture), metadata Json
```

- История, а не перезапись: новое решение делает прежнее неактивным (`isActive=false`) и ссылается на
  него. Это прямо по правилу «состояние — это данные»: видно не только что решили, но и что решали
  раньше и кто.
- Каждое решение — событие в `dp_audit_logs` (таблица есть).
- Снимки страниц LexisNexis — файлы в приватном хранилище (`private-store`, как у скриншотов),
  строка-мастер в `dp_database_profiles` с `rawMetadataSafe.complianceVisual` — ровно как у Dow Jones.
- Файл `admin-review-decisions.json` остаётся для классического контура и читается **вторым**:
  решение в таблице сильнее файла для одного и того же ключа. Через один шаг после запуска таблицы файл
  из канонического пути убирается (решение 1).

Почему не файл на томе, как сейчас: файл не версионирует решения, не знает автора, не переживает
переезд тома и не даёт спросить «какие решения вошли в выпуск №3». Все четыре свойства нужны, потому
что выпуск — юридически значимый документ, и на вопрос «почему в отчёте нет X» надо отвечать
данными.

### 4. Как решения доезжают до отчёта — одним путём, пересборкой

Правило одно: **в отчёт попадает только то, что собрано из данных.** Ни одна кнопка не меняет
документ мимо сборки.

- **Материалы.** `analyst-overrides-loader.ts` уже применяет `WRONG_SUBJECT` и `EXCLUDED` и
  классификацию негатива. Добавляется одно: `CONFIRMED_SUBJECT` → решение `SUBJECT_MATCH` с кодом
  причины `analyst_confirmed`. Код причины печатается в артефакте `subject-resolution.json`, а на
  листе «Кого проверяли» появляется строка «N материалов отнесены к проверяемому лицу решением
  аналитика».
- **Темы.** Новый проход в синтезе находок, симметричный `mergeGuaranteedFindings`: подтверждение
  переводит улики темы из корзины `LIKELY` в `SUBJECT_MATCH`, находка пересобирается тем же
  синтезатором (цитаты, счёт, уровень — как у любой подтверждённой темы); снятие переносит находку в
  `excludedFindingIds` с причиной; примечание добавляется к утверждению последней строкой и проходит
  те же ворота текста, что и всё остальное. Матрица рисков перестаёт печатать «Требует подтверждения»
  у подтверждённой темы, потому что её больше нет в корзине `LIKELY` — а не потому, что ярлык
  заменили.
- **Комплаенс.** Статусы записей доезжают уже сегодня. Снимки: `buildComplianceVisualAssets`
  (классический) переносится в канонические визуальные активы и привязывается к слотам
  `p34_dow_jones` / `p35_lexis_visual` / `p36_lexis_visual_2` (сегодня второй слот слит с первым —
  при двух и более страницах снимка слияние снимается). Сайдбар страницы заполняется описанием
  аналитика; под снимком печатается происхождение: «Снимок отчёта LexisNexis от <дата отчёта>,
  загружен <дата загрузки>» — и подпись по решению 6.
- **Ворота те же.** Текст аналитика проходит бюджеты клиентского текста, сторож внутренних кодов,
  проверку висящих хвостов — **при сохранении**, в API, а не в рендере: аналитик видит отказ сразу
  («примечание длиннее 320 знаков», «в тексте служебный код»), а не через пять минут сборки.
- **Цена пересборки.** Аналитика и дека пересчитываются полностью (модель на них не тратится);
  стадии модели платятся по изменившимся пакетам секций — ключ пакета включает текст находок, и
  подтверждение темы обесценивает только её пакеты. Точную цену круга проверки на реальном прогоне
  надо **померить** в первом шаге, а не обещать.

### 5. Интерфейс

Новая вкладка кейса «Проверка перед выпуском» (для унифицированных джоб; классическая страница
ручной проверки остаётся классическому контуру и убирается отдельным шагом — решение 1):

- шапка: состояние («черновик, круг 2», «выпуск от 05.09, круг 3»), счётчики открытых пунктов по
  видам, две ссылки на скачивание, кнопки **«Пересобрать черновик»** и **«Выпустить»**;
- предупреждение «есть решения, принятые после начала последней сборки» — по несовпадению
  `decisionsDigest` джобы с текущим хешем решений; это и есть ответ на гонку «сохранили, пока
  собиралось»;
- список пунктов группами (материалы / темы / комплаенс), фильтры «открытые / все», у каждого пункта
  — страницы с миниатюрой PNG и действия; решение сохраняется сразу, без общей кнопки «сохранить»;
- «Выпустить» показывает перед подтверждением список открытых пунктов и по решению 7 либо блокирует,
  либо предупреждает;
- после выпуска вкладка показывает, какие решения вошли (список из `analyst-overrides-applied.json`,
  расширенного темами и комплаенсом), хеш документа и кто выпустил.

API (все под существующей защитой ролей): `GET …/unified-collection/review-sheet`,
`PUT …/review-decisions/{itemKind}/{itemKey}`, `POST …/compliance/visual-import` (провайдер
`LEXISNEXIS` добавляется к существующему), `POST …/unified-collection/release`,
`GET …/unified-collection/page-image?jobId&page`.

### 6. Порядок шагов — каждый со своим планом, красным логом и коммитом

1. **Черновик и выпуск.** Блок `release`, строка-черновик на обложке и в подвале, право «выпуск
   отчёта», ограничение скачивания для `CLIENT_VIEWER`, кнопка «Выпустить» как пересборка + пометка.
   Замер цены круга на реплее прогона 0053. Ничего из данных ещё не редактируется — шаг мал и
   безопасен.
2. **Лист проверки только для чтения.** Артефакт `review-sheet.json`, вкладка со списком пунктов,
   страницами и PNG, без действий. Проверяется на бандле 0053: лист обязан назвать все 201 строку
   «фамилия при запросе» и обе темы матрицы.
3. **Решения по материалам и темам.** Таблица `dp_review_decisions` (миграция аддитивная — только
   `CREATE TABLE`), API, действия во вкладке, `CONFIRMED_SUBJECT` в загрузчике правок, проход
   подтверждения/снятия тем в синтезе, примечание аналитика, ворота текста при сохранении. Тесты:
   решение доезжает до всех трёх точек (индекс деки, рамка снимка, плитка сетки) — это уже
   закреплённое правило, и новый вид решения обязан его пройти; мутации — откат каждого прохода.
4. **Ручной блок комплаенса.** Импорт снимка LexisNexis (`lexisnexis_report`), описание в трёх
   полях, происхождение под снимком, перенос `buildComplianceVisualAssets` в канонический контур
   для всех трёх баз, раздельные слоты при нескольких страницах. Растровая проверка страницы со
   снимком A4-пропорции — картинка портретная, а слот альбомный, и как она ляжет, надо увидеть
   растром, а не предполагать.
5. **Аварийный выход** — только если владелец скажет «да» в решении 5.

Вне программы: WYSIWYG-правка PDF; свободная переписка машинных формулировок (решение 2); правка
состава страниц руками.

## Решения владельца — до первой строки кода

1. **Хранилище решений.** (а) Таблица `dp_review_decisions` с историей и автором — рекомендую;
   (б) файл-артефакт на томе, как сегодня у классического контура. Следствие (а): миграция схемы на
   Railway (аддитивная), зато ответ «какие решения вошли в выпуск» — данными.
2. **Свободный текст аналитика.** (а) Только решения, текста нет; (б) примечание аналитика — одно
   предложение к теме и описание в трёх полях у снимка комплаенса, печатается с пометкой
   «аналитик» — рекомендую; (в) свободная переписка любых формулировок. Следствие (в): фраза без
   происхождения, ворота текста судят её как нашу, и правило «прослеживается до наблюдения» нарушено
   по построению.
3. **Что видит `CLIENT_VIEWER`.** (а) Только выпуск — рекомендую; (б) и черновик тоже.
4. **Черновик на листе.** (а) Строка «Черновик — не для передачи клиенту» на обложке и в подвале —
   рекомендую; (б) без пометки. Следствие (б): черновик и выпуск неотличимы в руках.
5. **Аварийный выход — загрузить вручную исправленный PDF как выпуск.** (а) Нет — рекомендую;
   (б) да, но с обязательной причиной, хешем файла, записью в аудит и без прохождения ворот,
   о чём говорит сама вкладка. Следствие (б): в системе появляется документ, о котором ни одна
   проверка ничего не знает.
6. **Подпись под ручным содержимым.** (а) Дата и слово «аналитик» без имени — рекомендую;
   (б) имя аналитика. Отчёт читает сам субъект, и имя сотрудника в его руках — отдельный вопрос.
7. **Выпуск при открытых пунктах.** (а) Разрешён, но перед подтверждением показывается список
   открытых пунктов, и их число записывается в выпуск — рекомендую; (б) запрещён, пока есть хотя бы
   один. Следствие (б): один спорный материал в приложении блокирует весь отчёт.
8. **Снимок LexisNexis отсутствует.** (а) Лист печатает то же, что сегодня («визуальный экспорт
   недоступен», записи текстом) — рекомендую; (б) лист не печатается вовсе. (Пустые листы Dow
   Jones / LexisNexis по прежнему решению остаются как есть.)
9. **Классическая страница ручной проверки.** (а) Оставить до конца программы, потом убрать одним
   шагом — рекомендую; (б) убрать сразу в шаге 2.
