# 0061 — Черновик и выпуск: состояние документа

Первый шаг программы 0060 «Ручной блок». Решения владельца от 05.09.2026: всё по рекомендациям,
**пометки о правках аналитика — только в админке** (в отчёте их нет). Ветка `feature/manual-review`;
Railway её не разворачивает, деплой по-прежнему из `feature/topvisor`.

## Зачем

Сегодня у собранного отчёта одно состояние: он есть. Клиенту его отдаёт та же кнопка, что и
аналитику, и «проверенный документ» от «только что собранного» неотличим ничем. Пока нет этого
различия, лист проверки (шаг 0062) некуда прикладывать: непонятно, что именно проверено и что
именно ушло клиенту.

Поэтому первым шагом заводится **состояние документа**: любая сборка даёт **черновик**, а
**выпуск** — это отдельное действие, которое пересобирает отчёт и помечает результат. Ничего из
данных этот шаг ещё не редактирует.

## Что делается

### A. Состояние живёт на джобе

К `UnifiedCollectionJob` добавляется блок:

```ts
release?: {
  state: "draft" | "released";
  /** Выпуск запрошен и идёт пересборка; на успехе превращается в released. */
  requested?: { by: string; at: string } | null;
  releasedAt?: string | null;
  releasedBy?: string | null;
  /** sha256 выпущенного PDF — чем этот документ отличим от любого другого. */
  documentSha256?: string | null;
};
```

- Блока нет вовсе (все прежние прогоны) — это **черновик**. Признак задаётся данными, а не словом:
  предикат `isReleasedReport(job)` один на весь продукт.
- Любая успешная сборка ставит `state: "draft"`, **кроме** той, что идёт по запросу выпуска.
  Документ изменился — выпуск устарел по построению.
- Выпуск = запрос (`requested`) + пересборка + пометка на успехе. Отдельной кнопки «пометить
  выпуском без пересборки» нет: иначе выпуском станет документ, собранный до последних решений.
- Пересборка провалилась — `requested` снимается вместе с восстановлением состояния. Иначе
  следующая, ни о чём не подозревающая пересборка молча выпустила бы отчёт.

Переход считает чистая функция `releaseStateAfterPrepare` — её и проверяют тесты; запись в джобу
делает оркестратор там же, где выставляет `reportLinks`.

### B. Черновик говорит о себе на обложке

Обложка черновика печатает строку «Черновик для проверки аналитиком — не для передачи клиенту»
перед обычной строкой конфиденциальности. У выпуска обложка прежняя.

Это **текст в нагрузке**, а не новая ручка рендерера: рендерер прошлой версии напечатает его как
обычный подзаголовок обложки. Окна деплоя у шага нет.

Подвал страниц (`cleeq · Конфиденциально`) не трогается: он зашит в рендерере, и его правка — это
уже окно деплоя. Названо вслух: у черновика отличается **обложка**, а не каждая страница.

`documentState` едет в сборку деки через `FragmentExtras` и входит в ключ кэша пакета
`FRONT_MATTER_MAIN` — иначе выпуск взял бы обложку черновика из кэша и напечатал бы клиенту слово
«черновик». Ключ уже устроен так же для решения о персоне, которое печатает тот же пакет.

### C. Клиент получает только выпуск

Новое право `report.release` (ADMIN, ANALYST) — им закрыт запуск выпуска.

Скачивание: `CLIENT_VIEWER` получает файл только у выпущенного отчёта; аналитик, ревьюер и
администратор — всегда, потому что им черновик и предназначен. Предикат
`downloadDenialForRole({ role, released })` чистый и офлайновый; маршрут скачивания и карта
доступности кнопок спрашивают его, а не выстраивают своё условие.

### D. Кнопка выпуска

`POST /api/digital-profile/cases/[id]/unified-collection/release`: право `report.release`, те же
условия допуска, что у пересборки (`assertRebuildEligibility`), запись `release.requested` и запуск
той же пересборки. Никаких платных вызовов — путь тот же, что у «Пересобрать отчёт».

## Чем проверяется

1. `release-state-of-the-report.test.ts` — переходы: сборки без запроса дают черновик; сборка по
   запросу даёт выпуск с временем, автором и хешем документа; провал пересборки снимает запрос;
   прежняя джоба без блока читается как черновик.
2. `draft-cover-says-it-is-a-draft.test.ts` — обложка черновика несёт строку о черновике, обложка
   выпуска не несёт; ключ кэша пакета `FRONT_MATTER_MAIN` различает состояния (иначе выпуск взял бы
   обложку черновика из кэша).
3. `client-viewer-downloads-only-released.test.ts` — предикат отказа: клиенту черновик не отдаётся с
   названной причиной, выпуск отдаётся; аналитику и администратору отдаётся всегда.

Мутации: откат каждой из трёх правок (переход состояния, строка обложки, ключ кэша, предикат
скачивания) обязан покрасить свой тест. Прогоны — полный контур (`npm run ci`, `build`, ворота деки,
растр, эталон золотого кейса) и дифф эталона вслух: строка обложки меняет клиентский текст только у
черновика, эталон собирается как выпуск.

## Что вне этого шага

- Лист проверки и любые решения аналитика (шаги 0062–0063).
- Ручной блок комплаенса со снимком LexisNexis (шаг 0064).
- Интерфейс вкладки «Проверка перед выпуском» — следующим шагом, сразу за этим.
- Подвал страницы: слово «черновик» на каждом листе потребовало бы правки рендерера и окна деплоя.
