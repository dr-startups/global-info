## Задача и границы

Посетителя можно создать, провести через шаг «Это вы?» и принять от него заявку; аналитик видит это
в карточке кейса и в списке дел. Прогон не запускается: ручка `run` отвечает `503` до этапа 3.

В рамках:

1. Таблица `dp_self_checks` одной миграцией.
2. Общий помощник подписи `auth/signed-token.ts`; `auth/session.ts` переходит на него без изменения
   формата токена сессии.
3. Модуль `src/modules/self-check/`: схемы, токен, квоты, капча, сервис, публичные проекции, обёртка
   ручек и гард.
4. Ручки `POST /api/self-check`, `GET /api/self-check/[publicId]`, `POST …/persona`,
   `POST …/persona/decision`, `POST …/lead`, заглушка `POST …/run`.
5. Действия аудита `SELF_CHECK_*`, `ipAddress` в `recordAudit`.
6. Служебная ручка `GET /api/digital-profile/cases/[id]/self-check`, панель «Проверка с сайта» в
   карточке кейса, фильтр «с сайта» в списке дел.
7. `docs/ENGINEERING.md`, раздел 9: модель, токен, квоты, контракт.

Вне рамок: лёгкий прогон, вердикт, суточный потолок прогонов и настоящая ручка `run` (этап 3);
страницы и клиент сайта (этап 4); обезличивание по сроку (этап 6 — гард уже отвечает `410` на
обезличенную запись); доверие к `x-forwarded-for` только от прокси площадки (этап 6, чеклист
безопасности); раннер смоков на Windows. Эталоны, `DECK_CONTENT_VERSION` и дека не трогаются.

## Контекст

- Подпись сессии — `auth/session.ts:48-100`: HMAC-SHA256 через Web Crypto, сравнение без утечки по
  времени, `createSessionToken:62`, `verifySessionToken:75`. Модуль работает и в edge-middleware
  (`src/middleware.ts`). **Тестов формата токена сессии в проекте нет** — ТЗ рассчитывает на них как
  на контроль выноса, поэтому контроль пишется на этом этапе.
- `storage/signed-url.ts` — отдельная подпись ссылок через `node:crypto`; ТЗ называет её
  существующим исключением.
- `http/errors.ts:14` — `ErrorCode` закрыт восемью значениями, `ConflictError:73` уносит причину в
  `details.reason`. Классов со статусами `410`, `429`, `503` нет.
- `services/case-service.ts:180` — `createCase` открывает свою транзакцию и повторяет её при гонке
  номера дела (`generateCaseNumber:159` считает `count`); чужой транзакции не принимает.
- `services/subject-profile-admin.ts:131` — `saveSubjectProfileEdits` пишет профиль **файлом** в
  хранилище (`:213`), а не в базу; ИНН проверяет только по форме (`:160`).
- `services/subject-persona-check.ts`: `subjectInputHash:111` — SHA-256 ФИО, алиасов и даты без
  соли; `buildPersonaPanel:485` — бюджет 20 с, офлайн-вето; `recordPersonaCheck:723`;
  `loadLatestPersonaCheck:745`; `recordPersonaDecision:810` — решение пишется один раз, тот же ответ
  идемпотентен, другой — `409 PERSONA_DECISION_ALREADY_RECORDED`. Маршрут панели оператора не
  защищён от параллельных вызовов: каждый `POST` собирает панель заново.
- `services/audit-log-service.ts:89` — `recordAudit` не принимает `ipAddress`, колонка в таблице
  есть (`prisma/schema.prisma:1084`).
- `auth/auth-config.ts:17` — без `DIGITAL_PROFILE_SESSION_SECRET` секретом становится
  `change-me-in-production`; `assertAuthConfigSafe` смотрит на это только при включённом входе.
- `validation/case-schemas.ts:101` — запрос списка дел без признака происхождения;
  `caseListWhere` — `case-service.ts:250`.
- SmartCaptcha: `POST https://smartcaptcha.cloud.yandex.ru/validate`, форма `secret`, `token`, `ip`;
  ответ `{ status: "ok" | "failed", message, host }`. Документация советует ответ с кодом не 200
  считать ответом `ok`, чтобы не задерживать людей.
- Макет, экран заявки: имя, один способ связи переключателем (телефон / Telegram / email), удобное
  время вариантами `any`, `morning`, `day`, `evening`, комментарий.
- На стенде запросы идут без `x-forwarded-for`: все посетители стенда — один адрес.

## Решения реализатора

1. **Коды ответов — существующие восемь**, причина в `details.reason`: `400 VALIDATION_ERROR`
   (поля, `CAPTCHA_FAILED`); `403 FORBIDDEN` (`SELF_CHECK_FORBIDDEN`); `404 NOT_FOUND`;
   `409 CONFLICT` (причина по месту); `410 NOT_FOUND` (`SELF_CHECK_EXPIRED`); `429 FORBIDDEN`
   (`RATE_LIMITED`); `503 MODULE_DISABLED` (`SELF_CHECK_DISABLED`, `CAPTCHA_NOT_CONFIGURED`,
   `SELF_CHECK_SECRET_NOT_CONFIGURED`, `NOT_IMPLEMENTED_YET`).
2. **Порядок гарда:** рубильник → запись по `publicId` (нет — `404`) → обезличена (`410`) → cookie
   (нет, чужая подпись, истекла, другая проверка — `403`). `410` раньше cookie, потому что срок
   cookie равен сроку хранения: к обезличиванию cookie тоже истекла, и человек читал бы «откройте в
   том же браузере» вместо «срок истёк». Разница `404`/`403` существования не выдаёт — в `publicId`
   144 случайных бита.
3. **Cookie — путь `/api/self-check`**, а не ещё и `/check`, как в ТЗ 3.3: страница мастера данных не
   читает (ТЗ 3.1 — всё через API), а путь у cookie один — два пути значили бы две cookie.
4. **Секрет.** Токен и хеши подписываются `DIGITAL_PROFILE_SESSION_SECRET`. В deploy-like окружении
   секрет по умолчанию или короче 16 знаков — `503 SELF_CHECK_SECRET_NOT_CONFIGURED`: иначе токен
   посетителя подделывается по значению, которое лежит в открытом коде.
5. **Хеши с солью** — HMAC тем же примитивом, что подпись. `subjectHash` — HMAC от
   `subjectInputHash({ ФИО, алиасов нет, дата })`: нормализация имени остаётся одна, а соль не даёт
   восстановить ФИО и дату перебором по таблице.
6. **Дедупликация — по cookie** (решение владельца): проверка из токена с тем же `subjectHash`,
   моложе `SELF_CHECK_DEDUPE_DAYS`, не обезличенная и не пойманная ловушкой → `200
   { existingPublicId }`; иначе новая проверка. Идёт до лимитов: возврат к своей проверке ничего не
   создаёт и лимита не тратит.
7. **Порядок создания:** схема → капча → дедупликация → лимит по IP → ловушка → создание.
8. **Ловушка** — строка `BLOCKED` с `honeypotTripped` **без кейса**. Отступление от ТЗ 3.2
   (`caseId` необязателен): список дел — рабочее место оператора, как и у фикстур смоков, а мусору
   бота там не место. Ответ как у успешного создания, cookie ставится; панель, решение и заявка по
   такой записи — `409`.
9. **Создание — одна транзакция.** Из `createCase` выносится `createCaseInTx` и общий повтор при
   гонке номера; кейс, запись проверки, аудит и файл профиля пишутся в одной транзакции, файл —
   последним: не записался — база откатывается. Остаток риска: отказ коммита после записанного файла
   оставит файл профиля без кейса.
10. **Профиль субъекта** пишется, только если есть что писать: ИНН → `inn`; город, место работы,
    должность и домен сайта → `contextIdentifiers`.
11. **Панель персоны собирается один раз.** Захват `CREATED → PERSONA_PENDING` одним `updateMany`;
    второй вызов во время сборки — `409 PERSONA_BUILD_IN_PROGRESS`, после — последняя панель без
    новой траты. Захват без панели старше 60 с (процесс умер посреди сборки) перехватывается; ошибка
    сборки возвращает статус `CREATED`.
12. **Заявка на этапе 2** принимается и в `PERSONA_DECIDED`: прогона ещё нет, решение — последнее
    состояние, из которого посетитель сам не сдвинется, а приёмка этапа по ТЗ — «создание → панель →
    решение → лид». На этапе 3 правило сужается до `DONE`/`FAILED`/`BLOCKED` (ТЗ 4), тест заменяется.
    Повторная заявка обновляет контакты; статус лида, выставленный менеджером, не сбрасывается.
13. **Капча.** Без ключа: deploy-like — `503 CAPTCHA_NOT_CONFIGURED`, локально — пропуск с
    предупреждением. С ключом: нет токена или `status ≠ ok` — `400 CAPTCHA_FAILED`; ответ не 200 или
    сервис недоступен — пропуск с предупреждением по рекомендации Яндекса (расход держат лимиты);
    офлайн-контур без подменённого клиента — `400`, в сеть не ходит.
14. **`SELF_CHECK_BLOCKED` в аудит** — на лимит и ловушку, но не на отказ капчи и не на выключенный
    рубильник: такой отказ боту ничего не стоит, и строка журнала на каждый сделала бы журнал
    мишенью. Контакты в аудит не пишутся — только какие каналы заполнены.
15. **`blockedReason`** — колонка сверх ТЗ 3.2: проекция отдаёт причину `BLOCKED`/`FAILED`, а этап 3
    пишет туда отказ квоты. Заводится этой же миграцией, чтобы этап 3 не делал вторую.
16. **`CONSENT_VERSION`** — `src/modules/site/content/legal.ts`. Текста согласия ещё нет (этап 4),
    версия называет черновик и меняется вместе с текстом.
17. **Служебная ручка на кейс без проверки** отвечает `data: null`, а не `404`: панель монтируется в
    карточке каждого кейса, и отсутствие проверки — не ошибка.
18. **Пробел для этапа 6:** `ipAddress` в `dp_audit_logs` обезличивание записи проверки не сотрёт.
