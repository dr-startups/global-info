# Шаг 04. Покрытие провайдеров, честная готовность и разрыв в compliance

**Статус:** ГОТОВ К РАБОТЕ (требует решения владельца продукта по compliance)
**Файлы:** `src/modules/digital-profile/providers/config.ts`,
`src/modules/digital-profile/providers/capabilities.ts`,
`src/app/api/digital-profile/providers/route.ts`
**Приоритет:** P0 для Serper, P1 для остального.

---

## 04.1. Половина структуры отчёта держится на одном ключе

Отчёт построен вокруг двух регионов — RU и UAE. На живом прогоне без
`SERPER_API_KEY` недоступными оказались сразу три провайдера:

```
google                   unavailable
orion_profile            unavailable
orion_uae_international  unavailable
```

То есть **весь UAE-контур и весь Google-контур** обеспечиваются одним ключом Serper.
Частично дыру закрывает Arsenkin (`check-top` умеет Google RU и Google UAE), но
базовый сбор поверхностей, ORION-профиль и международный контур — нет.

**Действие:** получить ключ Serper и внести в `.env`. Без него оценка качества
отчёта проводится на половине задуманной структуры, и любые выводы о «пустых
слайдах UAE» будут артефактом конфигурации, а не свойством кода.

## 04.2. Провайдер отчитывается «готов», не будучи готовым

Эндпоинт `/api/digital-profile/providers` на прогоне с незаполненным ключом
показывал:

```
GOOGLE   kind=REAL   status=ENABLED   supportsRealCalls=true   missingConfigKeys=[]
```

При том что `SERPER_API_KEY` содержал плейсхолдер `<<<FILL>>>`. Проверка готовности
смотрит только на непустоту строки, поэтому любое мусорное значение читается как
валидный ключ. Оператор видит зелёный статус и узнаёт правду только из пустого
отчёта.

**Решение:** валидация формы ключа (длина, префикс, отсутствие плейсхолдеров вида
`<<<`, `change-me`, `TODO`) плюс опциональная проверка живым лёгким запросом с
кэшированием результата. Статус `ENABLED` обязан означать «проверено», а не
«переменная не пуста».

## 04.3. Compliance-блок никогда не наполнялся реальными данными

Обнаружено при переходе на `real_only` (шаг 01): провайдеры `ai_profile` и
`compliance` отвалились с причиной «provider has no real implementation in
real_only mode». До этого их наполняли mock-агенты — 2 и 3 «находки»
соответственно.

Состояние источников:

```
DOW_JONES    DISABLED   нет ключей, нет базового URL
LEXISNEXIS   DISABLED   нет ключей, нет базового URL
WORLD_CHECK  DISABLED   нет ключей, нет базового URL
```

Реализованы только заглушки и ручной импорт. Это **продуктовый разрыв, а не баг**:
эталонный ORION наполняет эти разделы реальными подписками, здесь на их месте была
синтетика.

**Требуется решение владельца продукта.** Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Подключить реальную подписку (LexisNexis / Dow Jones / World-Check) | паритет с референсом | дорого, длинный цикл закупки и юридического согласования |
| Ручной импорт аналитиком (механика уже есть) | работает сегодня, законно | не масштабируется, требует человека на каждый кейс |
| Честно показывать «проверка по санкционным базам не проводилась» | быстро, не вводит в заблуждение | раздел выглядит слабее, чем у конкурента |

Чего делать **нельзя** — возвращать mock. Синтетическое «совпадение по санкционным
спискам» в документе о реальном человеке недопустимо ни при каких обстоятельствах.

## 04.4. Скриншоты SERP не собираются

`SERP_CAPTURE_PROXY_RU` / `SERP_CAPTURE_PROXY_UAE` пусты, браузеры Playwright в
dev-образ не устанавливаются. Отчёт обходится синтетическими SVG-снимками выдачи.
Для референсного качества нужны настоящие скриншоты — решается прокси + установкой
браузеров, вынесено сюда как известное ограничение, не как задача первой волны.

## Критерий приёмки

- [ ] `SERPER_API_KEY` заполнен, UAE-контур даёт непустые поверхности;
- [ ] статус провайдера `ENABLED` подтверждается проверкой ключа, плейсхолдеры
      распознаются как «не настроен»;
- [ ] по compliance принято и зафиксировано продуктовое решение;
- [ ] в отчёте нет разделов, наполненных синтетическими данными.
