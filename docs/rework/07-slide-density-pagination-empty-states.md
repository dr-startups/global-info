# Шаг 07. Плотность слайдов, пагинация и пустые состояния

**Статус:** ГОТОВ К РАБОТЕ (замерено на сгенерированном отчёте)
**Файлы:** `src/modules/digital-profile/orion-golden/deck-sections/semantic-summary-pagination.ts`,
`.../deck-assembler.ts`, `.../fragment-builders/`, `renderer/orion_golden_render/`
**Приоритет:** P1 — визуальная сторона жалобы; лечится после шагов 05–06.

---

## Проблема

Отчёт на контрольном кейсе: **56 слайдов, 48 с контентом, 8 в пустом состоянии**.
Но «с контентом» здесь означает «есть хотя бы один буллет» — фактическая плотность
несопоставима с референсом.

### 07.1. Пагинация размазывает тонкое содержание

Резюме занимает **одиннадцать** страниц-продолжений. Страница 7 из 56 озаглавлена
«Резюме — темы риска (продолжение 4/11)» и содержит **один буллет** на ~15 % высоты
листа; остальные 85 % — белое поле. Страница 14 — «Резюме — продолжение
(продолжение 11/11)», снова один блок текста и пустая страница под ним.

Механика понятна: 5 findings × несколько полей разложены по слотам с фиксированной
ёмкостью, и вместо уплотнения включается «продолжение». Чем беднее содержание, тем
**больше** страниц — ровно наоборот тому, что нужно.

### 07.2. Рекомендации вырождаются в повтор одной строки

Страница 14 целиком:

> **Следующие проверки.** 1) Сверить первоисточники и статус материалов по теме
> «Деловые связи, владение и контрагенты». 2) Подготовить согласованную позицию для
> KYC и партнёрских запросов. 3) Сверить первоисточники и статус материалов по теме
> «Криминальные и судебные материалы». 4) Сверить первоисточники и статус материалов
> по теме «Семейные и личные связи»... 8) Сверить первоисточники и статус материалов
> по теме «Репутационные скандалы и негативные сюжеты».

Восемь пунктов, из которых семь — одно и то же предложение с подставленным
названием темы. Это не рекомендации аналитика, а результат цикла по темам.

### 07.3. Пустые состояния не различают причину

Восемь слайдов в пустом состоянии:

```
p11_ru_suggestions_yandex   no-suggestions
p14_ru_images_1..4          no-images / no-images-continued   ← четыре подряд
p30_uae_images              no-images
p31_uae_knowledge           no-ai-answers
p35_lexis_visual            VISUAL_ASSET_UNAVAILABLE
```

Четыре последовательных слайда «нет изображений» — это структурный дефект: раздел
из четырёх слотов резервируется независимо от наличия данных. Плюс `p35_lexis_visual`
показывает техническую заглушку `VISUAL_ASSET_UNAVAILABLE` — внутренний код в
клиентском документе.

Важно: причина «не собрано» и причина «собрано, но пусто» для читателя принципиально
разные, а выглядят одинаково. Сейчас, при отсутствующем Serper, «нет изображений»
означает «источник не подключён», но отчёт этого не говорит.

### 07.4. Противоречие уровней риска на одном слайде

Страница 3 («Резюме») одновременно содержит:

- плашку «Итоговая оценка: **Высокий** риск»;
- текст «...но итоговая оценка **критическая**».

Два разных вердикта в двух блоках одного слайда — следствие того, что плашку
считает детерминированный builder, а текст пишет GPT по своим данным.

### 07.5. Мёртвый KPI

Плитка «0 — Вероятно о субъекте» всегда ноль: уровень `LIKELY_SUBJECT` в
классификаторе не выдаётся (`likelySubject: 0` при 207 `subjectMatch`). Показатель
занимает место на главном слайде и не несёт информации.

## Решение

### 07.6-a. Уплотнение страниц-продолжений — СДЕЛАНО

Причина найдена в `packContinuationPages`: блок длиннее 66 % бюджета буллета
получал **страницу целиком в одиночку**.

```ts
const long = b.text.length > Math.floor(bulletBudget * 0.66);
if (long) { flush(); pages.push([b]); continue; }
```

Бюджет буллета — 900 символов, то есть порог 594. Типичный блок темы занимает
600–900 символов, поэтому почти каждый монополизировал страницу: отсюда девять
страниц-продолжений с одним буллетом примерно на шестой части листа.

Бинарное правило заменено накопительным бюджетом страницы
(`CONTINUATION_PAGE_BUDGET_FACTOR = 3` бюджета буллета, не более
`MAX_BLOCKS_PER_CONTINUATION_PAGE = 3` блоков). Страницу в одиночку получает
только блок, который сам по себе не помещается в бюджет — рядом с ним всё равно
ничего не встало бы. Раскладка соответствует тому, что вёрстка уже
поддерживала: прежний код допускал три коротких блока на странице.

### 07.7-a. Схлопывание одинаковых рекомендаций — СДЕЛАНО

`new Set` убирал только точные дубликаты, а строки различались названием темы,
поэтому восемь тем давали восемь копий одного предложения — целый слайд
«Сверить первоисточники и статус материалов по теме «X»».

`collapseRecommendations` группирует рекомендации по «форме» предложения
(текст с обнулённой цитируемой частью) и объединяет однотипные в одну строку со
списком тем. Содержательно разные рекомендации сохраняются, порядок первого
появления не меняется.

Покрытие: `tests/unit/summary-density.test.ts` — 9 случаев (схлопывание,
сохранение различающихся, дедупликация одной темы, порядок, пустые строки;
плотность страниц, соблюдение бюджета, сокращение числа страниц, сохранность
всех блоков).

### 07.8-a. Внутренние коды в клиентском тексте — СДЕЛАНО

В деке контрольного прогона на странице профиля стояло: «Визуальный экспорт
страницы недоступен (**VISUAL_ASSET_UNAVAILABLE**); содержимое записи приведено
в текстовом виде». Отчёт читает человек, а не оператор системы.

Само это место исправлено, но правило сделано общим, а не про один код: иначе
следующий такой же появится незамеченным. `scanDeckForInternalCodes` идёт в
`validateAssembly`, то есть проверка выполняется на **каждой сборке деки**, а не
в отдельном тесте. Аббревиатуры due diligence (PEP, OFAC, KYC, ОГРНИП) кодами не
считаются — иначе правило вычистило бы законные слова из раздела комплаенса.

Тест `internal-code-scan.test.ts` проверяет правило на сохранённой деке **до**
исправления: если оно перестанет срабатывать, это будет видно там, а не у
клиента.

Различение «не собрано» / «собрано — пусто» уже работает: `coverageContent`
разводит `NOT_COLLECTED`, `MEASURED_EMPTY` и `COLLECTION_FAILED` и печатает
человеческую причину с контуром проверки.

### 07.9-a. Единый источник вердикта — СДЕЛАНО

Плашку «Итоговая оценка: Высокий риск» считала аналитика, а текст «…но итоговая
оценка критическая» писала модель — промпт **прямо просил** её вернуть
`overallRiskLevel`. Два вердикта об одном человеке на одном слайде.

Уровень риска — вывод из доказательств, и считается он один раз. Модель
получает готовый уровень как вход и объясняет его. Промпт при этом не гарантия,
поэтому поле в ответе перезаписывается (`withDeterministicRiskLevel`) — и в
одиночном вызове, и в своде map-reduce.

`INSUFFICIENT_DATA` уровнем риска не становится: «недостаточно данных» — это не
«низкий риск», и подменять одно другим значит успокаивать читателя там, где
проверка не дала ответа.

### 07.5-a. Мёртвая KPI-плитка — снята данными

«Вероятно о субъекте» всегда показывала ноль, потому что классификатор не
выдавал `LIKELY_SUBJECT`. После правок шагов 10–13 уровень выдаётся четырьмя
путями (контекст, полное имя на мягкой поверхности, запрос по субъекту, общий
подтверждённый домен), и на прогоне с полным набором провайдеров плитка
показывала 31. Плитка осталась: теперь это измерение, а не структурный ноль.

### 07.6-b. Ёмкость страницы-продолжения — СДЕЛАНО (и нашлось хуже)

Замер отрендеренных страниц финального прогона: **17 листов из 52** с пустым
хвостом больше трети, худший — один блок в 115 знаков на весь лист. Пять
страниц «Россия — резюме аудита» подряд, заполненных на 18–62 %.

Причина — три ответа на один вопрос «сколько блоков помещается на страницу»:

| где | ответ | чем оказался |
|---|---|---|
| `template-registry.maxBulletsPerSlide` | 2 | калибровка **первой** страницы, где есть KPI-плитки, нарратив и карточка «Действие» |
| `withContinuations` | делит по счёту, поровну | продолжения обвязки не несут с шага 13 (D3/D4), но освободившееся место им не отдали |
| `ctx.bullets(..., max_items=3)` + мерка высоты | 1–2 | мерка завышала высоту в **1.7–1.8 раза** |

**Хуже пустоты нашлась потеря.** Страница «Обзор цифрового профиля» отдавала
рендереру **четыре** темы повышенного внимания и не делилась вовсе — этот
построитель разбиения не знал. Рендерер рисовал то, что влезало под шестью
KPI-плитками, а остальное **молча выбрасывал**: до клиента дошла **одна тема из
четырёх**, и следа об этом не было ни в артефактах, ни в логах.

Сделано:

1. **Мерка приведена к тому, что рисуется.** Прежняя мерила весь блок одним
   куском кеглем тела с межстрочным 1.2 и отбивкой 6 pt между всеми строками, а
   строки «Где видно…» и «Всего по теме…» рисуются кеглем подписи, с отбивкой
   1 pt и межстрочным 1.12; сверху лежал ещё запас 1.18. Теперь каждая строка
   меряется своим кеглем, запас 1.08. Замер: превышение факта было 1.82× и
   1.71×, стало 1.36× и 1.21× — с запасом в безопасную сторону.
2. **Рендерер о потере сообщает.** Выброшенные блоки идут в телеметрию
   (`droppedBullets`/`droppedLines`), а сверка геометрии поднимает
   `CONTENT_DROPPED_BY_RENDERER` уровня CRITICAL. Молча содержимое больше не
   исчезает.
3. **Ёмкость продолжения записана там же, где ёмкость страницы** —
   `maxBulletsPerContinuation`. Для `regional-summary` это 3 по замеру: без
   обвязки три тематических блока занимают ~83 % полосы. Шаблоны без замера
   ведут себя как прежде.
4. **Обзор профиля проходит через разбиение** с ёмкостью первой страницы 1 — по
   замеру этой страницы обвязка оставляет под блоки около 29 % листа.
5. **Хвост не остаётся одиноким.** Девять блоков при ёмкости 2 + 3 давали
   2 | 3, 3, 1; выравнивание за счёт соседа даёт 2 | 3, 2, 2. Правило общее с
   пагинатором резюме — `balanceTailPage`.

Замер после правок на тех же данных: листов с пустым хвостом больше трети —
**17 → 12**, худший — 0.18 → 0.26, страниц в деке 50 → 49 при том же
содержимом. Оставшиеся редкие страницы — таблицы с малым числом строк
(`orion_golden_search_table`): там нечем заполнять, и придумывать строки нельзя.

Покрытие: `tests/unit/slide-capacity-no-content-loss.test.ts` (13 случаев),
`tests/unit/pdf-review-phase-f.test.ts` (+1).

### 07.6. Уплотнение вместо продолжений (исходная формулировка)

Правило: **новая страница создаётся только когда предыдущая заполнена ≥ 70 %**.
Если весь раздел не набирает одной полной страницы — он занимает одну страницу, а
не одиннадцать. Пагинатор (`semantic-summary-pagination.ts`) должен сначала
собирать содержимое, измерять его и лишь затем принимать решение о разбиении.

### 07.7. Рекомендации — из содержания, а не из цикла по темам

Рекомендация должна отвечать на вопрос «что конкретно проверить в этом материале».
Формируется вместе с claim'ом (шаг 05.2), где уже есть статус утверждения и
источник. Одинаковые рекомендации схлопываются в одну.

### 07.8. Честные и информативные пустые состояния

- различать `NOT_COLLECTED` (источник не подключён / сбор не выполнялся) и
  `EMPTY_VALID` (собрано, данных нет) — механика уже есть в
  `provider-surface-coverage.json`, до слайда она не доходит;
- текст пустого состояния объясняет причину человеческим языком: «Поиск по
  изображениям не выполнялся: провайдер не подключён» вместо «нет изображений»;
- **резервировать слоты по факту данных**: четыре слайда изображений не создаются,
  если изображений нет вовсе;
- ни один внутренний код (`VISUAL_ASSET_UNAVAILABLE`) не попадает в клиентский
  документ.

### 07.9. Единый источник вердикта

Уровень риска считается один раз в аналитике и используется и плашкой, и текстом.
GPT получает уже вычисленный уровень как вход и не выводит собственный.

## Критерий приёмки

- [x] ни один блок не теряется при разбиении, а выброшенное рендерером
      содержимое поднимает CRITICAL вместо тишины (07.6-b);
- [~] нет страниц с заполнением < 40 % при непустом разделе: осталось шесть,
      и все — таблицы с малым числом строк, где заполнять нечем;
- [ ] резюме занимает ≤ 3 страницы;
- [ ] в списке рекомендаций нет двух пунктов, отличающихся только названием темы;
- [x] пустое состояние называет причину и различает «не собрано» / «собрано — пусто»;
- [x] внутренние коды отсутствуют в PDF — проверка идёт в `validateAssembly`
      на каждой сборке деки, не только в тесте;
- [x] уровень риска в плашке и в тексте совпадает — источник один, ответ
      модели к нему приводится;
- [x] KPI-плитки, всегда равные нулю, убраны или заполняются — «Вероятно о
      субъекте» наполнилась после правок шагов 10–13 (31 на контрольном прогоне).
