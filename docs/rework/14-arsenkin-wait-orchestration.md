# Шаг 14. Ожидание Arsenkin оркеструет система, а не пользователь

**Статус:** СДЕЛАНО (проверяется живым платным прогоном)
**Источник:** ручное тестирование заказчика, 26.07.2026
**Файлы:** `services/arsenkin-poll-budget.ts`, `workflow/auto-resume.ts`,
`services/unified-orion-collection-orchestrator.ts`,
`app/api/.../unified-collection/route.ts`, `client/CaseHeader.tsx`
**Приоритет:** P0 — пользователь выполнял работу оркестратора.

---

## Наблюдение

> При анализе в UI вылезает ошибка «Arsenkin durable poll exceeded 40
> attempts», после которой можно нажать кнопку начать заново. Далее вылезла
> аналогичная ошибка, только с кнопкой «Продолжить импорт Arsenkin», при этом в
> очереди запросов Arsenkin в ЛК всё отправлено, запросы были, некоторые
> находились в состоянии выполнения. После того, как несколько раз нажимали
> кнопку ретрая, сбор данных пошёл опять, и в конечном итоге результат появился.

Ключевая деталь — **в кабинете провайдера задачи выполнялись**. Прогон был
здоров, отказ был выдуман нами.

## Причина: бюджет считал не то

`pollAttempt` увеличивался на **каждом** опросе, включая те, где провайдер
честно работал:

```ts
const attempt = Math.max(0, Number(job.pollAttempt ?? 0)) + 1;
if (attempt > MAX_ARSENKIN_INGEST_POLL_ATTEMPTS) { /* отказ */ }
```

При потолке паузы в 30 секунд сорок опросов — это около **двадцати минут**, то
есть ровно длина честного полного прогона пяти агентов. Бюджет попыток работал
как таймер и срабатывал на здоровой работе.

Это та же ошибка, что A2 из шага 13 («бюджет попыток — это бюджет времени»),
только во второй, независимой реализации: там я поднял потолки у `WorkflowStep`,
а этот счётчик остался со старой семантикой.

## Почему помогала кнопка, а система не справлялась сама

Ручное восстановление обнуляло счётчик:

```ts
pollAttempt: ingestResume || renderResume ? 0 : job.pollAttempt ?? 0,
```

А автоматическое возобновление (`bounded-resume:from-arsenkin-ingest`) — **нет**.
Поэтому автоматический повтор возвращал прогон в опрос со счётчиком, уже равным
пределу, и следующий же тик снова объявлял отказ. Каждое нажатие покупало ещё
двадцать минут; сам по себе прогон сдвинуться не мог никогда.

Отсюда и вся картина: «нажали несколько раз — пошло». Оркестрация лежала на
пользователе, потому что только у него была кнопка, обнуляющая бюджет.

## Решение

### 14.1. Бюджет измеряет тишину, а не время

`arsenkin-poll-budget.ts` — чистый модуль. Считается **сколько опросов подряд
прошло без продвижения**. Продвижением считается рост любого из: терминальных
агентов, принятых результатов, выполненных задач, наблюдений. Пока задачи
двигаются, ожидание не тратится.

Первый замер продвижением не считается — иначе перезапуск обнулял бы счётчик, и
застрявший прогон ждал бы вечно.

Сверху — общий срок ожидания (4 часа): наблюдённый полный прогон занимал около
двадцати минут, так что это заведомо больше любого честного и при этом
ограничивает худший случай.

Пауза между опросами теперь растёт **только при простое**: продвижение — не
повод ждать дольше.

### 14.2. Автоматический путь умеет то же, что кнопка

`bounded-resume:from-arsenkin-ingest` обнуляет счётчик простоя. Иначе
«повторяемый отказ» — неправда: повтор упирается в тот же предел мгновенно.

Общий срок при этом **не продлевается**: он и ограничивает худший случай,
сколько бы возобновлений ни случилось. Раньше ограничения не было вовсе —
ручные нажатия продлевали прогон бесконечно.

### 14.3. Отказы различаются по излечимости

Исчерпанная тишина повторяема: провайдер мог замолчать временно. Исчерпанный
общий срок — нет: возобновление упрётся в него сразу же, и предлагать кнопку
значит звать оператора чинить то, что кнопкой не чинится.

### 14.4. Кнопка появляется, только если без неё не сдвинется

`workflow/auto-resume.ts`: пока у шага есть запланированный повтор (есть срок,
бюджет попыток не исчерпан), пользователю показывается ожидание — «система сама
вернётся к работе», — а не приглашение вмешаться. Код ошибки в шапке при этом
не печатается: запланированное продолжение это не отказ.

Основание для кнопки ровно одно: **само не продолжится**. Стадия, код ошибки и
то, «выглядит ли это как отказ», к вопросу отношения не имеют — пользователь
нажимает не потому, что что-то сломалось, а потому что без него дело не
сдвинется.

## Критерий приёмки

- [x] опрос, на котором провайдер продвинулся, бюджет не тратит;
- [x] автоматическое возобновление обнуляет счётчик простоя так же, как кнопка;
- [x] общий срок ожидания не продлевается возобновлениями;
- [x] пока запланирован автоматический повтор, кнопка восстановления не
      предлагается, а показывается ожидание;
- [ ] на живом платном прогоне пользователь ни разу не нажимает ретрай —
      проверяется регрессионным прогоном.

Покрытие: `tests/unit/arsenkin-poll-budget.test.ts` — 24 случая.

## Что осталось непроверенным

Все изменения — про поведение во времени на живом провайдере, и юнит-тесты
проверяют правила, а не то, что провайдер ведёт себя как ожидается. Настоящая
проверка — регрессионный прогон без единого нажатия.
